# 产品定义与 MVP 边界（VISION）

> **本文档是范围判定的唯一锚点。** 任何"某能力放哪个阶段"的争论，先回看本文件再下结论；禁止凭直觉在细节文档里改阶段归属。
> 当前锁定状态：2026-08-26（工单模板/关联归属 2a，见 §3）。

## 1. zhuzhao 是什么

企业内部 **IAM（身份与访问管理）+ 工单** 统一平台：

- **IAM 内核（Phase 1，已完成）**：认证（双 Token / RT 轮换）、Casbin RBAC + 资源级鉴权（ResourceRegistry）、`ltree` 组织树（含虚拟组 / HR 同步）、操作审计（脱敏 + action 注册）、统一响应信封、软删除。
- **工单（Phase 2，进行中）**：工单 CRUD + 状态机 + 基于 scope 的权限；模板预填、关联鉴权已纳入 2a。
- **扩展能力（Phase 3，暂缓，设计就绪）**：SLA 计时/违约、通知、多级审批流、自动分派、报表、生产加固（可观测/可运维/安全）。

目标用户：企业内部员工（提单/处理）、IT/运维（受理/分派）、HR（组织/权限协同）、管理员（配置）。

## 2. MVP 边界铁律（裁决微观决策的依据）

**Phase 2a = 最小可交付的工单闭环**：能创建、查看、编辑、关闭一张工单，且权限正确。判定一条能力是否属于 2a 的唯一标准：

> **凡依赖 2c Authorize、事件机制（Asynq / L1）、或审批流引擎的，一律 defer 到 Phase 3；纯 DB、无事件依赖的，可纳入 2a。**

应用示例（避免再次横跳）：
- ✅ **工单模板 / 工单关联** → 纯 DB、无事件依赖 → **属 2a**（迁移 000015 / 000016）。
- ❌ SLA 违约计算、站内/邮件通知、审批流、自动分派 → 依赖事件/审批引擎 → **属 Phase 3**。

## 4. 文档真相源与修改纪律（防"乱"的核心）

真相只有三层，细节文档必须与之自洽：

1. **roadmap.md** = 执行视图（什么阶段做什么、现状）。
2. **design-decisions.md** = 决策日志（为什么，带日期，旧决策保留不删）。
3. **代码 / migrations/** = 真实落地（磁盘 `migrations/` 现状至 000009；000010+ 为规划编号）。

修改纪律（任何范围/阶段调整都按此顺序，缺一不可）：
1. 在 `design-decisions.md` **追加**一条（日期 + 旧→新 + 理由），不删旧。
2. 同步 `roadmap.md`。
3. 级联到 `modules/*`、`phase3/*` 等细节文档。
4. **禁止只改一处**——这是此前文档互相打架的唯一根因。

## 5. 与"设计 spike"的边界
