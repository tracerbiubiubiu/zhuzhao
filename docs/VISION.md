# 产品定义与 MVP 边界（VISION）

> **本文档是范围判定的唯一锚点。** 任何"某能力放哪个阶段"的争论，先回看本文件再下结论；禁止凭直觉在细节文档里改阶段归属。
> 当前锁定状态：2026-08-26（工单模板/关联归属 2a，见 §3）。

## 1. zhuzhao 是什么

企业内部 **IAM（身份与访问管理）+ 工单** 统一平台：

- **IAM 内核（Phase 1，已完成）**：认证（双 Token / RT 轮换）、Casbin 路由级 RBAC、`ltree` 实体组织树、操作审计（脱敏 + action 注册）、统一响应信封、软删除。
- **工单（Phase 2，进行中）**：工单 CRUD + 状态机 + 基于 scope 的资源级权限（ResourceRegistry 已随 2a 落地）；模板预填、关联鉴权已纳入 2a；虚拟组（2b-org）与 HR 目录同步（2b-ext，延后）随组织增强交付。
- **扩展能力（Phase 3，暂缓，设计就绪）**：SLA 计时/违约、通知、多级审批流、自动分派、报表、生产加固（可观测/可运维/安全）。

目标用户：企业内部员工（提单/处理）、IT/运维（受理/分派）、HR（组织/权限协同）、管理员（配置）。

> **⚠ 边界外已登记场景（2026-09-01，未立项，触发条件驱动）——外部供应商协作**：实际业务中内部员工与外部供应商协同，需求两档：① 供应商**提交并查看自己的工单**（requester 模式）——现状已可凑合（local 账号 + L1 建单权限 + 属主豁免可见性）；② **内部工单选择性共享给供应商**（组级整体共享现状可凑合：专属虚拟组 + `expires_at` 临时成员 + ticket_scope=group；**工单级「给这张不给那张」现状不满足**——可见性纯由组织成员关系推导，无工单级参与者/共享机制）。配套缺口：users 无外部账号类型（source 仅 hr/local，供应商与员工同构、可被 org_roles/继承 BFS 误赋全局角色）、组织树无供应商形态（org_type 1–4 全内部语义）。候选演进：外部账号类型 + 供应商组织形态（隔离于 HR 同步域）+ 组级 shared 可见性（业界主流：Zendesk shared organization / JSM customer portal）→ 工单级共享列远期；人员变动策略（合作结束 = expires_at 到期 + 禁用，名下工单随离职处置策略一并拍板，见 hr-directory-sync.md §3.2 待设计）。**触发条件 = 真实供应商接入诉求；启动时先改本文档立项，再级联设计。**

> **⚠ 边界外已登记场景（2026-09-01，未立项，触发条件驱动）——工单类型级创建授权**：现状 L1 `ticket:create` 为布尔开关，创建时传任意 `type_code` 仅校验存在 + is_active（ticket/service.go:97-101），**无「谁能创建哪些类型」控制**；读侧类型维度亦无可见性过滤（模板 org_path 仅预填辅助、不构成授权）。业界两派：类型自带授权（ServiceNow user criteria 派）vs 分组域圈类型（Jira 项目派）。候选演进（最小实现，ServiceNow 派）：`ticket_types` 加授权约束列（如 `create_roles`/`visible_org_paths`，空=全员可用保持兼容）+ Create 校验 + 类型列表按身份过滤；分组域派（服务目录/项目概念）对当前体量偏重不推荐。**触发条件 = 出现按角色/人群限定可提工单类型的真实诉求。**

## 2. MVP 边界铁律（裁决微观决策的依据）

**Phase 2a = 最小可交付的工单闭环**：能创建、查看、编辑、关闭一张工单，且权限正确。判定一条能力是否属于 2a 的唯一标准：

> **凡依赖 2c Authorize、事件机制（Asynq / L1）、或审批流引擎的，一律 defer 到 Phase 3；纯 DB、无事件依赖的，可纳入 2a。**

应用示例（避免再次横跳）：
- ✅ **工单模板 / 工单关联** → 纯 DB、无事件依赖 → **属 2a**（迁移 000015 / 000016）。
- ❌ SLA 违约计算、站内/邮件通知、审批流、自动分派 → 依赖事件/审批引擎 → **属 Phase 3**。

## 4. 文档真相源与修改纪律（防"乱"的核心）

真相只有三层，细节文档必须与之自洽：

1. **roadmap.md** = 执行视图（什么阶段做什么、现状）。
2. **design-decisions.md** = 决策日志（为什么，带日期，旧决策保留不删）。
3. **代码 / migrations/** = 真实落地（现状以磁盘 `migrations/` 为准；截至 2a 收口已落地 000010 / 000015 / 000016，后续编号见 phase2/README §2.4 预分配表）。

修改纪律（任何范围/阶段调整都按此顺序，缺一不可）：
1. 在 `design-decisions.md` **追加**一条（日期 + 旧→新 + 理由），不删旧。
2. 同步 `roadmap.md`。
3. 级联到 `modules/*`、`phase3/*` 等细节文档。
4. **禁止只改一处**——这是此前文档互相打架的唯一根因。

## 5. 与"设计 spike"的边界

`phase3/*` 文档是**设计就绪稿，非交付承诺**：细节详尽但暂不排期。它们用于 Phase 3 启动时取用，不应反过来绑架 Phase 2 节奏，也不应在 Phase 2 进行期间频繁改写阶段归属。
