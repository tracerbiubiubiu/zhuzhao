## 1. 现有底座怎样继续使用

Phase1–4已交IAM、资源级工单、通用服务和UI基础；Phase5已验收整合main。核心仍在一个 Go 应用里，任务服务（Taskrunner）和动态清单（ActiveList）独立运行，utils 提供共用代码。表单、工单状态机、动作、任务、通知、存储和情报代理都沿用现有模块，按各自接口逐步改进。

风险模块的五组能力（R1–R5）、AI/MCP、给工单保存固定版规则和新的扩展宿主仍待实施。现有的 `HookRegistry` 只在当前进程把事件传给处理函数。需要在重启后继续的投递，还得另存待办记录。准确main基线/运行证据见[审查报告](review/reports/pre-phase6-replanning-2026-11-11.md)与[后续验证](review/reports/pre-phase6-requirements-audit-2026-11-11.md#6-固定候选的完整运行验证回填)。合main不等于生产发布。

## 2. 新Phase6：把现有底座变成可信业务闭环

**完整纳管的条件与估算（2026-11-12 对照）**：[现行合同](design/uaa-governance-integration.md)要求认证及受管权限治理，E01-UAA-C在P6.0交公共来源/编码/撤权规则，P在P6.1归属公共端口及mock，R具备供给可准备并在公司UAA纳管企业模式首次正式激活前通过；当前首版本地正式优先，完整 P/R 在核心稳定后按公司要求或所有者另行批准启动，不因Phase归属强制提前，也不以其它provider代验。本轮已补估C2–3、P25–39、R13–22工程日，当前完整有限基线与资源场景见[注册表](planning/uaa-implementation-estimate.json)和更新排期；外部等待及既有非UAA范围资格条件另列。业务路线延续、mock保留；本次不是UAA已接通。

**按启用形态分别验收。** 本地核心稳定后，后续研发优先仅 SSO，以适用的本地会话与授权成果为基础，先做合成登录验收，再按公司和所有者批准范围联调试点。仅 SSO 工日待净估。 [四项分工与验收](planning/uaa-sso-local-authorization-plan.md)

独立模式保留原有账号/角色/菜单授权和权限管理，不等待公司UAA、私有adapter或R。C仅冻结公共规则与合成候选矩阵；真实映射及批准R前核验。P合同/mock准备可并行，完整投影/撤权出口验收须C04和X02-F实际共享能力通过（含其D06/X01-C依赖）；最小双模式前端与安装/切换/受控退出runbook随P/R交付，不等U06全站视觉。P负责用例，G03接CI，G04负责质量口径，新增接线/质量净量已在P计一次，原包预算不被本轮重新分类。

任何实际生产首发都须满足[按模式发布证据门](planning/planning-backlog.md#按运行模式检查的发布证据门)：复用G05/E09适用通用硬项，若早于P7只前移这些硬项，不机械等全P7/I03；公司纳管企业模式额外要求R。R通过不等于生产就绪，独立模式先发布也不取消项目内企业接入待办。

[阶段入口](phase6/README.md)。按四个实施波次和一个扩展波次交付：

- **P6.0**：独立worktree/环境、统一PR/组合CI、公式/文件/完成与发生次正确性、普通用户安全首页、受支持工具链/Node/镜像。冻结模型调用和X01扩展最小合同；不先堆功能。
- **P6.1**：授权/事务、发布定义/实例快照、转换采集、字段和HR mock；R01最小持久意图先于不可丢消费者。X01交私有扩展稳定接缝/同步身份，X02交connector参考；PG/Redis升级按副本/恢复验。
- **P6.2 风险登记和整改**。先用模拟来源发现风险，录入台账，把通知发给有权查看的人，再定级、审批接受或派单整改。例如同一个漏洞影响同一责任人名下的两台资产，可以共用一张工单，整改结果逐台复测。责任人不同或漏洞不同则分单。自然语言查询（A01）也须按当前用户权限返回结果。随后再扩充来源和自动动作。
- **P6.3**：现有全站体验/批量标签/筛选、配置晋级、通知和任务结果、受限自动路由；A02每次精确确认建单；X03交设备目录/状态/人工登录入口。异构设备不假设SSO，不造CMDB/NMS/PAM。
- **P6.E**：本地流程指标/每日快照和SOC事件协作；E10已计调查/触发核验在P6.1出口完成，获选的实际导入/合并在P6.E另估交付。高级设计器、完整迁移器、通用审批和报表不共同阻塞风险核心，保留项分别有后续窗口。

## 3. 新Phase7：能运行、能集成、能持续管控

[阶段入口](phase7/README.md)。保留原P7的接入/能力/身份/调度/观测业务价值，将MCP与自然语言放在同一能力底座上。

先列出可调用的功能和版本，允许有权限的人导出 OpenAPI 或 Schema，并提供身份、授权、撤销和凭据引用（`secretRef`）管理（I01/I02）。工作人员可用表单发起一次获准动作，从工单调用并查结果与历史（U08）。这些功能可独立使用。A03 增加 MCP 接口，A04 再增加自然语言入口。

接着交故障恢复控制台、指标、告警和请求追踪（I03），以及一次性或延迟任务与维护任务、Taskrunner 任务的只读总览（I05）。业务任务统一由 Taskrunner 调度。A04 可预览并确认周期任务或单次任务；实际执行前再查持续授权是否有效。

I04/E01按provider交两类代表源纵切和真实接入子包；D17保留可信告警的本地新建/关联/通知/维护窗，不做专业检测关联。D18在确需迁版时提供删状态map/dry-run/分批CLI。R06/R07及G05/G07持续承接AL、utils、制品/恢复和升级。先一条完整旅程，再增加源/动作/表单；未知供应方不阻塞无关mock/合同。

## 4. 新Phase8：扩专业执行、报告与领域智能体

[阶段入口](phase8/README.md)。原自动化功能继续承接，不被AI入口取代：

R03先一条管理员发布/审批/固定版本/预构建→受权运行→结果/工件/历史旅程；优先已有SOAR/runner承载上传/隔离。R04先双向调用一个Action与一个专业workflow，再逐项扩充；本地不默认再造脚本中心、凭据库或模板市场。

A05–A07以同一目录/权限/结果为基础，按实际场景选择企业Agent接入或平台领域Agent。领域Agent先依所选模型/工具和当前权限；只有选择知识检索时才消费知识ACL/引用，不要求先接外部Agent或所有知识供给。配置/skill不授执行权，步数/时间/费用/工具允许集与恢复证据可查；模型部署/训练不在范围。

E04先固定周/月报、受权运营查询、Word/PDF、定时/终态触发和分发回执，已有报告API优先，缺口用有限模板；后扩订阅/有明确受众的视图。E06先外部通报→内部处置→回复稿/回执，IOC/ATT&CK/分类取专业结论；演练/通告先薄协作。E03只交选定的轻审批/日历/会话场景，再按使用反馈扩，先不造通用引擎。

## 5. 新Phase9：免搬运、有人接管、可恢复和可举证

[阶段入口](phase9/README.md)。R02用一条告警→风险→工单→任务→结论回源链证明持久协同；动作、脚本、批准、等待、条件、并行汇合的效果可由成熟SOAR/工作流提供，本地保必要业务状态/责任/run引用。先有限链与简单汇合，复杂图按证据再扩。

值班协作（R05）要能查夜间的主要和备用负责人、谁确认接管、超时通知谁，以及处置手册和证据。没有专用值班工具时，可先按时段维护责任表。合并通知时，紧急变化仍须发出；本地处置完成和向上游回传失败分别显示。首版就通过 R01 保存必须可靠执行的后续动作，进程中断后仍能查询和继续处理。

E08推荐改的是默认自研DAG、全量迁回并退役SOAR的旧技术路线，不自动删业务协同/模板复用效果；P7比较，P9开工基于代表链选择。E07依据独立发布/容量/故障隔离决定拆服务，长期模块化单体与SOAR共存都是有效形态。

## 6. P10及更远：保留候选，按真实价值扩展

工单保留/跨设备草稿/Office/外部协作等在E05明确窗口评审，优先现有下载/本地草稿/企业身份和专业预览；保留的增量有子窗口/估算，未采纳项有理由和替代。原阶段编号不强制保留原实现方式，不能将条件提案无期限挂着或全部一次立项。

后续围绕真实闭环数据、私有扩展升级反馈、能力复用和Agent评测继续演进。AI已从P6.2开始，不等到旧Phase11；不预定通用市场、多租户SaaS、K8s/Kafka或全面微服务。不为远期名词创建空仓/空模块。
