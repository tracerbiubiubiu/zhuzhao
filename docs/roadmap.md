# 全项目路线图：承接、扩充与渐进演进

日期：2026-11-11。以现有五仓和原Phase6–9/更远规划为输入，重新组织整个后续路线；Phase6只是近期一段。尽可能承接已有业务价值，纠正不适合当前规模的设计，融合AI、内网扩展、设备与工程治理。下面是可审方案，功能尚未实施，原工作日/日历不作为当前承诺。

主线为**数据聚合与安全全生命周期管控**。专业发现/研判/执行取已有SOC、CMDB、TI、SOAR等供给；平台负责受权入口、责任、流程、结果与证据。模型只调已有API，内网仅内部服务；mock长期保留。既可接企业Agent，也可围绕本平台特有业务运行有限领域Agent。

[唯一总账](review/planning-backlog.md)维护71包、510来源、依赖与粗估；[能力连续性](review/roadmap-capability-continuity.md)逐条追溯原规划，[渐进方案](design/project-evolution-strategy.md)说明最薄首期/增强条件，[控制台](review/11-project-control.md)说明当前实现。不得以调查完成代替保留功能交付，也不把所有旧提案变成必须自建。

## 1. 现有底座怎样继续使用

Phase1–4已交IAM、资源级工单、通用服务和UI基础；Phase5已验收整合main。主仓为模块化单体，TR/AL是独立薄服务，utils是公共库。表单、FSM、动作、任务、通知、存储和情报代理继续作为底座，按模块接口逐步改进，先不全量拆服务/重写。

当前风险R1–R5、AI/MCP、不可变定义和新扩展宿主等仍为待实施。现有HookRegistry是进程内派发，不能以已有Hook冒称持久投递。准确main基线/运行证据见[审查报告](review/reports/pre-phase6-replanning-2026-11-11.md)与[后续验证](review/reports/pre-phase6-requirements-audit-2026-11-11.md#6-固定候选的完整运行验证回填)。合main不等于生产发布。

## 2. 新Phase6：把现有底座变成可信业务闭环

[阶段入口](phase6/README.md)。按四个实施波次和一个扩展波次交付：

- **P6.0**：独立worktree/环境、统一PR/组合CI、公式/文件/完成与发生次正确性、普通用户安全首页、受支持工具链/Node/镜像。冻结模型调用和X01扩展最小合同；不先堆功能。
- **P6.1**：授权/事务、发布定义/实例快照、转换采集、字段和HR mock；R01最小持久意图先于不可丢消费者。X01交私有扩展稳定接缝/同步身份，X02交connector参考；PG/Redis升级按副本/恢复验。
- **P6.2**：mock发现→风险台账→受权通知→评估/接受→N:1整改/复测；A01开始受权自然语言查询。先可解释的业务链，再扩源和智能化副作用。
- **P6.3**：现有全站体验/批量标签/筛选、配置晋级、通知和任务结果、受限自动路由；A02每次精确确认建单；X03交设备目录/状态/人工登录入口。异构设备不假设SSO，不造CMDB/NMS/PAM。
- **P6.E**：本地流程指标/每日快照和SOC事件协作；E10按明确样本处理导入/合并。高级设计器、完整迁移器、通用审批和报表不共同阻塞风险核心，保留项分别有后续窗口。

## 3. 新Phase7：能运行、能集成、能持续管控

[阶段入口](phase7/README.md)。保留原P7的接入/能力/身份/调度/观测业务价值，将MCP与自然语言放在同一能力底座上。

第一小步是I01/I02的版本目录、受权OpenAPI/Schema导出、主体/授权/撤销与secretRef管理，U08让普通同事用表单一次运行获准Action，查结果/历史并从工单调用。它不依赖AI；A03提供MCP，A04再增加自然语言入口。

接着I03交完整恢复控制台、指标/告警/trace，I05交一次性/延迟和维护/TR统一只读总览。TR保持业务调度唯一主，AI不成为第二调度器。A04通过同一preview/confirm安排周期或单次任务，执行复验持续grant。

I04/E01按provider交两类代表源纵切和真实接入子包；D17保留可信告警的本地新建/关联/通知/维护窗，不做专业检测关联。D18在确需迁版时提供删状态map/dry-run/分批CLI。R06/R07及G05/G07持续承接AL、utils、制品/恢复和升级。先一条完整旅程，再增加源/动作/表单；未知供应方不阻塞无关mock/合同。

## 4. 新Phase8：扩专业执行、报告与领域智能体

[阶段入口](phase8/README.md)。原自动化功能继续承接，不被AI入口取代：

R03先一条管理员发布/审批/固定版本/预构建→受权运行→结果/工件/历史旅程；优先已有SOAR/runner承载上传/隔离。R04先双向调用一个Action与一个专业workflow，再逐项扩充；本地不默认再造脚本中心、凭据库或模板市场。

A05–A07以同一目录/权限/结果为基础，先接企业Agent与已有知识ACL/引用，再在平台特有场景运行有界领域Agent。配置/skill不授执行权，步数/时间/费用/工具允许集与恢复证据可查；模型部署/训练不在范围。

E04先固定周/月报、受权运营查询、Word/PDF、定时/终态触发和分发回执，已有报告API优先，缺口用有限模板；后扩订阅/有明确受众的视图。E06先外部通报→内部处置→回复稿/回执，IOC/ATT&CK/分类取专业结论；演练/通告先薄协作。E03只交选定的轻审批/日历/会话场景，再按使用反馈扩，先不造通用引擎。

## 5. 新Phase9：免搬运、有人接管、可恢复和可举证

[阶段入口](phase9/README.md)。R02用一条告警→风险→工单→任务→结论回源链证明持久协同；动作、脚本、批准、等待、条件、并行汇合的效果可由成熟SOAR/工作流提供，本地保必要业务状态/责任/run引用。先有限链与简单汇合，复杂图按证据再扩。

R05保夜间有效主备、接管回执/超时升级、手册和证据引用；无专用值班系统时可用最薄时段责任表。通知聚合不吞紧急变化，回传失败与本地完成分开。R01的不可丢意图已经前置，不能为等P9容忍早期丢业务。

E08推荐改的是默认自研DAG、全量迁回并退役SOAR的旧技术路线，不自动删业务协同/模板复用效果；P7比较，P9开工基于代表链选择。E07依据独立发布/容量/故障隔离决定拆服务，长期模块化单体与SOAR共存都是有效形态。

## 6. P10及更远：保留候选，按真实价值扩展

工单保留/跨设备草稿/Office/外部协作等在E05明确窗口评审，优先现有下载/本地草稿/企业身份和专业预览；保留的增量有子窗口/估算，未采纳项有理由和替代。原阶段编号不强制保留原实现方式，不能将条件提案无期限挂着或全部一次立项。

后续围绕真实闭环数据、私有扩展升级反馈、能力复用和Agent评测继续演进。AI已从P6.2开始，不等到旧Phase11；不预定通用市场、多租户SaaS、K8s/Kafka或全面微服务。不为远期名词创建空仓/空模块。

## 7. 排期与调整规则

T0/投入未定，当前为带依赖/归属/粗估/出口的波次排期，不能将工作日上限相加承诺上线。各包明确最薄首期、真实待验及增强条件；后期包的准确DTO/Schema在开工前冻结，不要求今天设计所有未来细节。
