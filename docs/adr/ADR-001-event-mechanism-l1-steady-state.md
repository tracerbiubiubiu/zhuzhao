# ADR-001: 工单事件机制采用 L1（ticket_events 轮询）作为事件源长期稳态，Asynq 仅作异步任务执行器不替代事件源

## 日期
2026-08-25

## 状态
已采纳

## 背景
讨论工单业务能力的事件驱动机制时，提出疑问：当前 L1（`ticket_events` 表持久化 + 轮询单消费者）是否最优？是否应引入 Kafka（高吞吐事件流）或 Asynq（Redis 队列）？
当时项目状态：单体优先、Phase 3 整体暂缓（微服务拆分无需求），共享单 PG 集群 + Redis（辅助角色）。

## 决策
- **工单事件机制采用 L1（`ticket_events` 轮询 + 分布式锁单消费者）作为长期稳态机制**，不是临时过渡。L1 负责"事件事实源（持久化 + 可重放）"。
- **当前不引入 Kafka**；**不将 Asynq 用作事件总线**（事件源职责仍归 L1，不复用 Redis 承担持久化）。
- **但引入 Asynq 作为"异步任务执行器"**（见 ADR-002）：覆盖"审批通过自动触发某个事件"的耗时动作执行，以及"预置定时任务"的周期触发。L1 与 Asynq 职责互补，不冲突。
- 实现期不得因"以为 L1 是过渡"而偷工减料：`processed` 标记、分布式锁防重、双重职责（audit/signal）分离均按产线级实现。
- Kafka 仅在**真实微服务拆分（多服务事件流）**时才评估。

## 理由
- 单体单 PG 阶段，L1 复用现有 PG，零新增组件，事务内写入崩溃不丢，秒级轮询对工单通知/SLA 足够。
- Kafka 价值在"多服务解耦 + 高吞吐"，当前微服务推迟，引入纯增运维负担，属过度设计。
- Asynq **不作为事件总线**：事件源职责仍归 L1（`ticket_events` 持久化 + 可重放），不把 Redis 升为事件关键路径、不需为事件持久化加 Redis 高可用。
- Asynq **作为异步任务执行器**有价值且时机已到（见 ADR-002）：审批通过要触发的"数据同步/外部事件"是耗时动作，预置任务需要周期触发——这两类本质是"执行异步任务"，正是 Asynq 主场，Redis 已存在（辅助角色）可直接复用，不新增基础设施。
- 演进路径清晰：L1（事件源，现在，长期稳态）→ Asynq（异步任务执行器，现在，覆盖场景A触发 + 场景B定时）→ L2 Outbox+Asynq worker（按需，解多消费者瓶颈）→ Kafka（仅拆微服务时）。

## 后果
- 正面：事件源与任务执行职责分离、各司其职；零新增基础设施（复用现有 Redis）；Asynq 自带重试/定时，省去自写定时器与重试逻辑。
- 负面/风险：Redis 作为任务执行器后端，需保证 Redis 可用（当前已是辅助组件，影响面可控，任务失败可重试不丢事实）；L1 事件 → Asynq 入队需保证消费者在事务提交后再 Enqueue，避免"事件未落库就触发任务"。
- 后续跟进：若未来出现多消费者/异步邮件需求，启动 L2（Asynq + Outbox）；若拆微服务，评估 Kafka。
