# ADR-005：统一能力接缝与AL源变更事实责任

日期：2026-11-13。状态：**新增需求驱动的设计候选，未实施**；本页记录这一阶段的设计，具体数据结构（schema）、迁移、容量与新增工作量仍需在对应设计审查中确定。细节以[能力调用合同](../design/capability-invocation-contract.md)为准，分期见[增量范围册](../planning/capability-interconnect-supplement.json)。本文 AL 指 activelist，TR 指 taskrunner。

## 背景

所有者要求核心和插件的产品能力均可经授权对外调用，并有内部共用的调用通道；需要支持工单接收任务结果、定时任务更新 AL，以及 AL 变化触发任务。现有 I01/X01、C03/R01/D12 是对应计划中的工作项编号，可以承接大部分方向；仅有编译期动作表、失败后不保证补投的进程内 Hook，或网页操作后的事件补发，还不能证明所有写入口的数据变化都已接通。

ADR-003历史收敛要求AL不感知事件、由主仓调用成功后发布。这能描述主仓某次业务操作，不能证明AL直接API、定时写、导入等全部数据变化被捕获。新增需求改变了该覆盖前提，需要限域修订。

## 设计方向

1. 共用的能力描述和调用合同覆盖核心、插件及只做适配的连接器；本地仍通过领域接口（Port）调用，跨服务使用 HTTP，长任务采用可靠的异步执行。现有 API 保留，不强制所有调用经过 HTTP 或同一个远程调用（RPC）入口。
2. 静态能力用`capability_id + contract_version`；OpenAPI `operationId`只是接口定义别名；动态`operation_id`保留效果幂等语义。旧wire/action_id先做映射，不能改名造成重复副作用。
3. AL 只在数据写事务内生成最小变更凭证/事务发件箱（outbox），或提供可证明完整的变化记录流（feed）。主仓管理订阅、权限、因果预算（约束任务相互触发后继续产生的工作，具体规则见能力调用合同）、路由与任务；TR 负责已批准的业务调度。AL不依赖TR、不复制IAM、不构造第二业务事件总线。
4. 区分命令、事实、结果回执（receipt）和通知；统一公共元数据以及什么条件算完成，不合并各领域的状态机。MCP 适配也使用已选定的同一能力和授权路径。

## 保留与覆盖的边界

保留ADR-003的独立服务、独立PG数据库、统一网关、服务签名和薄动态数据平台定位。覆盖“只在调用方成功后发事件足以捕获全部AL变化”的旧保证；不恢复Change Stream平台、字段历史库、独立权限产品或通用编排引擎。

源事实写入是AL自身事务的责任，不是让主仓连接AL库；跨库仍不声称一笔事务。旧代码没有该能力，当前接口、表和部署不因本ADR自动变化。

## 代价与验证门

AL 源变更事实、经授权的任务适配器（adapter）、订阅和共用准入检查会增加工程量，不默认包含在原 I01/R06 中。先核对写入口覆盖、批量操作的记录粒度、幂等与完整性、重放、回调认证，以及限制任务反复触发自身的预算，再重新估算和安排进度。

Phase 6.0/6.1 先确定合同和最小调用入口，Phase 6.3 先实现工单任务结果，Phase 7 交付 AL 双向调用的代表场景，Phase 8/9 按实际需要扩展。D12 不能反过来依赖 I01 全部完成，以免形成循环依赖。没有实际变化、事件乱序或重复、任务写回 AL 后再次触发自身、队列已满和旧任务执行进程（worker）恢复，均需覆盖正常与异常处理的场景；未执行这些验证不得称互通已交付。

例如，定时任务直接调用 AL API 新增一条封禁 IP，即使没有经过主仓网页，也应由源变更凭证或完整变化记录流覆盖。该任务随后把处理结果写回 AL 时，还需按上述自触发预算判断是否允许再次触发任务；这只是候选设计要验证的场景，不表示当前已支持。
