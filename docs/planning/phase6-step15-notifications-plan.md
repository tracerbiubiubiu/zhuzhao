# Phase 6 第 15 项实施计划

基线为 Core 4aebdfea。以主排期第 15 项、联动详设 §6 与 §9、接线详设 §7–8 为准。使用合成账号、工单与 HTTP 提供方。真实渠道另行验收。

1. 复验现有待办、抄送、首次超时、模板、偏好和历史收件箱。沿已有入口验数据和用户可见结果，存在的产品能力直接验收。
2. 从整改提交复测的真实事务产生复核提醒。按当前具名风险责任人去重，记原票版本及原操作号。交叉验证回滚、同号重放、撤权及知会规则。沿用旧业务事件的兼容行为，避免同一复核事件两次生效。
3. 模拟 HTTP 使用固定签名路由和公开向量。逐收件人保存冻结载荷、同号幂等键、尝试和回执。数据库原子领取与版本更新，已受理、送达、明确拒收、结果未知各有结果。重启及丢响应按原 ID 查询，未知时暂停新发送。凭原提供方证据更新送达，迟到回执不回退。
4. 复用模板和偏好。接入零发送预览及按原记录读投递状态，给浏览器提供最小功能。主会话负责集成和项目控制台回填，分别复核源事务、传输、权限和真实故障。
5. 在独立运行栈跑现有首超时、浏览器与新切片，执行仓库普通档门禁，记录候选指纹、实测及后继范围。

独立用例重点为业务成功但通知事务写失败、用户不再有当前资格、相同标识命名空间隔离、回调迟到、提供方先保存效果而响应断开、模板预览零副作用。运行材料位于隔离本地工作区。

## 首条复核提醒的验收范围

- 待办查现有受派未结工单。普通抄送与工单事件沿站内收件箱验收。首次超时继续按原指派代际查一次性提醒。
- 整改进入待复核时，按这次提交中实际进入待确认的逐项结果选当前风险责任人。同票同次提交对同一收件人只入箱一条。有待复核原项并保有当前资格才显示该提醒并计入角标。原收件人保有原票与关联风险读取权时，复核结束后仍可按原 ID 查投递元数据。
- 新投递在提交时冻结模板与载荷。公共 mock 仅投影状态和合成标识，托管的模板仅接受 `ticket.status`。查询与异步回执须绑定原投递号、渠道版本和载荷摘要。提供方无查询时保留待核实结果。
- 复核提醒偏好控制外送，站内事项与已读状态独立。模拟外送由固定 profile 启用，默认关闭。历史 `message_log` 继续显示旧渠道发送记录。公司地址、字段映射、告警升级和新渠道进入获准的对应验收窗口。
- 普通档验收使用独占 Core/PG/Redis/RustFS。发布前复跑 UI 类型、单测、构建、浏览器与真实收件人场景。测试用例和原始运行记录随固定候选核对。 [开发门禁](../guides/development.md#4-交付前验证)
