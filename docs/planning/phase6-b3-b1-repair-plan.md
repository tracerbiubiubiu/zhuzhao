# Phase 6 第 11–14 项复验修复计划

> 范围为合成参考查询、工单任务和活动清单。基线为 Core a165d46f、UI 701a0b2d、Taskrunner f6414974、ActiveList 22556fea。候选在独立工作树验证，提交后交所有者审阅。

## 1. 原号对账

- 先加回归，覆盖 Taskrunner 重新计算归因后丢受理响应、同号错误动作或操作号，以及原清单更新结果未知。核心从签名客户端读取已保存的同一任务，并接受 Taskrunner 对本次实际签名 AK 计算的服务归因和既有归因。必须匹配任务号、动作、原操作号和一次性任务形态。业务执行仍核 Core 已保存意图和当前授权。
- 真正获得新受理并校验响应绑定后可记录派发受理。幂等、无效或丢失回应后由原任务详情核实。派发受理和业务成功使用各自回执。
- 清单更新已可能发出时，只按原操作查已保存的效果回执。查询 404、不可达或当前资格不足时保留待核实。随后查到合法回执再记录原结果。

## 2. 在途排空

- 增加独立排空模式，要求原连接与签名配置。停止新工单 B3 流转意图和新源入箱。重复投递已存且内容相同的源事实时回原 ACK，首次看到的事实留在 ActiveList 等待重试。
- 保留签名回执端点及 Core 周期对账。租约取得后重查已发送标记，未发送任务以无效果的暂停原因收束，已可能发送的写操作仅查原回执。排空期间不新投任务、不重入队、不发起清单写。
- 直接关闭若仍有待核实操作，启动应说明保留排空模式的前置条件。终态历史和原工单权限保留，存量普通任务入口继续可用。

## 3. 工单发布与参考查询

- 工单预检与发布使用同一静态动作合同。验证报告 profile、清单更新目标、版本及受控 patch，工单拒绝仅供订阅使用的读取动作。旧定义读取及成功原号重放按冻结事实，任务运行仍复核最新权限。
- 参考查询公开入口的 401 表示本地登录失效。服务间签名失败映射依赖不可用，现行授权拒绝与合同冲突有各自状态。已有准入确认的合同不符返回 409，缺少确认返回 503。

## 4. 复核与交付

- 三个独立工作树分工，主会话负责原号对账和集成；不同助手实现排空、发布与 B1，并交叉复核彼此的固定差异。每项先复现预期失败的普通回归，再验证修复通过。
- Core 从主线基线先跑 quality-plan 和 quality-check，再执行 lint、单测、集成、覆盖率、Swagger、迁移与四阶段验收。用独占 PostgreSQL、Redis、合成源和固定四组件复验原号、清单条件写、源事件以及浏览器。
- 特别验证实际签名但未授权代报操作者的 Taskrunner 组合、已发原回执在重启排空后恢复、首次源事件留在上游，以及 B1 服务身份失败时浏览器仍能查询本地会话。记录必须区分本轮实测和历史候选证据。
