# Phase 6 第 12–14 项实施与验收计划

> 范围为 B3 的三条合成业务链。起点为 Core `9d0019b7`、Taskrunner `30b839af`、ActiveList `d2fd4553` 和 UI `7da903fe`。详细合同与边界见[联动详设](../phase6/task-activelist-message-detail.md)和[跨仓执行合同](../design/cross-repo-execution-contract.md)。

## 分工与顺序

1. Taskrunner 复验现有 DB 先行、原号查询和执行栅栏。补固定动作的回执协议、同号输入检查及暂态处理。用相同任务号重投，验证 202、无凭证的 200 和标识不符的响应都无法结束任务。
2. Core 在一个已发布工单转换中保存原工单修订、定义哈希、动作参数、操作和派发意图。由 worker 提交固定任务号，回调持久记录证据摘要或失败原因。原工单按当前读权展示原运行结果。验证事务回滚、响应丢失、进程重启和晚到回贴。
3. ActiveList 和 Core 各实现一边有类型的更新与读取合同。首批只选合成复核记录的一组标量字段。一条工单动作可按明确授权更新指定记录，写前重验主体和范围。ActiveList 在同一事务核目标和版本，保存效果回执与变化事实。验证越权行、禁改字段、撤权和并发冲突。
4. ActiveList 直接获权写入也产生变化事实。独占推送通道与 Core 持久收件对接，规则按原事实生成稳定 ID 的只读任务。只读取同记录中的授权字段，区分事件版本与观察版本。验证重发、重启、撤权和查询无数据写入。
5. 网络接线、迁移、共享状态文件由主会话整合。各仓实现交给不同助手交叉复核。隔离运行实际四组件和依赖，固定候选版本，执行适用普通档门禁及逐项验收。第 11 项继续使用其独立分支和运行资源。

## 验收要点

- Core 只把有持久业务回执的任务列为成功，派发状态独立于最终业务效果。回贴绑定原工单及修订，迟到结果保留在原运行。
- ActiveList 原操作成功后可按当前资格读回同一回执，重复更新不增加修订。没有明确权限的调用无法经旧网关或旧读取面访问监控类型。
- 直接改清单可在没有工单的情况下触发实际 Taskrunner 任务。重复事实保留同一收件和任务号。清单记录在查询执行前后的文档版本一致。
- 使用合成授权、记录和网络错误。真实无人值守授权沿所有者议程第 Q09 项审批。
- 启用 B3 时，Core 在启动期拒绝覆盖清单收件或任务回执路由的网关前缀，检查包括匹配保留路径的命名参数。Taskrunner 出站需要签名密钥。B1 与 B3 同时启用时，参考应用来回两个方向的 AK 和实际密钥均须与清单收件、清单执行及 Taskrunner 双向通道分离。凭据检查使用 Taskrunner 实际签名的 AK，沿用省略时的默认值。


## 隔离专项记录

- 第 12 项由独立助手经实际 Core HTTP 发布并执行合成工单。Taskrunner 停机期间丢弃首次转换回复，工单推进到后续状态，再用原请求键读回原转换。Taskrunner 重启后，报告只回填原修订与定义。存量任务接口拒绝直接读取 B3 任务。另测了排队后停用操作者，以及授权人员用 Chromium 在原单读取、键盘刷新报告的路径。
- 第 13 项由主会话通过实际 Core、Taskrunner 和 ActiveList 执行。验证了两条同版本任务只有一条写入、越权行和字段导致事务回滚，以及排队后撤权无效果。ActiveList 自身的真实 PostgreSQL 专项另核对了原号重放、同值更新、原命令到期后的只读回执查询，以及注入回执写失败时文档与源事实一起回滚。
- 第 14 项由另一位助手在全新数据库复验。ActiveList 直接写入后，在 Core 落库并丢失 ACK，随后杀掉并重启进程。原事实只派生原任务，重复推送复用原收件凭据。三个源事实对应三个 Taskrunner 任务，两条成功观察和一条撤权阻止记录。没有关联工单及任何查询触发的清单写入。撤权后旧观察值也被拒绝读取。
- Core 另验了停用 B3 后的读取边界。原单仍能查看历史回执，旧任务接口继续拒绝直接读取。所有记录和授权均为隔离夹具。

Core 四阶段既有验收及 99 对迁移往返通过。候选全量门禁与远端合入分别记录。普通任务页和旧清单代理保留既有入口，当前监控类型及其任务由固定受控入口访问。本批选定一条固定订阅规则。订阅在线换版和真实无人值守授权沿详设各自的放行范围。

## 独立复核与接续验证

1. 对照四仓远端 main 冻结在途候选源码。现有候选运行中的门禁由原工作树保留，接续修复在 `codex/phase6-b3-verified` 四仓工作树中验证。
2. Core 复测排队期间的专属流转资格撤销，并验证工单进入后续节点后仍可关联原运行。ActiveList 复测越权与缺失行的相同响应，以及唯一键冲突时的权限边界。修补各自以合成测试的红绿结果为准。
3. 用同一候选四组件及专属 PostgreSQL、Redis 回放三条实际 HTTP 业务链。核对原任务、操作、收件、租约和存量入口的结果。按仓报告普通档门禁、首次失败和补跑，分别标注在途证据和本次验证。

本轮复核和运行证据见[固定候选验收](../review/reports/phase6-b3-steps12-14-validation-2026-11-26.md)。
