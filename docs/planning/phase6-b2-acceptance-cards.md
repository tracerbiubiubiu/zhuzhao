## 卡一 C05 停用已提交而 Redis 撤销未写成

管理员停用账号，PostgreSQL 已经保存，但 Redis 暂时写不进去，仍能读到停用前的登录状态。设计里把从数据库同步到 Redis 的这份状态称为“投影”。要验的是这种情况下旧登录能否被拒绝。使用实际停用 `POST /api/v1/users/status`、刷新 `POST /api/v1/auth/refresh`、文件代理 `GET /api/v1/files/*key`，另选同候选内可核当前权限的受保护读入口用于 Bearer/PAT。复核四种凭据的 HTTP 拒绝，以及重启和恢复后的原回执。[C05 合同与 SESSION 用例](../phase6/foundation-iam-module-detail.md#43-c05切换恢复与独立验收)

### 前置与有效性检查

- 使用独占的真实 PG、Redis 和应用实例，准备合成文件对象等测试数据，固定实际 API 与代理目标。用专属合成账号分别承担停用管理员、目标账号和同线路仍获权的控制账号。目标与控制账号的凭据在测试窗口内有效，角色和目标资源范围在用例期间固定。每次操作沿[开工计划的隔离装备](phase6-b2-kickoff-plan.md#3-隔离装备与验收交接)校验归属。
- 停用前目标旧 Bearer 和仅 cookie 的文件请求都应成功。PAT 用符合当前业务权限的受保护入口确认成功。预留有效 RT 槽给停用后的探针，刷新正向控制使用独立设备槽，避免预先消费试验 RT。候选上的凭据须在停用前由本候选按当前 schema 签发。基线红例用基线自己签发的有效凭据。
- 记录目标账号启用状态、候选当前会话代际（安全状态版本号）和 Redis 已确认同步到的代际（投影水位）、首次请求发出前已知的操作号 K、原有会话状态和资源读取摘要。确定服务端实际判定原因的观测点。全程只记录引用、状态与前后变化，凭据及文件内容使用合成测试数据并留在隔离环境。
- 仅阻断目标账号向 Redis 写入撤销状态，保留旧 Redis 值可读。记录故障注入实际命中，并读取核对。在同一服务和路由用仍获权的控制账号证实正常。逐凭据记录校验、实际进入当前账号判定及读取 PG 停用事实的请求关联证据。到期、签名或 schema 错误、资源无权、限流 429、整库不可用及通用 503 均使本轮撤权断言无效，另开对应变体。
- 实际执行前，逐项确定从哪里读取证据：实际存储、唯一键、受权查询入口、响应原因和 UI 提示。由仍获权的管理员用 K 查询原命令、目标、已提交事实、结果代际和 Redis 同步状态。独立读取核对唯一 `session_projection` 意图、目标、`expected_epoch`、`desired_active=false`、租约/fence（执行租约及防止过期执行者覆盖结果的标记）和完成状态。PG 回执证明本地提交，实际确认与 Redis 已确认代际共同证明同步恢复。[持久安全事实与回执](../phase6/foundation-iam-module-detail.md#42-c05的有限持久方案)

### 顺序、判据与证据

| 顺序与动作 | 判据 | 需要重新读取核对的证据 |
| --- | --- | --- |
| 1. 用首次请求前确定的 K 提交停用，持续阻断目标 Redis 撤销写入 | **账号已停用，Redis 同步待恢复。** 数据库在同一事务保存停用状态、新会话代号、操作 K 的回执和一条待同步记录。Redis 仍能读到旧的登录状态，Redis 确认的版本号落后于数据库。管理端须提示账号已停用，缓存清理待恢复。 | 从独立 PG 观察连接读已提交事实和前后变化。记录 K、意图身份、故障命中和旧 Redis 摘要。若丢失首次响应，通过同一个 K 受权查原结果。 |
| 2. 保持故障，尝试用旧 Bearer 读受保护资源，再走仅 cookie 的有效文件路径 | **终态拒绝。** 当前账号已停用。请求无受保护数据或文件内容输出。 | 真实 HTTP 响应、认证原因、目标业务数据的读取结果及同线路控制账号成功。分别验证 Bearer 与无 Authorization header 的 cookie 请求。 |

| 6. 当前获权者重新启用，待启用的新代就绪后新登录 | **通过新会话，旧 JWT 继续拒绝。** 新 AT、RT 与文件会话可在权限内使用。仍有效且未撤的 PAT 按当前账号和业务资格恢复，已撤或到期 PAT 继续拒绝。 | 新代、原停用及启用事件的读取核对，旧代 AT/RT/cookie 负例。独立核 PAT 的当前有效性和授权。 |

**恢复分支。** 数据库未提交时按原合同核安全写前后记录未变。提交结果未知时先查首次请求的 K，未确认期间留待核查。数据库读不可用、账号有效且无法证明 Redis 已同步当前代际，分别验依赖故障。已从数据库证实停用的账号走终态拒绝。Redis 整体不可信的恢复及轮换签名密钥留给 SESSION 专项。

**验收出口。** 已验收的隔离候选在故障窗口以实际账号状态拒绝四类旧凭据，并区分已提交待同步、响应丢失待核查和同步已完成。换候选复验时仍按顺序 1–6 逐项取证，记录首次失败和重跑。依赖故障与会话拒绝分别核对实际结果。 [联合验收记录](../review/reports/phase6-b2-stage3-acceptance-2026-11-22.md) · [C05 行为和目标合同](../phase6/foundation-iam-module-detail.md#41-c05现有wire与尚未持久化的部分)

## 卡二 B2 两条合成风险合在一张工单并逐项复测

**合成样例与角色。** 沿用开工计划的 R1/R2，在同一管理范围、目标组织和指定整改类型的 A 版流程规则下新建 T-201，A 版启用复核。两条风险由同一风险负责人 U 管理。M 有主锚批派资格，P 是合法办理人，U 有当前复测权。X 具有复测入口所需的粗粒度功能权限和目标读权，当前复测职责仅属 U。R1 为高、D 日 17:00 截止，R2 为中、D+1 日 17:00 截止。D 为固定 UTC 样例业务日。[风险代表场景](../phase6/risk-module-detail.md#14-漏洞整改代表场景)

**证据输入。** R1 提交逐项整改说明和可核的合成变更/复测引用，只用引用。R2 提交逐项整改说明与有效的合成附件引用。引用能定位稳定对象和版本，当前复测人可以按实际权限读取核对。附件另核归属和有效性。每次提交把引用绑定具体关联和当前版本，与对应业务变更同事务。复测按项记录依据、结果、复测人和时间，打回记录原因。初始提交和重提保留各自证据。

**复测设置与证据要求。** 本卡主路径启用复核。验证关闭复核的设计变体时，使用另一份已通过发布预检的合成定义，沿流程允许的完成动作检查逐项字段、措施、证据及当前资格。缺证据须拒绝。 [复核开关与逐项证据](../phase6/risk-module-detail.md#52-逐风险结论与review-gate)

| 业务已提交，站内投递暂失败或执行过程重启 | **业务已通过，通知待恢复。** 以同一投递键恢复并重验当前收件资格。用相同前置分别读取核对资格仍在时只入箱一次、已撤权时有尝试记录和指定抑止原因且零新增入箱。未执行或缺证据不能记为抑止通过。读取失败须明确可见，正常空列表状态单独验。 |

投递键按 `(source,source_event_id,rule_id,rule_version,recipient_user_id,channel,semantic_key)` 读取核对。同一源事件重试用原键，分别检查历史、投递和入箱的前后变化。实际执行前按候选登记开放及关闭的实际路由或动作，以及预期拒绝原因。[风险通知与去重合同](../phase6/risk-module-detail.md#6-d15通知与统一审计)

主流程用各角色分别查结果。拒绝时查原因和记录是否未变。恢复时沿用首次请求的操作号或投递键。“待复测”是正常的工单状态。
