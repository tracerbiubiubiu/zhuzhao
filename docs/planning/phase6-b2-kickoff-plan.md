### 三类工单的范围与定向验收

- **本轮试用：按指定整改类型新建工单。** 用 R1/R2 合成风险演示时，发布该类型的 A 版流程规则后，派单创建工单 T-201，将两项风险关联到 T-201。真实试用也只接收本轮按指定类型新建的工单，不将升级前存量工单纳入试用。
- **升级前已经存在的工单。** 在独立测试环境造一张模拟升级前创建、还在办理的同类型工单 T-100。只有能核实原来的流程规则，才把 T-100 关联到那个规则版本。处理途中中断可以继续，原编号、操作历史、有效引用、进入当前状态的时间和期限都保留。无法证明规则来源时，不能猜一个版本；找不到可用规则时，有权限的人仍可查看，在页面上看到不能办理的原因。只是部分历史来源不明时，标明未知，关单只看已生效的结果。还要检查其它类型、已结束或未选定的工单保持原样，以及旧客户端对配置的修改是否仍受校验。 [测试步骤](#53-旧票兼容单独核对)
- **新机制下的 A/B 工单：各用创建时关联的规则，权限每次按当前状态检查。** 在独立用例中还原同一组 R1/R2：A 版发布后创建 T-201，随后发布 B，T-201 仍按 A 办理；按 B 创建的 T-305 用 B。合成小例子可设 A 要填“修复方案”，B 另加必填“复测环境”：T-201 不因 B 发布而多出该必填项，T-305 缺它须拒绝；也可选其他可核的动作或必填字段差异。两版都检查操作者当前身份和权限，撤权后均须拒绝，不因保留 A 版规则而保留过去的权限。
- **入口与失败反例。** 主锚写、办理及复核分别验无权、失权、陈旧版本、关系交接和缺证据；隐藏对象同不存在一致。预览后变更依据或撤权，提交依原分类拒绝且无新业务事实。关单、普通转换、删票及后台入口经同一套风险复核检查，暂不支持的入口由服务端关闭。对同号重试、丢响应和重启查原回执，已完成项不重复。验非本人接受批准、待批准阻止票终态；验已接单、改派和撤权抑止旧待发送提醒。权限反例核票、字段、时间、关联、附件、业务历史和必要意图的前后变化，允许设计要求的拒绝留痕。
- **浏览器里要能办理什么。** 用实际代表角色从待办点进工单，刷新后还能回到原工单，两条风险共用一张工单时列表只显示一次。核逐项复测、只打回其中一项，以及失去权限后的页面提示。真实试用前，在 Q12 记录运行哪一版软件、参加人员、数据保留多久及怎么停用和回退，并提供 AUTH-01/02/07 在所用范围已通过、或相关服务端入口已经关闭的证据。关键提醒走真实渠道验证，或用业务已经批准并验证的备用办法。 [工单规则版本示例](../phase6/ticket-module-detail.md#33-发布迁版与配置晋级) · [真实试用条件](../phase6/first-usable-release-plan.md#41-b0预演与真实业务试用准入)

### 入口与现场导览：谁在哪里操作、看到什么

下面用上述 R1/R2 关联的 T-201 走读计划中的操作。界面和 API 的准确字段、授权、错误码由本批按合同确定。 [风险工作流](../phase6/risk-module-detail.md) · [工单办理](../phase6/ticket-module-detail.md)

1. **风险管理者核实两项风险，预览并派单。** 输入两个合成风险、定级依据和目标类型。预览应显示合成一张票、两条关联和适用期限。提交前若管理者失去派单权，或风险依据已经变化，服务端应拒绝且没有新票和新关联。提交前保留操作号，超时后按原号查结果。
2. **整改办理人接单并逐项提交证据。** 在同一张票上分别填写两项措施。一项可用已获准读取的证据引用，另一项用合成附件走上传、引用和读取核对。缺所需证据、附件失效或当前办理资格失效时，不能推进这项风险。
3. **当前风险负责人逐项复测。** 第一项通过，第二项写明理由打回。重新打开同一张票时，第一项已生效，第二项仍待整改，票继续在办。下一次只提交第二项。全部有效关联具备本流程认可的生效结论后，服务端才允许终结。关闭失败先查未完成项、复核职责及当前版次。 [两风险验收卡](phase6-b2-acceptance-cards.md#卡二-b2-两条合成风险共票并逐项复测)

**停用发生在业务提交前时**，C05 用 PostgreSQL 中的账号状态和会话代际（安全状态每次变更的版本号）拦住旧凭据，C04 在业务提交事务中核当前凭据及办理资格。以管理员停用办理人的账号为例，测试会让停用提交成功、向 Redis 同步撤销状态失败，同时保留 Redis 旧值可读；这份由数据库同步到 Redis 的会话状态称为“投影”。旧访问令牌、刷新令牌、文件会话和该停用账号的 PAT 都应在各自入口拒绝。管理员在首次请求发出前保留操作号 K，后文“原 K”均指这一次请求的同一个操作号。响应丢失后，仍有权限的管理员用 K 查停用是否提交及 Redis 同步是否待恢复。结果未知时保留待核查，禁止自动换号重做。恢复只重试数据库已保存的同一条同步任务（意图），确认 Redis 已完成撤销后才可另行启用。启用后旧访问令牌、旧刷新令牌和旧文件会话仍须拒绝，未撤销且未过期的 PAT 按当前权限判定。待启用的写入口逐个证明检查有效，缺证据的入口保持服务端关闭。 [停用故障验收卡](phase6-b2-acceptance-cards.md#卡一-c05-停用已提交而撤销投影失败)

B2 随业务交付所需的风险列表、详情、逐项复测，以及流程规则无法解析时的禁止写入提示，首页待复核按当前复测职责对同一张票去重。具名角色在浏览器上验证待办深链刷新、部分打回后重提、无权态与原结果查询。完整工单工作区和跨域扩展按后续分工交付。 [前端详设](../phase6/frontend-page-family-detail.md) · [当前模块入口](../modules/README.md#按业务场景串起当前实现)

## 2. C05 首批开工计划

**目标**为账号停用或密码安全写提交后，用数据库中的当前账号状态和会话代际判定旧凭据。安全状态、代际、可查回执和Redis 同步意图同事务，写入 Redis 失败后可恢复。PAT 沿独立生命周期核当前账号、令牌和业务资格。复用现行自助改密条件写及 F021 已确认的重复操作语义。[底座 C05 合同](../phase6/foundation-iam-module-detail.md#4-c05账号atrtpat-与停用恢复) · [F021 行为决定](owner-decision-agenda.md#本轮规划修订的独立确认)

### 按顺序交付的审阅单元

1. **先固化入口和故障红例。** 盘点 `internal/service/user_service.go` 的 `Create/UpdateStatus/Delete/ResetPassword`、`internal/service/auth_service.go` 的 `Login/Refresh/UpdatePassword`、`internal/middleware/jwt.go` 的 `JWT`、`internal/middleware/fileauth.go` 的 `FileAuth`、PAT repo 与 `internal/pkg/admincli/reset_password.go` 的 `ResetSuperadminPassword`。确定当前/目标响应、获权回执查询和 UI 结果矩阵。第一条红例在真实 PG/Redis 验停用写已提交、只让向 Redis 写撤销状态失败、会话读仍可见旧 Redis 值的分支；用仍合法的旁路账户证明探针并未被通用故障截断。
2. **交数据库安全事实和操作原子性。** 先给创建、存量初始化、停用/启用、删除、管理重置和自助改密写失败零提交及并发断言。实现成对扩列迁移、`session_epoch ≥ 1` 与 `0 ≤ session_projection_epoch ≤ session_epoch`、初始 `1/0`、可重入初始化及共用私有 operation/intent 存储，按仓内实际实现核可复用性。新迁移同步到 `internal/testutil/testdb_integration.go` 的集成装配。安全写在当前守卫和目标行锁内重验状态/hash/代际，并同事务写状态或口令、代际、回执和意图。应急 CLI 保留恢复能力，先明确受权目标及撤销确认后启用的安全顺序，另测 HTTP 重置保留停用。
3. **接通真实认证入口与 Redis 同步恢复。** Utils 用增量签发接口提供 `session_schema=db_epoch_v1` 和规范正整数字符串 `session_epoch`，维持旧消费者接口。主仓 JWT AT/RT 与文件 cookie 读当前 DB 安全快照，再核 Redis 同步结果及会话槽。校验登录不借用新代际，refresh 按原代际和设备隔离且一个赢家。同步在 DB 锁外执行，按代际只向前更新 Redis，按 DB 当前代际与 lease/fence 确认结果。失败只重投原意图，旧确认或清理不得覆盖新代。PAT 继续其独立分支，登录和启用均不能清除待恢复安全屏障。由 C04 再把具体凭据事实接入实际业务提交守卫。
4. **交付客户端、受控恢复和准确候选组合。** UI 接线核 `src/common/request/src/index.ts` 和 `src/store/modules/user.ts`，明确当前会话终态退出、可恢复故障、改密已提交以及结果待核查。保留单飞刷新，迟到结果按会话世代隔离。完成Redis 同步长期失败的告警和受权重投，验新旧 JWT 切换、可信单项恢复及不可信 Redis 恢复。业务代码、测试或迁移候选走普通档，局部审阅单元只作集成输入，须等适用的全量门禁和独立故障验收通过后才能宣布 C05 交付。

存量用户保留主体 ID、账号状态及业务归属。切换先扩展表结构，补齐并校验存量账号安全字段，再受控切换读写并要求重新登录。纯 Redis 旧代际不可作为可信迁移源；降版前须能拒绝旧会话，不能仅删安全列或按旧代继续接受。具体迁移编号、错误码和接口联动由实施方依基线确定。C05 沿用已有 **6–10 单席工程日候选**，按首批实耗校准；G04 和共用存储/验收按现有净估扣重。[底座切换与验收](../phase6/foundation-iam-module-detail.md#43-c05切换恢复与独立验收) · [运维恢复合同](../ops/runbook.md#62-c05会话投影长期失败的受控恢复设计候选未实现)

### 撤权故障回归

### 开发前要确定的接合条件

- **C05 红例的判据。** 当前 `JWT` 的 AT 分支依赖 Redis 会话状态，`FileAuth` 将 cookie 交给同一认证链。现有 `AuthService.Refresh` 和 PAT 查询已有账号状态检查。基线回归须区分各入口原行为，AT 与 cookie 是首条停用缺口的关键断言。候选负对照先签发当时代际和 schema 都合法的会话，再在固定时钟内提交停用；保持旧 Redis 可读，只让 Redis 同步写入失败。确认旧凭据在停用前确实可用，失败后分别核预期认证原因、DB 已停用及原回执/意图，并用另一合法账户验证下游路由仍可达。到期、旧 schema、限流、业务权限错误和 Redis 整体不可用分别测。
- **C05/S2/C04 的连接边界。** 当前迁移与运行路径尚无设计中的 `capability_operations`、`authorization_effect_intents`。先固定 S2 私有回执、操作唯一键、同一 DB 事务写入及当前获权查询，沿既定报价扣重。对 F021 的操作 K，选用首次提交前已知的稳定请求身份，确保首个响应丢失后仍能核查原操作，确定旧调用方的可查边界。复用已有 IAM 守卫与事务接线，C05 提供当前主体和凭据事实，C04 再接入业务写事务复验。固定“认证已通过→另一事务先提交改密或撤销 PAT→原请求再尝试提交”的用例，保持角色、工单和对象资格不变以单独验证凭据检查，再验合法业务先于撤权提交。F017 的本地强审计另随 `SetRoles/AssignMenus` 验，范围沿既定决定。
- **C05 客户端与应急恢复。** 实施方确定终态错误码和可信来源、普通依赖故障、已提交待恢复和结果未知，分别映射调用端。现有 UI 已有单飞刷新和会话世代控制；先复用对应路径，再设计受权回执查询、提交后停止复用旧会话和管理员操作他人时的反馈。CLI 保留容器授权的应急恢复入口，先确认原撤销效果再允许恢复启用，并定义没有可登录管理员时如何续原操作。提前登记旧调用契约、最小角色和实际操作回复。[C05 现有与目标边界](../phase6/foundation-iam-module-detail.md#41-c05现有wire与尚未持久化的部分)
- **D01/D03/D04/D02 与风险域与工单的连接。** 拟定所选类型的状态与动作、关系来源、字段/文件及允许使用的流程规则版本清单。对照 `iam_command.go` 的 `withHTTPCommand` 已先锁票行，`ticket_transition_snapshot.go` 的 `LockTransitionSnapshotTx` 在内层读取并锁配置。先梳理各入口真实锁顺序，再确定共同顺序和发布/办理双向提交用例。静态顺序差异需要反例验证。A/B 样本允许的状态转换或必需字段应有可观察差异，再撤当前权限核两版均拒绝。复核者兼手工 CC 时，交接只撤对应风险参与来源。风险域与工单的连接还需固定部分通过、关闭及删票时的有效关联、历史和通知行为，所选暂缓入口登记服务端关闭与可实测拒绝条件。
- **合成用例的规格。** 复用风险详设的 M（风险团队）、U（两项风险负责人）、P（办理人）、V（副锚读者）、H（无功能权限）、N（无对象范围），增加 S（合法继任负责人）。另用具有主锚审批资格的申请者测禁止自批，由另一位仍具资格的审批者测正例，避免无审批权本身就拒绝、掩盖自批检查。逐入口列主体、对象、动作、预期结果和持久记录的前后变化。升级前存量工单补规则关联的正例，以模拟迁移前保存的可信配置及合成工单为依据，缺来源/缺定义是独立负例。在隔离环境为同一类型实际发布 A、B，验证各票的定义引用、动作和必需字段，区分发布并发冲突、票改动冲突、已关闭状态和缺快照。用可控时钟复现接单、提醒和超期；真实浏览器须断言失败提示、重试及旧数据显示，避免 503 被空结果、零计数或静默成功掩盖。[合成角色与业务场景](../phase6/risk-module-detail.md#13-公共reference-v1两风险的完整纵切)
- **初始化和切换。** 为存量账号补上 `epoch=1/projection_epoch=0`，在保持既有入口的准备阶段核当前代际是否已有同步意图和Redis 同步完成情况。实际切入新 schema 前，先确认要启用的账户集合具备可恢复的 Redis 初始同步状态及切换/重登证据。独立验切换前后登录、刷新、旧代拒绝和晚到 worker。各审阅单元可分批集成，启用条件同时含安全写、回执/意图、认证判定和恢复。继续沿底座合同对无法证实 Redis 同步完成的当前代返回可恢复故障，并以原哈希比较替换刷新槽，保留较新合法会话。[底座有限持久方案](../phase6/foundation-iam-module-detail.md#42-c05的有限持久方案)
- **隔离预检和停止条件。** 任务 manifest 记录独占归属，组合验收另核制品与模板、迁移和依赖指纹。主仓的迁移往返连接成功只覆盖它自己的数据库检查，仍需以实际连线证明 API、PG、Redis、文件和 UI 指向同一候选。UI 基线的 `playwright.config.ts` 固定探测 4000 且允许复用已有服务器，须同时验证浏览器启动/代理目标和当前实例。任一连线或归属不符，先停止该轮。故障点要记录命中，正常对照不可被误伤。停止和清理只处理本次有归属证明的对象，核共享指纹；进程强杀后的残留先对账。[环境归属与验收纪律](../ops/runbook.md#71-验收连接与临时文件隔离2026-11-04)

## 5. 桌面联审与开工就绪

本轮按 C05、R1/R2 新建 T-201、升级前合成副本 T-100及 A/B 发布后工单依次推演。各步「通过」「拒绝」「待核查」「待恢复」均为以后在隔离环境实际执行的预期，当前只有设计判据和取证路径。证据须注明实际候选及所用合成账号、工单、文件等测试数据。拒绝须命中预期检查，核对前后记录确认相应业务数据未变，允许合同规定的拒绝留痕。缺证据、连到其他候选的服务或资源、正常对照不通或故障未命中时，该轮无效。

### 5.1 C05 撤权故障

先按 `user_service.go` 的 `UpdateStatus`、`jwt.go` 的 `JWT`、`fileauth.go` 的 `FileAuth` 与 `auth_service.go` 的 `Refresh` 核静态入口。基线停用后的 Redis 撤销由 `AfterIAMCommit` 执行，红例重点辨别 AT 和仅文件 cookie；RT 与 PAT 已有账号状态检查。候选须额外证明 PG 当前账号事实、回执和持久意图。四种凭据分别记录判定原因。基线和候选各用自身签发的合成凭据。[认证与恢复合同](../phase6/foundation-iam-module-detail.md#43-c05切换恢复与独立验收) · [C05 验收卡](phase6-b2-acceptance-cards.md#卡一-c05-停用已提交而撤销投影失败)

1. **前置通过。** 从实际候选签发可用凭据，独立记录账号启用、代际、Redis 已确认同步到的代际（投影水位）、请求关联引用及故障前资源读取结果。独立读取并核对预留 RT 槽存在、匹配停用前代际和设备、未过期且未消费，正常刷新用独立设备槽。同线路控制账号在故障前后均须成功，确认走到本轮要看的服务和校验路径。
2. **停用已提交，Redis 撤销待恢复。** 首次提交前已有操作号 K，后续核查和重试沿用该号。通过独立 PG 连接读取，须同时看到账号停用、新代际、K 对应的原回执和唯一同步意图，Redis 旧值仍可读，定向写故障有命中证据，Redis 已确认代际仍落后。客户端丢失响应且尚未读到提交证据时先按 K 受权核查，结果保持待核查。明确回滚则核账号、代际、成功回执与意图零变化。
3. **旧凭据终态拒绝。** 逐个读取核对实际响应、请求关联证据、预期账号判定原因及目标业务前后变化。AT 和仅 cookie 请求无受保护内容，RT 无新令牌或 cookie 且无槽替换，PAT 因账号停用拒绝且保留自身生命周期。到期、签名或 schema 无效、业务对象无权、限流或依赖故障须各自归因。账号活跃但无法证明 Redis 已同步当前代际，或 DB 无法确认时，另按依赖故障合同核可恢复结果与零受保护效果，PAT 沿自己的数据库分支。
4. **启用拒绝，重启后仍待恢复。** 故障保持期间，由仍获权管理员用不同操作号尝试启用。读取核对账号仍停用、无启用代际或成功回执。预先登记故障如何跨重启维持，重启后确认原同步意图仍待处理、Redis 已确认代际未变及目标重试再次命中。用 K 重交原停用请求只返回原操作结果，代际、成功回执和意图数量不增。启用所见状态和管理员可查的待恢复原因分别记录。
5. **原同步意图恢复通过。** 在同一可信 Redis 存储中解除故障，由获权者重试原同步意图。读取核对原目标代际、同一意图的确认和 Redis 已确认代际，核确认使用当前代际及有效租约/fence（本次执行的租约及防止过期执行者覆盖结果的标记）。原停用事实、代际推进次数和安全成功回执不变，旧凭据仍拒绝。查回执、重试同步、启用和 CLI 应急续办各核适用授权与目标范围。Redis 整体不可信归 SESSION 专项，单项恢复所得证据只覆盖本卡。
6. **恢复后启用通过。** 另行获准启用，等 Redis 确认已同步启用的新代际后再登录。对照启用回执、新旧代和实际读取结果，新 AT、RT、文件会话在权限内可用，旧 JWT 仍拒绝。仍有效且未撤的 PAT 按当前业务资格可用，到期或已撤 PAT 仍拒绝。

**结果与客户端映射。** 实施方查询首次请求的操作号 K，按完成、待恢复、尚不可判定三类结果，分别对照独立 PG 事实、认证原因、响应和 UI。另排首次响应丢失且暂查不到 K、明确回滚、已提交待恢复三轮。查不到 K 时维持待核查，明确回滚须有零提交证据，终态拒绝须有对应授权或凭据原因。B2 丢响应沿同一判别原则，使用业务自己的操作号。

### 5.2 B2 两条合成风险

按固定 UTC 时钟推演 §1 的 R1/R2：在指定整改类型的 A 版发布后新建 T-201。M 派单，P 办理，U 逐项复测。R1 仅用可核引用，R2 用合成附件。用仍具常规入口资格的对照主体分别验证缺证据、失权、版本冲突及复核门；给每个变体独立还原前置，避免前一次状态或修订号先挡请求。[两风险验收卡](phase6-b2-acceptance-cards.md#卡二-b2-两条合成风险共票并逐项复测) · [逐风险复核合同](../phase6/risk-module-detail.md#52-逐风险结论与review-gate)

2. **提醒与接单通过。** 按 09:05 分派、09:35 接单截止、09:36 应发一次、09:40 接单，分别读取核对分派、接单时钟、提醒状态和去重键。首响 40 分钟、分派到接单 35 分钟，业务截止保持独立。实际执行前查用到的应用时钟、数据库时间/时区、调度和逾期判定来源，按同一时间样本核提醒次数及时钟跳转前后的记录变化。时间来源无法对账的断言记未证。另验已接单、改派或撤权后的旧未发提醒被抑止。
3. **办理提交通过。** 读取核对 P 的方案及计划、票/风险/关联修订号、T-201 创建时关联的 A 版规则和两项各自的措施与证据。U 按实际对象权限可核引用，附件的对象归属、权限和业务绑定分别可查。此时只形成待复测事项，首页仅当前具名 U 计同票一次；17:01 仍显示逾期在办。缺单项证据或附件失效时从对应守卫拒绝，零相关字段、关联、状态及必要意图变化。
4. **部分复测通过，提前关票拒绝。** 独立读取核对 R1 生效结论、R2 打回理由和原证据，整票留在合法办理状态。逐个以合法动作和常规资格走普通关票、风险关闭及转换等实际开放入口，确认服务端复核门拒绝，R1 历史原样、R2 待办、整票零闭环意图；对首批关闭的入口核服务端禁用。X 有入口功能权和目标读权，使用当前版本及有效证据仍因缺复测职责被拒绝。预检后交接再提交另立一轮，以当前版本和有效凭据验证旧 U 已无复测职责，仍有合法 CC 时另查原可见性；继任者用同等业务前置做正对照。
5. **只重提 R2 后闭环通过。** R2 提新证据，经当前负责人复测通过后核两条有效关联都已有生效结论，票于 17:20 到终态。读取核对 R1 未重做、曾逾期可查、17:20 与建单相隔 8 小时 20 分，以及终态、历史和必要意图的提交证据。核通知失败记录可读取，浏览器准确显示当前角色所见结果。

**C05 到 C04 的提交边界。** 从首批实际开放且纳入 C04 的写入口中绑定一条业务样例。第一轮在初步认证通过后、业务提交前先完成凭据撤销，保持动作职责、对象及业务版本可用，核对事务内因当前凭据失效拒绝及业务数据前后无变化。第二轮让合法业务先提交，再完成撤权，分别查原业务回执和后续拒绝。按各凭据自己的失效合同选条件，密码变更与 PAT 自身撤销分开。与上面的复测职责交接用例分别归因。

**待核查与待恢复。** 首个响应丢失时，调用方按原操作号受权查询，先查明原回执，再读取核对票、关联及历史。通知故障变体先独立在 PG 证实业务回执和必要投递意图已提交，再查失败记录。后继投递失败按原投递键恢复，重验当前收件资格及消息条件。获权时只入箱一次，已入箱但确认丢失时读取核对原入箱记录，未发且已失权或条件失效则须有尝试记录、指定抑止原因和零新增入箱。重试或恢复后业务结论、历史及意图次数均不增。正常空列表状态和读取失败另各取一次证据。

### 5.3 升级前存量兼容与 A/B 发布分别核对

真实试用仍只接收本轮按指定整改类型新建的工单。本节沿用 R1/R2，分别还原独立的 T-100、T-201、T-305 合成用例：T-100 只验升级前存量兼容，T-201/T-305 验 D01 的“每张工单保留创建时的流程规则版本”。主动将工单改用另一版规则的迁版工作沿后续窗口。[存量工单与发布合同](../phase6/ticket-module-detail.md#33-发布迁版与配置晋级)

1. **有可信依据才补关联，中断后可按原批次继续。** 为 T-100 留存模拟迁移前保存的可信旧配置、映射依据、批准记录和工单原始摘要。核已选在办工单补上的定义引用/hash，确认原编号（ID）、历史、节点时间、当前期限和有效证据均保留，其他类型、未选工单、终态历史均无改动。若中断，读取核对已完成和未完成范围，按原范围继续，核无指向不存在定义的引用、无重复历史或后续动作。
2. **T-201 始终用 A，T-305 用 B，当前撤权后两版均拒绝。** 在同一指定整改类型下发布 A 后创建 T-201，再发布 B 并按 B 创建 T-305；沿 §1 的合成例，B 比 A 多要求“复测环境”，或选择另一处可实际验证的动作或必填字段差异。发布 B 前后核对 A 的已保存规则摘要，分别读取发布记录及两张工单的定义引用。保持办理人获权，分别提交符合 A、缺 B 新增字段及补齐该字段的请求，核各自按规则通过或拒绝，拒绝前后相应记录未变；若选动作差异则按相同原则核对。再撤当下权限，核两版同因拒绝且业务数据未变。登记仍写旧配置的客户端已切换或受控拒写的证据。
3. **规则来源不可信时不猜版本，缺定义时停写并说明仍可读取。** 先验 T-100 无可证来源时不补关联，再独立验缺对应定义时写入返回 503、动作停用、`definition_resolution=degraded`，工单和证据历史仍在且按当前权限读取。无权读仍拒绝，浏览器须将“规则无法解析，暂不可办理”与空结果区分。若只有历史结论缺出处，该结论记未知，关票仍仅计可证的已生效结论。为隔离用例依据独立证据复原对应原版规则后，只重试合法的新请求或查询原回执，复查原历史和期限。

### 6.2 C05 首轮取证清单

首轮使用[卡一](phase6-b2-acceptance-cards.md#卡一-c05-停用已提交而撤销投影失败)及[桌面判据](#51-c05-撤权故障)。引用同一轮 G04 记录、制品及连线指纹和材料 ID，记录请求关联号、操作引用 K、合成目标、入口、凭据类别和时点，附获权者读取核对的结果、前后变化及判定原因。脱敏摘要保留逻辑引用，原始日志留在获准的隔离批次。令牌、Cookie、口令、DSN 和文件正文不进记录或仓库。制品或连线变化后重做相关预检。

1. **入口与前置正对照。** 静态已核 `internal/router/router.go` 中 `UserHandler.UpdateStatus`、`AuthHandler.Refresh` 和文件代理挂接。`internal/middleware/fileauth.go` 的 `FileAuth` 复用 `JWT`，`internal/service/auth_service.go` 的 `Refresh` 和 `internal/repository/pat_repo.go` 的 `FindActiveByHash` 已核账号状态。绑定时确定实际地址、同一候选内适用的 Bearer/PAT 受保护读路由、仅 cookie 的文件对象、实际可观察的判定点与账号范围。实际执行证实各制品自身签发的目标凭据有效，所留 RT 槽未消费且代际、设备、期限匹配，控制刷新用独立设备槽，目标槽在观察窗内无其他刷新者。同线路控制账号故障前后均要通过，文件请求证实到达实际代理鉴权入口，浏览器缓存命中或 mock 回应不计。
2. **停用提交与 Redis 撤销待恢复。** 静态已核基线 `internal/service/user_service.go` 的 `UpdateStatus` 通过 `AfterIAMCommit` 安排 Redis 撤销。绑定时落定提交前由谁生成 K、实际唯一键和受权查询入口，核候选事务边界，登记 PG 独立读取证据的位置、唯一意图及 Redis 已确认代际字段、目标故障可观测时段。候选实际执行须同轮看到账户停用、新代际、首次操作号 K 对应的成功回执、唯一意图和仍落后的 Redis 已确认代际，另见旧 Redis 状态仍可读及目标故障命中。回滚分支独立核前后记录无变化，丢响应只按首次操作号 K 查，尚不可证时记待核查并暂停再次提交。
3. **四种凭据各自终态拒绝。** 静态可列预期账号原因和各入口应保持的业务事实。绑定候选时登记实际 HTTP 状态/原因、客户端显示及诊断关联。候选实际执行在同次已提交停用且Redis 已确认代际仍落后的窗口逐凭据留响应及当前账号判定。核 AT/仅 cookie 不回保护内容，文件请求确以仅 cookie 进入，RT 无新令牌或 cookie 且原槽无消费/替换，PAT 因账号停用拒绝且自身有效性未改变。依赖故障、凭据过期或格式、限流及资源无权给出各自证据，发生提前拦截的路径本轮无效。基线按自身已有状态和响应取证，红例只计目标保护差异，既有 RT/PAT 拒绝和局部 mock 证据单列。
4. **重启与重复操作。** 静态可定首次操作号 K、意图、目标代际及 Redis 已确认代际的比较关系，和另号启用被拒的判据。绑定时登记同一故障能否跨进程、重启所涉制品和资源、恢复及请求观察点。实际执行核重启前后原意图身份与待恢复状态、目标重试命中、重复停用零新增代际/回执/意图，以及另号启用拒绝和账号仍停用。若重启后无法证明原故障仍在，该步无有效结论。
5. **恢复及启用。** 静态可定获权重投原意图和目标代际、Redis 已确认代际及租约/fence 应满足的关系。绑定时确定受权查询、重投和启用的各自角色与出口。实际执行在可信同一 Redis 下恢复，核首次操作号 K 可查、同一意图完成、Redis 已确认代际达到目标代际、原停用仍在且无第二次安全写。之后另号获权启用，新代就绪后新会话方可使用，旧 JWT 仍拒绝，PAT 按其自身状态和当前权限判定。Redis 整体不可信时停止本卡单项恢复，沿 SESSION 专项。[C05 恢复与独立验收](../phase6/foundation-iam-module-detail.md#43-c05切换恢复与独立验收)
6. **服务端状态与界面证据。** 静态可列 §5.1 的待核查、已提交待恢复、恢复完成、明确回滚及终态拒绝。确定实际响应、判定原因与 UI 映射后再开始执行。执行时按 K 将同一操作的 PG 事实、HTTP 与界面提示逐项对上，未证实提交、已落库但 Redis 尚未同步到目标代际、已恢复三类状态须明确可区分。明确回滚核零提交，拒绝核实际守卫。单个通用错误不足以证明结果或原因。
