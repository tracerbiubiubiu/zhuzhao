## 1. 接下来怎么做

前三步做出一套能用测试数据验收的程序。比如测试人员可以让管理员停用账号、发布一版整改规则、再把两条漏洞风险合在一张工单里办理。实际开放给业务人员之前，要另外确认试用环境、人员和数据。后面四步也按同一名主要开发人员的时间依次安排。 [真实试用条件](#5-外部依赖和需要拍板的事)

开发与测试先用虚构资产和账号，以及可以模拟响应的情报、资产目录（CMDB）、人事和外部消息服务。真实试用建议用本地账号和获准的风险与资产记录。两位主管共同批准延期留到后续，真实数据来源、定级办法及自动动作在各自启用前确认。若试用必须提前加入其中一项，再核需要增加多少工作量。

1. **停用账号后旧登录失效。** 开工时确认五个仓库使用的版本、测试环境、一种整改工单类型、人员职责、所需证据和停止办法。管理员点停用后，账号状态先存入 PostgreSQL。即使 Redis 中的登录缓存一时未更新，旧登录也应失效。用户点击保存时再核当前权限和配置，检查不通过就不写入业务数据。管理员可以查原操作的结果并恢复失败的同步。对分配用户角色、分配角色菜单两项操作，本地审计记录写不进去时整个操作回滚，外部审计发送失败可以补送。公式、附件和日志按实际证据字段验证。现有接口盘点、测试数据和外部消息对接可同时准备。 [账号与权限设计](../phase6/foundation-iam-module-detail.md) · [独立测试环境](../design/engineering-execution-design.md)
2. **工单按创建时的规则办理。** 管理员发布整改规则 A 后创建一张工单，再发布 B。第一张仍用 A，之后按 B 创建的工单用 B，两张都按当前权限办理。升级前已经存在的测试工单，只有在能证明它当时使用什么规则时才补上版本，保留编号、历史和期限。找不到规则时按权限查看，暂停修改。保存整改证据时，同时保存字段、状态、时间、附件引用、历史及必要的后续处理记录，任何一项失败都撤回整次保存。发布前检查规则有效，旧客户端的写入口也要做相同的权限检查。先核所选类型的可见范围和参与资格，再在下一步核实际负责人和交接后的资格。办理页面、并发和浏览器检查随实际功能交付，完整流程画布、自动流转和跨环境复制配置随后再做。 [工单规则和版本](../phase6/ticket-module-detail.md) · [详设审计](../review/reports/phase6-detailed-design-audit-2026-11-20.md#1-会改变开工顺序的发现)
3. **工作人员能从风险登记办到逐项复测（发布验收点 B2）。** 先能录入风险或从一种模拟来源接收并保存风险，按权限查看列表、详情和计数，留下分级、责任与处理决定。派单人先预览两条风险合在一张整改工单，办理人接单后按项交证据，负责人逐项通过或打回。当前负责人申请接受风险时，由另一位具备资格的人批准。业务结果和应发提醒一并保存，第一次接单超时发一条站内提醒，发送失败可查，完整送达回执随后补齐。当前负责人看到一条待办，里面两项风险仍能分别验证。检查无权与确实没有数据的表现、重复提交和迟到结果、打回一项、删除工单或移出风险时的变化，以及丢响应后用原操作号查结果。试用前按议程 Q12 核人员、环境、数据、保留时间和回退办法。所选范围内的权限缺陷 AUTH-01/02/07 必须修复并用原错误场景验证，或者在服务端完全关闭对应功能并验证每个可达入口都拒绝。关键提醒用实际渠道验证。 [风险办理规则](../phase6/risk-module-detail.md) · [试用前要确认什么](../phase6/first-usable-release-plan.md#41-b0预演与真实业务试用准入)
4. **工单能发起任务，任务结果能更新清单（发布验收点 B3）。** 按当前人员、对象与字段权限，由工单的一步发起已获准的任务，记录原任务及结果，再按授权更新一项清单。随后验证清单变更能被核心接收并保存收件记录，再触发一个获准的只读任务。并行准备公共 HTTP 通知、发送状态和失败后的核对办法。用模拟数据查重复消息、撤权、迟到或进程重启时是否多做了一次业务。远端结果不明时先查原任务。实际无人值守动作还要批准授权范围，真实消息由提供方确认协议和测试窗口。 [跨系统办理细节](../phase6/task-activelist-message-detail.md)
5. **本地账号模式可以投入正式使用（发布验收点 B4）。** 验证工作人员在本地三层权限下能完成代表业务，使用办理页面、多选加标签和真实 HTTP 消息，并检查选定的旧对接程序仍可用。用计划上线的软件和环境试升级、回退、加密连接与密钥配置，以及先停止接收新请求、等待已接收的工作按约定结束，再由符合条件的进程接管。另验备份和恢复。处理一轮试用反馈并复查修复后，由所有者确认能否把主要开发时间转入 UAA。 [本地正式验收](../phase6/first-usable-release-plan.md#42-核心稳定的过渡出口)
6. **产品同时支持本地登录和企业管理。** 准备公开的扩展接口、资源目录和三类可以保留及恢复的同步记录。检查本地模式能独立使用、公司提供的数据按边界只读、非纳管部分仍可写、撤权能生效，以及安装、退出、四个必要页面和故障恢复。完成公共功能后可以与真实企业系统联调，测试资源和协议可以提前联系。 [公共功能明细](uaa-implementation-estimate.md)
7. **用真实 UAA 联调，经批准后切换（发布验收点 B5）。** 核真实登录、账号、账号角色、角色资源同步及授权范围。与公司服务失联时停写受管数据，检查撤权期限，先对比切换前后的身份和权限，再批准接管和退出清单。切换后用代表人员完成同一业务，核本地用户 ID、原记录归属、未完成事项和原操作回执都能继续查到。 [联调、切换与退出条件](uaa-real-integration-conditions.md)

### 按实际窗口增排的两项

- **隔离入网预演（发布验收点 B0）**。沿现有底座与合成数据测批准的目标、离线导入、登录/基础工单、升级回退与重启，给制品摘要、限制和停止入口。旧情景示例为 **2.5–5 日**。目标画像冻结后再复估实际净额，并确认预演窗口。真实试用所需环境证据在开门前取得；共享安装/恢复证据与正式发布只计一次。若这项必须用同一席位且排在真实试用前，主线相应增加尚未复用的工日。
- **最小可扩展基础版（发布验收点 B1）**。参考私有应用、进程外查询适配器及其当前授权、替换、禁用和兼容单独验收。按本轮要求安排在 B4 正式启用前，B4 复用已验参考组合，验证本次实际接缝和已登记旧协议消费者。原估算中，共用扩展接口已验时剩 **5–7 日**，接口未交时合 **7–10 日**。缺少可执行旧消费者时，先冻结已有最小参考组合或补接线再重估。完整风险真实源和设备能力仍按各自依赖安排。

## 2. 最早与保守排期

表中的工程量是从开工累计需要投入的工作日，按一名主要开发人员计算。较早情形假设别的团队能及时提供资料，主线上已交付的成果可以直接用，能共做的工作只做一次。保守情形多留了工日，供复用尚未证实、共用工作可能需要分别做的情况。为便于换算日历，以 **2026-11-23** 为演示开工日，最早按每周 5 个有效日，保守按每周 4 个有效日，不满一天的部分落到所在工作日。两个例子都还没扣法定假期，也没加外部等待和后排功能。实际日期取决于何时开工、有多少人力及何时满足试用和上线条件。

**分别记录通过工程检查的日期和实际开放的日期。** 用合成数据通过跨仓测试后，可以准备试用。真实账号和数据须按 Q12 批准，自动执行须按 Q09 确认授权和目标。本地正式运行前还要验证真实消息和运维条件。UAA 联调要等对方提供测试应用、协议、身份、网络和队列。正式接管前要比对新旧系统的授权结果，取得批准并约定切换时间。超出原约定的观察时间另算，等不到必要条件就顺延受影响的交付。
