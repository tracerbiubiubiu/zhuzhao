## 第一批 工单办理与读范围

### 开工冻结

- **撤回资格。** 只允许发起人本人撤回处于 `open`、无当前主责、且通过持久事实确认从未分派或受理的普通工单。首批由新建事务记录资格，首次分派或离开 `open` 后永久失去资格。没有可信记录的旧单拒绝撤回。已发布绑定规则必须声明 `open→cancelled` 的发起人撤回边，通用转换入口拒收专供撤回的边。风险在办工单继续走领域命令。转办限当前单一主责或获独立管理授权的操作者，候选和提交共用当前组织及人员资格。
- **读取权限。** 各入口先核功能授权，再用同一当前行谓词检查数据。存量类型为 `inherit`，保留原属主、组织、委托和合法抄送。新类型缺省 `participants_only`，只含发起人、当前主责及合法抄送。显式 `role_restricted` 加指定的现势有效角色。普通 `scope=all` 和组织委托只对继承策略按原合同生效。全局管理员例外在通过入口授权后适用。读取资格不授予写权限。失去某条来源后可使用剩余合法来源，失去最后一条时各入口均停止披露。
- **统计口径。** `GET /api/v1/tickets/stats` 使用独立 `ticket:stats` 权限，按状态、优先级或类型分组。各组分母为同条件下当前可见的在办数，超期为 SLA 截止严格早于同次 `as_of`，无分母返回 `null`。列表、统计和导出共用普通筛选条件，详情逐票使用同一行级判定。
- **交付分工。** 读取及统计、办理动作、薄 UI 分别在独立工作树先行测试并实施。主会话固定集成组合，由未参加实现的助手复核确切提交，再跑独占栈普通档和浏览器旅程。

### 1. 统一列表、详情、统计和导出

- **实施。** 先对账 `internal/service/ticket/service.go` 的 `Get`、`List`、`ExportStream`，`internal/service/ticket/resource.go` 的 `Authorize`、`GetFilter`，以及 `internal/repository/ticket_repo.go` 的 `buildTicketWhere`。列表与导出已有共用 SQL 条件，详情另做逐票判定。收敛所选类型的 L2 行范围，使详情判定与集合过滤使用相同的类型策略、组织和参与来源。保留入口各自的 L1 权限、旧类型继承策略及既有全局管理员例外。核列表与导出的普通筛选校验一致，关联候选继续按双端写资格收窄。个人角标仍通过独立职责接口取数。回归 `internal/service/ticket/risk_dispatch_read.go` 的 `RiskDispatchVisibleTicketsWhere`。
- **统计。** 按原第一档 `GET /tickets/stats` 方案提供状态、优先级和类型的固定分组，返回计数、超期在办数和比率。按同一授权范围与查询过滤后再聚合。开工冻结分母与 `as_of` 口径，建议按过滤后在办样本为分母，零分母显示无适用值。跨请求核对使用固定数据与时间。部门历史口径和风险态势归第 20 项。 [统计第一档](../phase6/04-r4-metrics-reports.md) · [工单侧统计（件 11）](../phase6/06-ticket-completeness.md#26件当前对账2026-11-14)
- **验收。** 枚举每个主体可见的票 ID，对照翻页后的全集、逐票详情、XLSX 行和各聚合桶。加一张同组织但类型不允许读取的票，以及跨组织、仅抄送、有两种读来源、撤掉最后一种读来源的票。显式 `all` 仍受类型策略过滤。隐藏与不存在的详情同形，聚合与导出均无隐藏票贡献。撤回导致的终态同时核对列表、在办计数、角标和在途影响计数。

### 2. 当前主责转办

- **实施。** 以 `POST /tickets/transfer` 为候选入口，请求带字符串票号、单一继任人、预期 `revision` 和幂等键。按共同生命周期合同冻结字段名、允许状态、管理职责及同人转办语义后接入 UI。复用 `service.go` 的 `assignWithGuard` 锁序和写入能力，转办单独核当前主责或独立获准的管理职责。现有 `/tickets/people` 只作基线，候选查询和提交共用当前人员启用、类型和组织资格谓词。锁内再次读取对象、原主责及目标资格，通过后更新主责、写转办历史和原操作回执。业务修订沿 `000087_ticket_evidence_transition.up.sql` 的 `advance_ticket_business_revision` 递增。
- **验收。** 在 A 版同一节点把甲的票转乙。比较转前后 `definition_version`、`status`、`status_changed_at`、SLA 截止及原时间历史逐值相等，主责改变、业务修订递增一次、转办事件一条。乙取得获准办理动作，甲只有自身其余合法读来源。分别拒绝越界、停用、预览后撤权、仅抄送写和旧修订。两个合法请求竞争只产生一个写入。提交丢响应或服务重启后按原键确认同一次转办，期间业务效果只发生一次。普通动作在风险整改单上继续受领域写守卫约束，风险重派走原入口。 [转办与候选合同](../phase6/ticket-module-detail.md#71-ticket准确wire候选人及实施切片)

### 3. 发起人条件撤回

- **实施。** 首批在选定类型的已发布图启用发起人撤回边，复用 `transition_service.go` 的版本化转换和 `evidence_transition.go` 的原键事务。锁内按生命周期合同核发起人、`open`、未受理且未分派，输入使用字符串票号、预期修订和幂等键。首批拟对曾分派后清主责及历史未知的票拒写，开工前锁定证据来源与历史边界。主线没有通用接单时间字段，不能用状态文本或当前主责为空推断历史。撤回写入终态、原操作结果及历史，详情动作与提交均使用同一个资格判定，并覆盖 `/:id/actions` 和旧 `/:id/transitions/available`。
- **验收。** 发起人能撤回全新未分派票。等详情打开后先分派或改变修订，原页面的提交被拒。再用已受理、曾分派后空主责、权限不足和无可信规则的旧票验证边界。并发撤回与分派只产生一个合法终态或主责写入，重放原键最多一次效果。终态从个人待办、在办统计、字段在途影响和可办动作退出，仍可按原读资格审阅。 [发起人撤回合同](../design/business-lifecycle-contracts.md#43-能力响应和兼容读取) · [终态联动（件 9）](../phase6/06-ticket-completeness.md#26件当前对账2026-11-14)

**第一批出口。** 固定 Core/UI 用浏览器完成查列表→转办→换人办理→发起人撤回另一张票→对账统计和下载导出。再让打开页面的操作人失去资格，复验按钮刷新及服务端拒绝。读取真实 PostgreSQL 的主责、节点/期限、修订、历史及回执，与 HTTP 和 UI 逐项对应。第二批保留这套样本和回归。

## 第二批 配置晋级、在途迁版与自动选路

### 4. 配置包导出、预演、获准应用和补偿

- **实施。** 首批计划入口选独立 CLI，命令与审批载体在开工时冻结。包使用类型代码、字段键、模板代码和稳定引用，范围为已发布图、完整字段和选定模板。先验字段读回再写入的往返，重点核 `internal/service/ticket/type_admin.go` 的 `validateFieldInputs` 对数值/评分字段的旧空 `options` 语义。复用 `definition_publication.go` 的定义校验与发布逻辑，对同一候选图和字段整体校验。便携包规范摘要与含目标本地身份的发布摘要分开计算。`internal/repository/ticket_repo.go` 的字段替换与模板写需要能在同一外层事务运行。
- **审批与应用。** 预演只读，输出实体动作、差异、阻塞项、当前发布版与在途计数。计划绑定包摘要、目标环境及库标识、引用、实体基线和审批。应用事务重读计划及基线，整包写入和成功审计一并提交。应用后按批准的补偿计划发布受控补偿版本、恢复模板前值，并保留受新版本约束的在途工单。补偿样本先取兼容的同键字段变更。字段锁会拦截删除新增字段的逆向操作，开工时锁定新增字段的受控补偿路径或预演阻断策略。 [配置晋级合同](../proposal/config-promotion.md#3-计划与应用) · [补偿与验收](../proposal/config-promotion.md#4-提交后补偿)
- **验收。** 两个合成库使用不同自增 ID，完成导出→预演→批准→应用→再导出，比较规范化配置。相同内容重新预演为无变化，旧预演遇目标漂移时拒绝。错目标、错包、错审批、关键依赖变化、受保护种子、异常草稿、后段写入失败及成功审计失败分别验证整包零部分落地。预演阶段核目标无业务写入，成功阶段核审计实际执行人和审批引用。再演练补偿，并逐票确认先建 A 版、新建 B 版及已绑 B 版的工单规则。

### 5. D01 同名状态最小在途迁版

- **实施。** 复用 `internal/service/ticket/instance_definition.go` 的 `resolveTicketDefinition`，并用 `cmd/server/bind_ticket_definitions.go` 所接可信旧单补绑命令回归空绑定语义。迁版是已绑定 A→B 的逐票操作。只读预演限非终态票，绑定票 ID、源/目标版本及摘要、同名节点、当前修订和兼容结果。执行要求同一类型且源定义的状态在目标定义中均保留，核当前权限、字段、证据引用和动作资格兼容。首批限普通票，存在在办风险关联或当前节点的超时和催办语义改变时阻断。批量界面如需承接，按明确选择的每张票逐一预演和返回结果。事务内更新版本绑定、记录迁版事件及操作回执，复用数据库业务修订触发器。删状态映射继续按 Phase 7 D18。 [迁版合同](../phase6/ticket-module-detail.md#33-发布迁版与配置晋级)
- **验收。** 对两张 A 版在途票应用 B 版发布，其中一张经批准迁 B，另一张继续按 A 办理。成功票版本及修订相应更新，`status`、节点进入时间、SLA 截止、催办水位和已有历史逐值相同，并用受控时钟跑一次实际超时扫描。新迁版事件只有一条，原动作和 Taskrunner/清单/消息业务效果计数相同。预演后有人办票、目标缺状态、字段或资格冲突、撤权或来源不可信时拒绝或重新预演。同号重查保持已提交效果，单票冲突可独立处理。升级前空绑定且缺可信规则的旧票继续使用相应只读路径。

### 6. D16 自动选路、有界执行与停在原节点

- **实施。** 在发布预检检查显式 `automatic` 出边、优先级、唯一默认边和明显环。首条只取普通票已发布图的自动边，显式门控旧快照并保留旧关键词分派回归。条件分派、定时和回调触发的后续切片沿 D16 各自的适用场景确认范围。按冻结的定义和同一条件求值器选首个命中，全部条件合法求值且无命中才用默认边。源节点业务事务保存可靠唤醒意图，按 R01 合同用扫描、租约和防旧执行者提交标记恢复。新短事务重查源状态、修订、动作合同、服务范围、字段和证据。参考 `evidence_transition.go` 的 `applyEvidenceTransitionGuardedTx` 复用转换校验，人工读取和直接写入口均识别自动边。本轮拟按详设的候选深度上限 16 冻结运行参数。 [选路合同](../phase6/ticket-module-detail.md#5-字段安全检索快速入口与自动路由) · [R01 和 D16 依赖](planning-backlog.md)
- **验收。** 用发布图验证多命中按优先级、全未命中走默认、以及自动边从人工可选动作中隐藏。条件求值异常、权威依赖超时、验证失败、旧版本、人工推进竞态和达到链深时记录对应处置。应暂停的分支保留最后已提交节点及原计时，不产生默认跳转或重复后继。模拟业务提交后停止 Core，重启后同一唤醒意图恢复；再用双消费者、迟到租约和重复唤醒检查对同一状态修订最多一次推进。页面或受权诊断入口应能读回暂停原因与原记录。

**第二批出口。** 从第一批样本出发实跑源库到目标库的晋级及补偿。固定同一张迁版票处理完预演、确认、按 B 版办理和自动选路停住，再核另一张 A 版票仍按 A 办理。对迁版与选路的并发用例用独立样本验证旧意图不能推进已迁版本。运行已验 B2、B3 和复核消息代表回归，核对回执、原时钟和存量历史。补偿处置及回退步骤随实现写入运维手册。

- **现有页面小切片（U03、U06）。** 批量标签可以复用逐票 `AddTags`，验跨页显式选择、部分成功、仅取消未发送项和按原票重试。系统与外围页可先补既有 API 的读失败状态，例如任务死信读取失败和 ActiveList 同查询刷新失败。现有情报页面的历史/结果布局和同查询刷新失败状态也可先做，设备与模型接入归第 19 项。标签与共用筛选修改同一列表文件，由同一 UI 工作树顺序接入。

### 可并行制作，随接口联验

- **跟第一批。** 工单详情动作区、单人候选、撤回确认、权限变化提示和统计/导出结果组件，可在合同冻结后用固定 JSON 和组件用例开发。实际交付需读服务端可用动作、候选和聚合结果，并用不同身份真实走通。同一份页面请求状态可支持四视角，但个人待办/已办和复核责任须等对应服务端责任谓词。首页及消息的数字、角标和钻取要用同一责任口径逐一核对。当前硬编码 `assigned/in_progress` 的过滤只适用于已有页面口径。
- **跟第二批。** 类型、字段和流程配置工作区可先交布局、步骤导航、草稿保留、预览组件及键盘操作。已有草稿/定义预检发布用现有 API 验草稿、发布和 409 冲突。新增晋级计划、在途迁版和自动选路暂停的界面，随对应受权读或写合同、实际批准及回执联验。晋级首批以 CLI 取证，界面原型可以消费合成报告，真实应用按钮随将来的 HTTP 授权评审。 [配置工作区](../phase6/ticket-module-detail.md#6-u01u07-页面与状态详细合同)

## 两批共同交付检查

- [ ] 核对已验能力与剩余缺口。每个任务先写能观察差异的失败用例，再限量实现、跑定向回归并做独立复核。Core 定向用 `GOWORK=off go test -tags=integration ./internal/service/ticket ./internal/repository ./internal/router`，按本批实际用例名筛选。先回归 `TestD01InstanceUsesBoundRules`、`TestD01DefinitionPublicationHTTP`、`TestD9_ConcurrentCloseAssignRace` 和 `TestTicketStatuses_ListAndExportRespectScope`，再增加两批各自的失败与成功用例。至少保留正常、撤权、失败回滚、旧数据、并发和原操作键证据。
- [ ] 固定 Core、UI、适用服务和数据制品。在独占 PostgreSQL/Redis/RustFS 等测试环境运行实际 Core/UI 及适用依赖。每批按普通档运行 `make quality-plan`、`make quality-check`，以及 `make lint`、`make test-unit`、`make test-integration`、`make test-cover`、`make acceptance` 和适用的 `make migrate-up`、`make swag`。迁移验从 v104 升级、适用降级/阻断及空库往返，第二批另保留第一批已产生的合成业务历史验证兼容。使用专属测试账号。 [普通档门禁](../guides/development.md#4-交付前验证)
- [ ] UI 先运行 `pnpm quality:plan` 与 `pnpm quality:check`，再在固定独占栈上以 `E2E_REQUIRE_COMPLETE=1 E2E_USE_PRESTARTED_UI=1 pnpm run gate` 验完整标准浏览器清单，并执行 `pnpm test:e2e:b2`。定向增量可用 `pnpm exec playwright test` 指定项目既有 `e2e/s10-ticket-detail.spec.ts`、`e2e/w4-ticket-smoke.spec.ts` 及新增本批用例。运行同一隔离组合核真实请求、角色、持久事实和浏览器结果。第 18 项最终按 27 个基线路由及本期新增页逐页收口。随验收记录列出通过、失败后复跑、尚待现场或后续工作的范围以及每个证据所对应的提交。 [前端证据要求](../phase6/frontend-page-family-detail.md#7-实施与证据)
