# phase6/ — Phase 6 规划：风险管理模块（规划草案）

> **文档定位**：Phase 6 唯一规划文档（草案）。**状态 = 未排期、未启动**。与 `phase5/*` 同款纪律：设计就绪稿，非交付承诺；启动批另立实施计划。
>
> **立项由来**（2026-10-08 所有者提出，决策登记 = [design-decisions §28](../design/design-decisions.md)）：**首个真正的业务模块**——面向企业内部风险管理团队，管理**软件/系统类风险**的"汇聚 → 评估 → 处置 → 关闭"闭环。所有者原始描述较简，本文档经业界实践对标补全（补全点在 §2 各段标注）。
>
> **硬前置（依赖链，关键）**：本模块的处置执行面**完全复用工单模块**——**依赖 Phase 5 的 S1（工单字段设计器）、S2（流程设计器）、S6（消息通知）、S10（抄送/标签/角标/节点超时——2026-10-09 差距分析后扩入）交付**；弱依赖 S5（风险证据附件）。因此 **Phase 6 排期必然后于 Phase 5**（至少上述段交付；快路径选项见 §7——S1/S2 可由兜底形态替代先行）。

## 0. 一句话

多数据源汇聚**风险单/事件** → 评估分级 → 派生**风险整改工单**（复用工单模块：字段/流程/指派）→ 消息通知驱动处理 → **工单终态联动风险单关闭**，形成风险处置闭环；为内部风险管理团队提供统一风险台账与处置跟踪。

## 1. 概念模型（两个实体，勿混）

| 实体 | 说明 |
|------|------|
| **风险单（risk item）** | 风险管理域自有实体，**自己的生命周期**：新增 → 已评估 → 整改中 → （复核）→ 关闭 / 已接受。字段：来源/类型/涉及系统/级别/指纹/风险责任人（owner）/deadline/处置策略 |
| **整改工单（ticket）** | 复用既有工单模块（类型/字段/流程全配置化——phase5 S1/S2 交付后具备条件）；风险单派生工单并保持关联 |
| **关系** | 一个风险单 ↔ N 个工单（第一档 1:1 足够）；工单终态 → 风险单联动关闭 |

**为什么分两个实体**（业界惯例）：风险是"持续存在的事实"（漏洞/隐患在整改完成前一直在），工单是"一次处置动作"。风险单的生命周期与工单状态机不同构——与 phase5 S2"工单流程 vs 任务编排不同构"同一分界逻辑。

## 2. 范围：四段（初稿，启动批细化；标注◆=业界对标后补全项）

### P6-R1 风险汇聚与台账

- 数据源第一档 = **手动录入 + 上报 API**（内部系统/脚本 POST 风险事件，走既有鉴权）；第二档（触发驱动）= 扫描器/SIEM webhook 连接器
- **◆指纹去重**：系统+类型+外部标识哈希——同风险重复上报归并（业界漏洞管理核心实践，Vulcan/Nucleus 类产品的立身之本）；重报时提升计数/更新而非建新单。**已关闭单重报语义须拍（2026-10-09 隐藏需求核查补遗）**：同指纹风险已关闭后又上报——reopen 还是建新单？业界漏洞管理惯例=建新单（回归/复活），不定则实现随意且影响台账口径。
- 台账页：按级别/状态/来源/涉及系统筛选、详情、**风险责任人（owner）指派**（风险单自身的 owner 先行，处置工单再指派处理人——两级责任人）。**人读编号表设计前必拍（2026-10-09 隐藏需求核查补遗）**：`RISK-2026-NNNN` 形态编号列+生成规则——工单现状唯一标识=自增 id（无人读编号），风险通报/通知跨团队引用无可核对凭据，合规场景更不可缺；**owner 离职（禁用）接管登记（同日补遗）**：用户禁用对工单/风险零联动（代码核实：Assign 连目标用户 active 校验都没有）——owner 离职=风险无人处置属合规硬伤，至少"名下风险清单告警+改派端点"，随 M-HR 离职处置件对齐。
- 上报 API 的鉴权与字段校验：走平台既有鉴权（AK/SK 或用户 token），schema 白名单校验。**滥用防护与审计线（2026-10-09 隐藏需求核查补遗）**：①脚本 bug 风暴可绕指纹去重（不同指纹）——上报端点挂既有 rate_limit 桶 + body 上限；②**risk_events 审计事件表**（同 ticket_events 形态：created/status_changed/level_changed/accepted/...）随表设计定型——"谁把高级改低/谁做的接受/有效期谁改的"须可追溯（风险闭环=合规场景），或显式降级复用 audit 中间件并说明取舍。

### P6-R2 评估与分级

- 级别第一档 = 手动选定（紧急/高/中/低）；◆评分模型（可能性×影响 5×5 矩阵、CVSS 映射）后续档。**级别枚举载体启动拍（2026-10-09 同日补遗）**：字典 vs Go 常量——影响 R4 报表口径与筛选复用；**deadline 语义一句话登记（同日）**：自然日 vs 工作日，内网第一档建议自然日+显式登记。
- **按级别配处置时限**：deadline 字段 + 超期提醒（走 S6 通知）——**刻意不做 SLA 计时引擎**（§23 暂缓域不碰，轻量形态够用）；超期扫描骑 P4 收归后的进程内 cron（`cron_scheduler.go` + advisory lock，既有设施零新增）
- **◆处置策略四选一（ISO 27001 risk treatment 标准模型）**：**整改**（mitigate，派工单）/ **接受**（accept，◆需审批 + 有效期 + **到期重审**——风险管理团队刚需，业界标配，原始描述未提）/ **转移**（transfer）/ **规避**（avoid）——后两者第一档登记即可
- **◆风险接受单**：接受 ≠ 关闭——独立状态"已接受"带有效期，到期自动重开评估并通知 owner

### P6-R3 处置联动（与工单/通知模块的桥，本模块核心价值）

- 风险单 → 一键生成整改工单：选工单类型 + **字段预填**（风险编号/级别/涉及系统/描述——复用 phase5 S1 的模板预填与字段 schema 能力）
- **编辑时预填 auto_fill（2026-10-16 所有者场景登记，与 phase5 S1 对表）**：字段预填的第二档语义——发起/编辑工单时按已填字段实时带出并**支持人工二次修改**（区别于 formula 强制计算：建议预填 vs SSOT 覆盖）。场景：风险事件主机 IP 自动带入工单系统 IP 字段 → 按 IP 查 **CMDB** 带出责任人同样预填可改（CMDB = phase5 S1 `DataFetcher` 数据源白名单的首个企业外部源实例）。元数据承载于字段 schema `field_options`（与 formula 同列，执行时机双态预留——phase5 S1 随 formula 批预留、实现触发驱动），详录 [phase5/01 号 §3.3③](../phase5/01-s1-form-designer.md)。
- **批量下发（2026-10-16 所有者场景登记，启动批细化）**：从风险事件集合批量下发整改工单，**字段可能不全**——形态 = **向导三步 + 部分成功 + 行级报告**（业界锚点：Jira CSV Import / Salesforce Data Loader / ServiceNow Import Set——校验与下发分离、部分成功为常态）：① 选风险事件集合 → ② 字段映射预览（auto_fill 带出结果逐行显示、缺失行高亮）→ ③ 下发策略：**完整行建单，不完整行不建单**、留风险侧标"未下发"可修正重发（零工单状态机改动）；**草稿态留二档**（业务强要求"每张风险单必有对应工单"时再加工单 draft 态——动 S3 状态机域，默认不做）。依赖：S1 auto_fill 预填 / S6 通知（下发完成通知）。
- **工单终态 → 风险单联动关闭**：机制与 S6 触发层同款拍板（显式 emit 推荐 vs 事件消费面）——**拍板须按"共享事件面"决策（2026-10-08 复核补充）**：S6（通知）与本模块（风险关闭）是同一机制的两个消费方，若选 emit 应做成**可订阅内部钩子**（一次状态变更、多订阅者），禁止把风险关闭逻辑硬编码进 ticket service 状态变更路径（risk 域焊进 ticket 域=破坏领域隔离，ticket 为未来拆分而隔离）；◆**复核态可选**（业界惯例：处置完成后由 owner 验证再关，自动直关为默认可配——尊重所有者"自动关闭"诉求，复核为开关）。**跨域一致性兜底（2026-10-09 隐藏需求核查补遗）**：emit 钩子=进程内 at-most-once，钩子前崩溃事件即丢——通知丢失无害（可补发），**风险单关闭联动丢失=工单已终态而风险单永远"整改中"**，无检测手段即永久不一致；R3 随批补"终态对账扫描"（cron 扫已终态工单关联的未关风险单 → 告警或自动关，骑既有 cron 设施；观测面依赖 phase5 S10 cron 可观测随行件）。
- 工单指派/超期/状态变化 → S6 模板通知（风险 owner + 工单处理人）
- 工单与风险单双向可见：工单详情挂风险来源链接，风险单详情列整改工单

### P6-R4 度量与报表（可后置）

- 风险敞口看板（按级别/状态/来源/系统分布）、处置 MTTR、超期清单、接受单到期清单
- excelize 固定列导出（复用 P4-4 模式；**必须接 L2**）

### 选型预置（建议值——启动批确认制）

- **指纹**：`SHA-256(涉及系统 + 类型 + 外部标识)` 落列 UNIQUE——去重判定 O(1)；
- **R3 风险→工单**：risk service 进程内调 ticket service Create（模块化单体内直依赖，与现有域间调用惯例一致；未来拆分随 Port 化迁移）；
- **求值器/导出/通知**：全部复用 phase5 公共件（S1 expr 求值器 / P4-4 导出模式 / S6 模板通道），本模块不自建；
- **风险单生命周期**：Go 常量状态机（新增→已评估→整改中→复核?→关闭/已接受），不入配置体系（§5 边界既定）。

## 3. 与既有拍板的衔接

- **对 Phase 5 的三项要求（2026-10-08 复核补充，已回写 phase5/README 对应段）**：
  1. **S6 触发层/收件人解析须域无关**——风险通知的收件人是 risk owner（非工单字段），S6 须交付"业务事件 → 模板 → 发送"的通用面（模板渲染与通道发送本就实体无关；触发挂接与收件人声明方式支持工单域之外的业务实体），否则 phase6 面临改 S6 或自建平行通知的二选一；
  2. **工单状态变更"事件面"= S6 与 phase6 的共享决策**（见 R3 段），不允许各自硬编码；
  3. **risk_items 落 L2 的锚点设计点**——按平台策略库 schema 约定带 `org_id`/`created_by`（fail-fast），风险归属组织=风险管理团队 org 还是受影响业务 org，启动批拍。
- **对 Phase 5 的 S10 依赖（2026-10-09 场景差距分析对齐）**：**风险工单按等级自动选抄送人**依赖 S10 抄送（cc 规则）；**风险事件/工单打标签筛选**依赖 S10 标签；**新风险事件右上角角标**依赖 S10 聚合计数端点；**节点逾期按级别通知**依赖 S10 节点级超时——硬前置相应扩为 **S1/S2/S6 + S10**（S10 缺席则四能力降级：手动抄送/固定筛选/无角标/仅风险单级 deadline）。
- **理想态登记（不做硬性要求）**：①风险事件规则化自动创建整改工单（免人工点击发起）；②威胁情报→资产关联自动创建风险事件（依赖资产管理平台，**所有者明示先不做**）；③任务多子任务+数据共享（taskrunner parent_id 后置项；子任务数据面=activelist 既有定位；编排维持 16 号红线不与工单流程合并——轻编排 zhuzhao 回调串联/重编排外部 DAG）。
- **第四线分析增量（2026-10-09，九段快照期产出——部分判定已被 S10 超越，增量九条归位）**：
  - **快路径选项（价值最高，启动拍板项）**：S1/S2 有已交付兜底形态（字段=管理页表格/流程=JSON 源码）——可不等 S1/S2、用兜底配置先跑通 R1–R3 MVP（真硬前置仅 S6+S10，约 5–7 周 vs 12–17 周），S1/S2 体验升级后补、配置平滑迁移；**取舍=牺牲管理员配置体验换风险闭环提前数月**。
  - **系统台账第一小步**：涉及系统先挂 P4-3 字典（统计聚合零成本），owner 解析仍需 R1 轻量系统台账（systems 表含 owner_user_id，派单按 system_code 解析默认处理人——P0-5 方案细化：台账与字典不互斥，字典管枚举、台账管 owner）。
  - **高级搜索登记（触发驱动）**：工单 keyword 现仅搜标题，custom_data 自定义字段筛选缺失是台账类使用硬伤——诉求出现时启用（PG JSONB 谓词或检索单独评估）。
  - **审计归档 cron 部署坑（跨段）**：`audit.archive.cron_enabled` 默认 false 且 compose/config 均未开启——归档定时清理当前**不运行**，保留期 180 天形同虚设；部署清单必设 `APP_AUDIT_ARCHIVE_CRON_ENABLED=true` 或改默认值（随启动批拍）。
- **BK-21 触发实锤**：风险单 = **新资源接 L2**——BK-21 护栏泛化（fail-closed 哨兵泛化 registry 层，1–2 天）**必须随本模块同批**（phase6 第一个随行件；此前多次分析确认的链式关系在此兑现）
- 权限码 `risk:read`/`risk:manage` 等种子 + 菜单（风险台账/管理按钮）随批；审批需求（风险接受审批）：S3b 审批引擎等首个真实审批场景（dd §29 翻案后已解冻排期）——**第一档接受审批维持 superadmin/owner 确认制，S3b 落地后可升级**
- 迁移：`risk_items`/`risk_sources` 等表族；编号启动时按 [11 号 §4 迁移地图](../review/11-project-control.md) 对账（**不在此写死下一编号**，与 phase5 S5/S6 按启动序 A2 竞争）
- **对接预留接口（内网前置，2026-10-09 补充）**：`RiskSourceConnector` 端口（Ingest 事件 → 风险单——第一档实现 = 手动录入 + 上报 API；扫描器/SIEM webhook 连接器 = 第二档各写一个 adapter）+ S9 情报消费内部接口。总纪律同 [phase5 §6 对接预留清单](../phase5/README.md)：外部对接点一律 Port+Adapter+config，endpoint/凭据禁止硬编码，桩实现 fail-fast 不虚标。
- **登录/登出审计随行（2026-10-09 隐藏需求核查补遗，合规随行件）**：`/auth` 匿名组无 AuditLog 中间件（`router.go:159-166`）——登录成功/失败/登出零审计；平台承担风险管理职能后为 ISO 27001 A.12.4 标准拷问点（与终报 P2-11"登录方式 sso/local 归因字段"是两件事，后者随 M-UAA 件 1[原 M-SSO]）。量级半天，本 phase 启动批随行或触发驱动。

## 5. 明确不做（边界）

GRC 全家桶（合规条款库/审计管理/法务/财务/经营风险——本模块只管**软件与系统类技术风险**）；SIEM/SOAR 实时响应编排；扫描器 SDK 直连（第一档 API 上报）；CMDB/资产库建设；漏洞扫描能力本身；SLA 计时引擎；**风险单生命周期第一档 = 固定状态机**（不入 `ticket_types` 式配置体系——"风险流程也可视化配置化"属范围蔓延，后续档按需评估）。
