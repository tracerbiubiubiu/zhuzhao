## 0. 一句话

多数据源汇聚**风险单/事件** → 评估分级 → 派生**风险整改工单**（复用工单模块：字段/流程/指派）→ 消息通知驱动处理 → **工单终态联动风险单关闭**，形成风险处置闭环；为内部风险管理团队提供统一风险台账与处置跟踪。

## 1. 概念模型（两个实体，勿混）

| 实体 | 说明 |
|------|------|
| **风险单（risk item）** | 风险管理域自有实体，**自己的生命周期**：新增 → 已评估 → 整改中 → （复核）→ 关闭 / 已接受。字段：来源/类型/涉及系统/级别/指纹/风险责任人（owner）/deadline/处置策略 |
| **整改工单（ticket）** | 复用既有工单模块（类型/字段/流程全配置化——phase5 S1/S2 交付后具备条件）；风险单派生工单并保持关联 |
| **关系** | 一个风险单 ↔ N 个工单（第一档 1:1 足够）；工单终态 → 风险单联动关闭 |

**为什么分两个实体**（业界惯例）：风险是"持续存在的事实"（漏洞/隐患在整改完成前一直在），工单是"一次处置动作"。风险单的生命周期与工单状态机不同构——与 phase5 S2"工单流程 vs 任务编排不同构"同一分界逻辑。

### P6-R1 风险汇聚与台账

- 数据源第一档 = **手动录入 + 上报 API**（内部系统/脚本 POST 风险事件，走既有鉴权）；第二档（触发驱动）= 扫描器/SIEM webhook 连接器
- **◆指纹去重**：系统+类型+外部标识哈希——同风险重复上报归并（业界漏洞管理核心实践，Vulcan/Nucleus 类产品的立身之本）；重报时提升计数/更新而非建新单。**已关闭单重报语义须拍（2026-10-09 隐藏需求核查补遗）**：同指纹风险已关闭后又上报——reopen 还是建新单？业界漏洞管理惯例=建新单（回归/复活），不定则实现随意且影响台账口径。
- 台账页：按级别/状态/来源/涉及系统筛选、详情、**风险责任人（owner）指派**（风险单自身的 owner 先行，处置工单再指派处理人——两级责任人）。**人读编号表设计前必拍（2026-10-09 隐藏需求核查补遗）**：`RISK-2026-NNNN` 形态编号列+生成规则——工单现状唯一标识=自增 id（无人读编号），风险通报/通知跨团队引用无可核对凭据，合规场景更不可缺；**owner 离职（禁用）接管登记（同日补遗）**：用户禁用对工单/风险零联动（代码核实：Assign 连目标用户 active 校验都没有）——owner 离职=风险无人处置属合规硬伤，至少"名下风险清单告警+改派端点"，随 M-HR 离职处置件对齐。
- 上报 API 的鉴权与字段校验：走平台既有鉴权（AK/SK 或用户 token），schema 白名单校验。**滥用防护与审计线（2026-10-09 隐藏需求核查补遗）**：①脚本 bug 风暴可绕指纹去重（不同指纹）——上报端点挂既有 rate_limit 桶 + body 上限；②**risk_events 审计事件表**（同 ticket_events 形态：created/status_changed/level_changed/accepted/...）随表设计定型——"谁把高级改低/谁做的接受/有效期谁改的"须可追溯（风险闭环=合规场景），或显式降级复用 audit 中间件并说明取舍。
- **◆外部平台勘查输入（2026-10-26 勘查回填，均为设计输入/登记级，立项批细化）**：
  - **字段模型六组分类**：risk_items schema 参照成熟漏洞台账的六组骨架——基本信息 / 风险信息 / 评分与优先级 / 关联资产 / 生命周期与状态 / **归属组**（责任人·所属组织·协同处理人·**关联工单 ID**——最后者即 R3 双向可见的字段位）；台账列显示、详情页分组、通知模板取词共用同一骨架，多来源数据灌入不散口径。
  - **处置流水独立表 + 状态轨迹**：处置动作 append-only 流水（动作类型/操作人/时间/备注）独立于风险主表，状态轨迹端点按单吐全历史；与 risk_events 审计事件表**相邻同构**（前者面向用户的处置历史、后者面向审计的领域事件），表结构同批设计；R2 四处置策略（含接受单有效期与到期重审）每次执行落此表——"整改中"持续数周的处置过程在关闭/复盘/审计时可完整回放。
  - **接入面「镜像+流水」结构**：外部源数据落**可重建镜像表**、本地处置落 append-only 流水表，`(外部id, 来源)` 弱关联、**无外键**、孤儿镜像骑既有 cron 清理——源重推/回刷不冲掉本地处置事实（本地是 SSOT）。**启动拍板项：状态口径二选一**——处置结论回写镜像侧 vs 本地只认流水（镜像状态仅参考）；不拍则两处状态漂移（外部平台实证踩坑：列表按镜像状态过滤、处置只写流水未回写）。此即统一接入层"从第一天按通用形态建"的具体结构，首源漏扫直接套用。
  - **owner 离职接管吸收「交接三件」**：名下风险清单告警 / 接管人批量改派+通知新 owner / 交接动作留痕（谁在何时把谁的哪些单交给谁）——已登记硬伤（本段上方）的现成解法形态，领域模型参照 [hr-directory-sync 前置件注记](../proposal/hr-directory-sync.md)，随 M-HR 离职处置件对齐。
  - **台账二层聚合视图（补全切片，不进核心闭环）**：按系统/类型/来源/级别/owner 分组聚合计数端点——管理层周会问答（"高危集中在哪几个系统、哪个部门整改最慢"）靠聚合而非逐条筛选；台账分组视图与 R4 看板**共用同一组端点**防口径漂移。
  - **台账页交互蓝本**：高级搜索条件树 / 批量编辑 / 标签 / 动态列 / Excel 导出——前端交互参照外部成熟漏洞台账页（勘查在档，实施时取用）。
  - **批量导入（触发驱动登记，2026-10-26 所有者批准）**：Excel 模板下载 + 导入校验 + 部分成功行级报告——存量人工台账（Excel）迁移场景；首源数据走 API 推，不依赖此项。
  - **上报 API 防重二道防线（登记，启动批拍）**：既有 rate_limit 桶之外，幂等栅栏（提交凭证形态，job_submissions 同款）作对照项——脚本风暴绕指纹去重场景的第二道闸。
  - **台账保留期/归档策略（触发驱动登记）**：数据量级上来后启用；形态可骑 intel_cleanup 同款 cron（外部平台有"N 天自动清理"先例）。

### P6-R2 评估与分级

- 级别第一档 = 手动选定（紧急/高/中/低）；◆评分模型（可能性×影响 5×5 矩阵、CVSS 映射）后续档。**级别枚举载体启动拍（2026-10-09 同日补遗）**：字典 vs Go 常量——影响 R4 报表口径与筛选复用；**deadline 语义一句话登记（同日）**：自然日 vs 工作日，内网第一档建议自然日+显式登记。
- **按级别配处置时限**：deadline 字段 + 超期提醒（走 S6 通知）——**刻意不做 SLA 计时引擎**（§23 暂缓域不碰，轻量形态够用）；超期扫描骑 P4 收归后的进程内 cron（`cron_scheduler.go` + advisory lock，既有设施零新增）
- **◆处置策略四选一（ISO 27001 risk treatment 标准模型）**：**整改**（mitigate，派工单）/ **接受**（accept，◆需审批 + 有效期 + **到期重审**——风险管理团队刚需，业界标配，原始描述未提）/ **转移**（transfer）/ **规避**（avoid）——后两者第一档登记即可
- **◆风险接受单**：接受 ≠ 关闭——独立状态"已接受"带有效期，到期自动重开评估并通知 owner

### P6-R3 处置联动（与工单/通知模块的桥，本模块核心价值）

- 风险单 → 一键生成整改工单：选工单类型 + **字段预填**（风险编号/级别/涉及系统/描述——复用 phase5 S1 的模板预填与字段 schema 能力）。**模板静态预填实态对账（代码核实 2026-10-26，前端会话）**：后端闭环（`template_code` → 描述/自定义数据/优先级三位预填，取舍=请求显式值>模板默认>类型缺省；模板类型不匹配报错、不存在静默跳过——`ticket/service.go` Create），两处缺口随 R3 补齐——①**前端发起页未接模板选择**（`template_code` 前端零消费；缺口件=发起页按当前类型列可选模板+选中预填，静态预填的前端消费先于 R3 亦可独立小批）；②模板 `default_sla_minutes` **未入 Create 预填链**（全仓仅 CRUD 存取、无运行时消费——启动批核对：补消费或删字段，不留死配置）。**映射档位**：单张生成第一档 = risk service 组装 Create 入参的**域内固定映射**（六组骨架字段位直取，无可配置面）；映射可配置（用户调整字段对应关系）= 二档触发驱动
- **编辑时预填 auto_fill（2026-10-16 所有者场景登记，与 phase5 S1 对表）**：字段预填的第二档语义——发起/编辑工单时按已填字段实时带出并**支持人工二次修改**（区别于 formula 强制计算：建议预填 vs SSOT 覆盖）。场景：风险事件主机 IP 自动带入工单系统 IP 字段 → 按 IP 查 **CMDB** 带出责任人同样预填可改（CMDB = phase5 S1 `DataFetcher` 数据源白名单的首个企业外部源实例）。元数据承载于字段 schema `field_options`（与 formula 同列，执行时机双态预留——phase5 S1 随 formula 批预留、实现触发驱动），详录 [phase5/01 号 §3.3③](../phase5/01-s1-form-designer.md)。**（2026-10-22 同步：承载已定 `field_meta` JSONB 列（迁移 000051 已实落——原文 field_options 系 A.2 方案 b 采纳前旧值）；全链设计已定稿 = [01 号 §3.3③⁺](../phase5/01-s1-form-designer.md)（params 多参绑定/一查多填/编辑时预填交互/三档错误 UX/链式限深）；**R3 前置待建四件** = prefill 端点 / params 泛化 / external_http 通用适配器 / DataFetcher 超时·限流·审计（首版代码未落——接真实外部源前必须），~3–4 天，phase6 立项批计入——11 号 §1 已登记）**。**配置面缺口（2026-10-26 前端会话核实）**：字段设计器现无 fetch/映射编辑 UI（前端 `field_meta` 零配置入口——后端取数链已通但无维护面）——配置第一档走 schema JSON（API 维护），交互式编辑器随 R3 立项批评估计入
- **批量下发（2026-10-16 所有者场景登记，启动批细化）**：从风险事件集合批量下发整改工单，**字段可能不全**——形态 = **向导三步 + 部分成功 + 行级报告**（业界锚点：Jira CSV Import / Salesforce Data Loader / ServiceNow Import Set——校验与下发分离、部分成功为常态）：① 选风险事件集合 → ② 字段映射预览（auto_fill 带出结果逐行显示、缺失行高亮）→ ③ 下发策略：**完整行建单，不完整行不建单**、留风险侧标"未下发"可修正重发（零工单状态机改动）；**草稿态留二档**（业务强要求"每张风险单必有对应工单"时再加工单 draft 态——动 S3 状态机域，默认不做）。依赖：S1 auto_fill 预填 / S6 通知（下发完成通知）。**映射载体与 B-20 同族注记（2026-10-26 对账补全，前端会话）**：向导②的「字段映射」= **源单据字段→工单字段**的单据级映射，与 datafetcher 字段级 fetch 映射（数据源键→字段，`field_meta.fetch`）是两层——第一档直接复用上行固定映射的预览（逐行显示将带出什么、缺失高亮），映射可选=二档；与 spawn_task `from:ticket.field` 入参映射（B-20，§7 尾款随行）同属「源单据字段→目标入参」语义——B-20 先交付则 R3 复用其求值形态，反之 R3 先落则 B-20 对齐 R3；启动批圈范围时两件合并设计映射语义，不各造一套
- **工单终态 → 风险单联动关闭**：机制与 S6 触发层同款拍板（显式 emit 推荐 vs 事件消费面）——**拍板须按"共享事件面"决策（2026-10-08 复核补充）**：S6（通知）与本模块（风险关闭）是同一机制的两个消费方，若选 emit 应做成**可订阅内部钩子**（一次状态变更、多订阅者），禁止把风险关闭逻辑硬编码进 ticket service 状态变更路径（risk 域焊进 ticket 域=破坏领域隔离，ticket 为未来拆分而隔离）；◆**复核态可选**（业界惯例：处置完成后由 owner 验证再关，自动直关为默认可配——尊重所有者"自动关闭"诉求，复核为开关）。**跨域一致性兜底（2026-10-09 隐藏需求核查补遗）**：emit 钩子=进程内 at-most-once，钩子前崩溃事件即丢——通知丢失无害（可补发），**风险单关闭联动丢失=工单已终态而风险单永远"整改中"**，无检测手段即永久不一致；R3 随批补"终态对账扫描"（cron 扫已终态工单关联的未关风险单 → 告警或自动关，骑既有 cron 设施；观测面依赖 phase5 S10 cron 可观测随行件）。
- 工单指派/超期/状态变化 → S6 模板通知（风险 owner + 工单处理人）——**外发渠道依赖诚实注记（2026-10-27 三方对标批）**：当前仅站内收件箱真落码（UIP=桩、邮件/IM 零落码、webhook 未入 S6 规则面），UIP 真实接线前超期/指派提醒仅站内可达；webhook 出站 adapter 形态登记于 [06 号](06-ticket-completeness.md) 件 10；**解法在途（2026-10-27 债台账 H 组立项）**：H-2「通用渠道接口 + 钉钉首发 adapter」承担个人 IM 到达，件 10 定位随之收窄为「工单事件→外部系统」
- 工单与风险单双向可见：工单详情挂风险来源链接，风险单详情列整改工单。**工单侧承载启动批拍（2026-10-26 对账补全，前端会话）**：风险侧=R1 归属组「关联工单 ID」字段位（已定）；工单侧现无风险来源锚点——`TicketRelation` 为 ticket↔ticket 双 int64 + `relation_type` 字符串（`model/ticket.go`），三候选：①关系表混载（rel_type='risk'、一端存风险 ID——跨实体弱关联无外键，与 R1 镜像表同哲学）②custom_data 约定字段（如 `risk_no`）+ 台账反查端点（零 schema 改动、查询侧成本）③ticket 主表加 risk_source_id 列（最直白、动工单主表）——不拍则工单详情挂不了风险链接（双向可见缺一半）；**与上行「终态对账扫描」共用同一关联锚点，须同批定**
