## 1. 先用本地账号，再接公司统一身份平台

**本地核心正式版（B4）。** 首次获准进入目标内网后，完成 B0、实际启用范围的真实服务验证、获批业务试用和目标运行门，方可用本地工号和密码正式启用。工作人员登录后从风险记录开工单，按权限办理，查看任务、清单更新和消息结果。三层权限分别检查功能、记录和本次动作。首版提供相应页面、历史、审计和失败恢复。 [首发与滚动更新安排](../planning/intranet-uaa-release-schedule.md#内网首发要到哪一阶段)

**UAA 仅统一登录。** 本地版稳定后，若公司允许应用只接认证，可以独立试点。员工由公司 UAA 登录，本地管理员继续管理角色、菜单和实际访问范围。已有本地用户 ID 和业务记录沿用。 [仅 SSO 分工与验收](../planning/uaa-sso-local-authorization-plan.md)

**UAA 纳管正式版（B5）。** 本地版稳定后，公司统一身份和权限平台接管获准范围。除员工登录，还需同步账号、员工被授予的角色、角色获准的资源，并处理目录、条件范围和回传。要实际验证撤权、故障时的处理和退出办法，获得接管批准后才能切换。

首发前保留长期 UAA 兼容接缝，包括跨服务主体与稳定资源标识、账号及授权数据的写主、公开接口版本和兼容回归。完整 UAA 双模式产品、企业登录、同步与治理页面，以及这套产品的完整 mock 均排在本地核心稳定之后。真实协议、身份和权限治理由公司单独批准后接入。企业专用 SDK、字段及凭据由独立对接程序在内网管理。

## 2. 必交业务与支持范围

**人工流程优先在外部隔离验收（B2）。** 同一漏洞影响同一责任人名下的两台资产。风险管理者派一张单，办理人逐台交证据，负责人逐台复测。责任人不同或漏洞不同则分别开单。首入内网后，经 Q12 批准的真实试用只办理按指定整改类型新建的工单。升级前已经存在的工单用隔离环境的合成样本验证。 [人工试用开工计划](../planning/phase6-b2-kickoff-plan.md#旧票范围与定向验收)

**下面列的是本地正式版的代表业务。** 首次准入前的完整清单覆盖 Phase 6 已确认纳入本期的全部工作，包括原定前端页面和浏览器验收、业务功能与扩展改造、离线制品、恢复和演练；逐项以主排程和相应验收合同为准。代表业务从登录、风险录入或接收、定级与指定责任开始。工单办理时可发起获准任务，结果更新到指定清单；清单变化后再触发一项获准的任务，首条后继使用只读复核。办理人能在原工单看到消息和结果，风险负责人核验证据。验收要核对后继任务实际创建并执行。 [本期范围与排程](../planning/intranet-uaa-release-schedule.md#3-全部-phase-6-目标与先后)

- 风险管理者能查看列表和详情、评估风险、指定负责人和期限，再按权限派单。漏洞整改按[漏洞和资产责任人](risk-module-detail.md#漏洞按责任人派单)派单。符合通用分组条件的其他风险也可派到一张工单，证据和复测结果按项保存。需要接受风险时走审批。风险发现和专业研判使用外部工具提供的结果。
- 工单可创建、分派、办理、提交证据、评论和复核。列表支持给有限数量的工单批量加标签，逐张检查权限，显示哪些没加上。新工单类型各自设定谁能查看。抄送人可以查看和评论，办理权限另行检查。每张工单只设一位主责任人。
- **任务服务（Taskrunner）。** 记录哪次操作、哪一步工单发起了哪个任务，保存任务的固定输入和结果。任务服务接单后，页面显示当前状态和结果；结果不明时先查原任务。业务已经完成、只差原工单显示结果时，补上结果显示即可。
- **动态清单（ActiveList）与消息。** 更新前检查当前程序能改哪些行和字段、数据有没有被他人改过。清单保存变更，核心服务记录收到的事件后再触发获准任务。请求签名用来确认服务身份，仍需检查能否执行这项业务。消息首版复用模板和发送规则，验证已受理、已送达、失败或待核实。首次进内网前用模拟渠道验收，现场验收时接通一条实际公司 HTTP 渠道。
- **办理页面与记录。** 验收本期原定前端范围所列页面及浏览器操作，以及重要时间与操作记录、去除敏感信息的日志和故障恢复。

先选一个整改流程、少量真实任务动作、一种清单结构及字段、一个清单变化触发规则和一条 HTTP 渠道。候选做法是固定字段与流程，首批暂不开公式或监控类型上的导入、整批替换。服务端要明确拒绝暂不开放的操作，已有其它类型继续可用。先验证工作人员能完成实际日常任务，若缺必需功能，再具体定义并重估。

已明确留到后续的事项沿其排期交付，包括 AI 能力、检索增强生成（RAG）、技能（skill）和 MCP 的产品化。具体功能以主排程确认的范围为准，本页列举的代表业务不改变各工作包的归属或验收义务。

### 4.1 B0预演与真实业务试用准入

首次进入、B0 目标环境合成预演、真实服务联调、真实业务试用和正式启用按各自范围取证。接真实业务身份和数据或开放业务操作前，实施方出具当前候选的 P1 处置表。`AUTH-01/02/07` 在所选范围内须有修复与反例证据，或有服务端关闭与全部可达入口拒绝证据。`AUTH-07` 涵盖组织管理同源粗门及 `BindOrgRole`。`AUTH-02` 涵盖提交、计划、触发、重试及最终执行。保留其它独立合法来源及受权业务功能，核对关闭能力的内部调用和 worker 入口也被拒绝。 [基础版边界](../design/foundation-release-boundaries.md#1-先交哪一版) · [第一批 IAM](iam-first-batch-design.md)

### 4.2 核心稳定的过渡出口

实施方以当前启用画像给出下列最小证据，业务所有者确认代表任务可用和反馈处置后，才能把主研发产能转入完整UAA-P/R：

- 本地三层权限下，风险维护者、普通工单办理者、受权复核者等代表角色完成§2的必交旅程；详情/列表/统计及受限字段同范围，越权有拒绝证据。
- 实际启用范围无未处置的P1、越权或数据损坏路径；尚未实现的能力明确关闭，已知限制有用途/责任/后继窗口，不以接受风险替代权限及数据正确性门。
- 重复提交、重启、撤权、冲突和未知效果有正常/拒绝/恢复证据；所选真实HTTP消息与本地正式制品、备份恢复/回退按适用门验收，mock不代替真实回执。
- 已完成一轮覆盖代表业务任务的试用反馈闭环：记录问题、修正及回归，剩余不阻塞事项有责任与排期。观察安排按真实使用画像确定，不预定“一周无故障”或任意性能/可用率数值。

这组判据是工程验收候选，不宣称现在产品已稳定。具体试用范围/用户与反馈接受由所有者确认，测试预期、故障注入和证据充分性由实施方负责；超出已价范围的新增工作先扣重补估。稳定后仍保留本地核心支持与回归产能，不能把同一席位全部投入UAA后无人维护；UAA资料联系不必等待此出口。

## 5. 真实业务后续接管与下一步

本地正式运行后，用户ID、风险/工单归属、附件/审计历史、receipt、未完成intent和在途任务均须保留，不能沿用“当前测试数据可重建”。认证subject与治理subject分开映射；工号/邮箱只作受审线索，不自动并号或删号重建。

UAA接管先做影子匹配和授权差异，批准映射/范围后切单一写主，收敛旧直接/组织/继承grant并核会话/待执行任务；同名admin不授系统权限。退出仍须批准有效本地基线，不恢复旧grant。中央角色/菜单不替代L2资源与L3动作检查。

首次本地正式消费者即登记合同并保护兼容；不等UAA后再保护。核心自带迁移，在承诺合同内用旧参考adapter验新核心，私有代码不跟内部表重构耦合。

B4 正式启用后，后续获准的更新沿用版本与接口合同。内网按批准的固定制品更新，保留业务数据、在途任务、审计、私有配置和凭据。每批按实际变更演练迁移与回退，核旧消费者与三模块联动。 [更新安排](../planning/intranet-uaa-release-schedule.md#b4-后怎么更新内网)

按主排程与模块交接推进本地权限、共用接口、风险和工单，再接任务、活动列表与消息。外部用合成样本和 mock 验收，现场的真实流程、字段、动作、订阅、消息合同、部署资源和执行人员在目标内网绑定。UAA 真实条件后续单列。F017 已确认两项 IAM 高风险写在本地审计失败时回滚，以及外送失败时补送，交付状态见项目控制台。 [模块交接](module-design-handoff.md) · [项目控制台 §6](../review/11-project-control.md#6-当前健康状态遗留问题追踪)

上述绑定沿现有 Q12、Q09 和 MH01/MR1 执行。真实窗口未确定时，记录待确认条件、受影响的验收点和责任角色，由责任人在对应放行前处理。
