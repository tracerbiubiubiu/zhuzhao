# 03 — P6-R3 处置联动：与工单/通知的桥（设计稿）

> **文档定位**：段级设计稿（2026-10-26 建档）——[README](README.md) §2 R3 段 + 并行前端会话实态对账整合展开；**登记级设计稿，启动批细化**。总纲与拍板状态 = [README](README.md)。本段 = 风险闭环的执行桥（R3 是本模块核心价值段）。
> **量级**：1–2 周 + 前置四件 3–4 天（Week 0 先行）。**迁移**：风险↔工单关联锚点随拍板点 1 定形态，编号启动对账。

## 1. 定位与一句话

风险单 → 整改工单的**生成、预填、批量下发、终态联动关闭、双向可见**五件桥接能力；全部复用工单模块既有面（S1 字段/模板、S3a 引擎、S6 通知），risk 域不碰工单状态机（领域隔离红线——ticket 为未来拆分而隔离）。

## 2. 现状基线（代码级锚点，2026-10-26 前端会话核实）

- **模板静态预填后端已闭环**：`template_code` → 描述/自定义数据/优先级三位预填（取舍 = 请求显式值 > 模板默认 > 类型缺省；模板类型不匹配报错、不存在静默跳过——`ticket/service.go` Create）。
- **两缺口**：①前端发起页未接模板选择（`template_code` 前端零消费）；②`default_sla_minutes` 未入 Create 预填链（全仓仅 CRUD 存取、无运行时消费——**◆启动拍板 4**：补消费或删字段，不留死配置）。
- **TicketRelation 现状**：ticket↔ticket 双 int64 + `relation_type` 字符串——**无跨实体（工单↔风险）锚点**。
- **字段设计器无 fetch/映射编辑 UI**：后端取数链已通（DataFetcher Registry，装配为空注册）但前端 `field_meta` 零配置入口。

## 3. 范围条目

### 3.1 一键生成整改工单

- 选工单类型 + 字段预填（风险编号/级别/涉及系统/描述——复用 S1 模板预填与字段 schema 能力）。
- **映射档位**：单张生成第一档 = risk service 组装 Create 入参的**域内固定映射**（六组骨架字段位直取，无可配置面）；映射可配置（用户调整字段对应关系）= 二档触发驱动。
- §2 两缺口随本段补齐（模板选择前端消费可先于本段独立小批）。

### 3.2 编辑时预填 auto_fill（前置四件 = Week 0）

- 发起/编辑工单按已填字段**实时带出、支持人工二次修改**（区别 formula 强制计算：建议预填 vs SSOT 覆盖）；场景：风险事件主机 IP 自动带入工单 IP 字段 → 按 IP 查资产带出责任人同样预填可改（资产 = `DataFetcher` 白名单的首个企业外部源实例）。
- **R3 前置待建四件**（Week 0 排位）：prefill 端点 / params 泛化 / external_http 通用适配器 / DataFetcher 超时·限流·审计——全链设计定稿 = [phase5/01 号 §3.3③⁺](../phase5/01-s1-form-designer.md)（params 多参绑定/一查多填/编辑时预填交互/三档错误 UX/链式限深）。
- 配置面第一档走 schema JSON（API 维护），交互式编辑器随本段评估计入。

### 3.3 批量下发

- **向导三步 + 部分成功 + 行级报告**（业界锚点：Jira CSV Import / Salesforce Data Loader / ServiceNow Import Set——校验与下发分离、部分成功为常态）：① 选风险事件集合 → ② 字段映射预览（auto_fill 带出结果逐行显示、缺失行高亮）→ ③ 下发策略：完整行建单、不完整行留风险侧标"未下发"可修正重发（零工单状态机改动）；草稿态留二档默认不做。
- **映射两层注记**：向导②「字段映射」= 源单据字段→工单字段的**单据级映射**，≠ datafetcher 字段级 fetch（数据源键→字段）——第一档直接复用固定映射的预览；与 B-20 spawn_task `from:ticket.field` 同属「源单据字段→目标入参」语义，**◆启动拍板 2：与 B-20 合并设计映射语义，不各造一套**（依赖序见 [00 号 §4](00-flow-engine-v2.md)）。

### 3.4 工单终态 → 风险单联动关闭

- **共享事件面**（与 S6 同款拍板）：可订阅内部钩子（一次状态变更、多订阅者），**禁止把风险关闭逻辑硬编码进 ticket service 状态变更路径**；◆复核态可选（默认自动直关，owner 验证复核为开关）。
- **跨域一致性兜底**：emit 钩子 = 进程内 at-most-once，钩子前崩溃事件即丢——通知丢失无害（可补发），**关闭联动丢失 = 工单已终态而风险单永远"整改中"** → **终态对账扫描**（cron 扫已终态工单关联的未关风险单 → 告警或自动关，骑既有 cron 设施；观测面依赖 S10 cron 可观测随行件）。

### 3.5 工单与风险单双向可见

- 风险侧 = R1 归属组「关联工单 ID」字段位（已定）；**工单侧现无风险来源锚点——◆启动拍板 1：三候选**：
  ① `TicketRelation` 混载（`rel_type='risk'`、一端存风险 ID——跨实体弱关联无外键，与 R1 镜像表同哲学）；
  ② custom_data 约定字段（如 `risk_no`）+ 台账反查端点（零 schema 改动、查询侧成本）；
  ③ ticket 主表加 `risk_source_id` 列（最直白、动工单主表）。
- **与终态对账扫描共用同一关联锚点，须同批定**。

### 3.6 通知

工单指派/超期/状态变化 → S6 模板通知（风险 owner + 工单处理人）——S6 触发面域无关既定，零新通知代码。

## 4. 启动拍板点

1. 工单侧风险来源锚点三候选（§3.5，与对账扫描同批定）。
2. 映射语义与 B-20 合并设计（§3.3）。
3. 风险「级别↔工单 priority」枚举映射（dd §29 残留开放项）。
4. `default_sla_minutes` 补消费或删字段（§2）。

## 5. 边界（不做）

风险流程配置化；工单 draft 态（业务强要求"每张风险单必有对应工单"时再议——动 S3 状态机域）；资产解析步实做（D29——phase6 内降级 `asset_ref=null`+未解析标记，门面归 phase7 前置批）；规则化自动建单（理想态①——等 S3a 动作库演进时与 D20「不建新机制」对表）。

## 7. 验收口径（能力语言）

风险单一键生成工单且六组骨架字段正确落位；批量下发部分成功时行级报告可查、未下发行可修正重发且零工单状态机改动；工单关闭后风险单自动联动关闭（或进复核），对账扫描可兜底单边漂移（人工制造单边状态可被扫出）；工单详情与风险详情互相可达；auto_fill 带出结果人工可改、取数失败有三档错误 UX 不阻塞提交。
