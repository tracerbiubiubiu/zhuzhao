## 1. zhuzhao 是什么

### 1.0 平台定位声明（2026-11-03 所有者定界——本节为全平台边界权威句）

> **一句话：专业工具负责发现与执行；本平台负责汇聚结论、管理安全流程全生命周期、调度能力、留存证据。**

边界三句（= 数据汇聚中心 + 安全能力中心 + 流程生命周期管理）与三个内沿精化：

1. **数据汇聚中心**——汇聚**结论级**数据（findings/告警归一化，D5）+ 有界原始快照（F2 回放窗口）；**不做原始数据湖/全量日志存储**（防静默滑向二流 SIEM——本边界最易滑坡处）。
2. **安全能力中心**——做**编排与胶水**（连接器触发专业工具执行 + 自建胶水脚本：富化/巡检/格式转换）；**不自建专业执行器**（封禁/查毒/取证发给防火墙/EDR/取证平台——F24「只做权威清单源不自建执行器」升级为能力域通则）。
3. **流程生命周期管理**——**安全域流程主权归本平台**（§29 翻案背书：内部 ITSM 二开对接成本高）；他域流程（IT 变更/运维）通过对接协作、不吞并。

**生命线注**：本边界的成败不在内部功能数量，在接口——数据进得来（接入归一化）× 动作出得去（Action 统一抽象）× 证据留得住（审计/时间线）。接口质量 > 内部功能数量（roadmap phase7→8→9 排序逻辑即此）。

**性质说明**：本声明是**收拢非新拍板**——三个内沿分别对应 D4/D5（资产纯查询/结论级汇聚）、F24 哲学/不做清单（不自建执行器）、§29 翻案（流程主权）；国内 SIEM/态势感知平台（天眼/ISOP/SIP 类）与此正交（他们提供专业发现/分析，本平台连接其结论与本地安全生命周期；专业执行仍由对应工具负责）——对外解释定位时用此一句。

> **⚠ 边界外已登记场景（2026-09-01，未立项，触发条件驱动）——外部供应商协作**：实际业务中内部员工与外部供应商协同，需求两档：① 供应商**提交并查看自己的工单**（requester 模式）——现状已可凑合（local 账号 + L1 建单权限 + 属主豁免可见性）；② **内部工单选择性共享给供应商**（原登记时仅有专属虚拟组 + `expires_at` + ticket_scope=group 的组级做法；后续 S10 已增加单张工单手动抄送可见性，但这不等于供应商身份、外部协作隔离与授权策略已经交付）。配套缺口：users 无外部账号类型（source 仅 hr/local，供应商与员工同构、可被 org_roles/继承 BFS 误赋全局角色）、组织树无专用供应商形态（当前以 `is_virtual` 区分实体/虚拟，原 `org_type` 枚举已退役）。候选演进：外部账号类型 + 供应商组织形态（隔离于 HR 同步域）+ 组级 shared 可见性（业界主流：Zendesk shared organization / JSM customer portal）→ 工单级共享列远期；人员变动策略（合作结束 = expires_at 到期 + 禁用，名下工单随离职处置策略一并拍板，见 hr-directory-sync.md §3.2 待设计）。**触发条件 = 真实供应商接入诉求；启动时先改本文档立项，再级联设计。**

> **⚠ 边界外已登记场景（2026-09-01，未立项，触发条件驱动）——工单类型级创建授权**：现状 L1 `ticket:create` 为布尔开关，创建时传任意 `type_code` 仅校验存在 + is_active（`internal/service/ticket/service.go` 的 `Create`），**无「谁能创建哪些类型」控制**；读侧类型维度亦无可见性过滤（模板 org_path 仅预填辅助、不构成授权）。业界两派：类型自带授权（ServiceNow user criteria 派）vs 分组域圈类型（Jira 项目派）。候选演进（最小实现，ServiceNow 派）：`ticket_types` 加授权约束列（如 `create_roles`/`visible_org_paths`，空=全员可用保持兼容）+ Create 校验 + 类型列表按身份过滤；分组域派（服务目录/项目概念）对当前体量偏重不推荐。**触发条件 = 出现按角色/人群限定可提工单类型的真实诉求。**

## 2. MVP 边界铁律（裁决微观决策的依据）

**以下是 2026-08 的 Phase 2a 分期裁决，保留阶段归属，不表示现今仍未交付事件/通知。Phase 2a = 最小可交付的工单闭环**：能创建、查看、编辑、关闭一张工单，且权限正确。判定一条能力是否属于 2a 的唯一标准：

> **凡依赖 2c Authorize、事件机制（Asynq / L1）、或审批流引擎的，一律 defer 到 Phase 3；纯 DB、无事件依赖的，可纳入 2a。**

应用示例（避免再次横跳）：
- ✅ **工单模板 / 工单关联** → 纯 DB、无事件依赖 → **属 2a**（迁移 000015 / 000016）。
- ❌ SLA 违约计算、站内/邮件通知、审批流、自动分派 → 依赖事件/审批引擎 → **属 Phase 3**。

## 4. 文档真相源与修改纪律（防"乱"的核心）

真相只有三层，细节文档必须与之自洽：

1. **roadmap.md** = 执行视图（什么阶段做什么、现状）。
2. **design-decisions.md** = 决策日志（为什么，带日期，旧决策保留不删）。
3. **代码 / migrations/** = 真实落地（现状以磁盘 `migrations/` 为准；截至 2a 收口已落地 000010 / 000015 / 000016，后续编号见 [review/11 §4 迁移地图](review/11-project-control.md)——phase2/README §2.4 已于 2026-10-12 退役逐号维护）。

修改纪律（任何范围/阶段调整都按此顺序，缺一不可）：
1. 在 `design-decisions.md` **追加**一条（日期 + 旧→新 + 理由），不删旧。
2. 同步 `roadmap.md`。
3. 级联到 `modules/*`、`phase3/*` 等细节文档。
4. **禁止只改一处**——这是此前文档互相打架的唯一根因。
