### 5.10 异步与消息一致性总口径（2026-10-16 所有者问询"phase5 有没有 MQ/asynq 确保消息不丢"）

**结论：phase5 不引入消息队列——MQ 不引，asynq 也不进 zhuzhao 主仓**（队列职责归 taskrunner，asynq 已在其位）。不丢的保障不靠统一队列，靠**按业务一致性分级**：

| 特性 | 异步面 | 不丢机制 | 丢失窗口与定性 |
|------|--------|---------|--------------|
| S5 GC/备份 | 进程内 cron（advisory lock+ReentrantJob）/rclone mirror（S5 备份——2026-10-16 存储后端拍定 RustFS 后由 mc mirror 改 rclone，镜像已拉） | 幂等扫描可重跑（慢≠丢）；备份 RPO 显式登记 | 无丢失概念（周期任务） |
| **S6 通知发送** | DomainEvent 钩子 at-most-once（事务提交后派发）+ goroutine | `message_log` 落行可追溯 + 死信告警链（P4-2 既有） | 派发后进程崩溃=丢一条通知——**接受**（通知无状态可补发，低一致性分级） |
| S10 超时扫描/角标 | cron 扫描 | 幂等重扫 + cron 可观测面（上次成功/失败告警——§3.4 随行件，防静默失败） | 迟发≠丢 |
| S9 缓存代理 | 同步调用 + TTL 懒过期回源 | singleflight 防击穿 + 上游令牌桶自留量（09 号附录 A.3） | 上游全挂/配额耗尽 → 返回陈旧缓存（`stale=true` 标注，拍板点 1）——旧情报可接受、**不静默报错** |
| 任务执行 | **taskrunner asynq**（独立服务既有） | 重试/死信/归档全套既有 | 架构分工：执行队列归 taskrunner，zhuzhao 是编排方 |
| phase6 R3 关单（未来高一致性消费者） | 同一 DomainEvent 钩子 | **不靠队列靠对账**：终态对账扫描周期补偿（phase6 R3 设计项） | 钩子丢失由对账兜底（最终一致） |

**为什么 asynq 不进主仓**：①唯一的异步通知面可接受丢失（补发无害）；②需要队列的场景（任务执行）已是独立服务 taskrunner 的职责，主仓再起 asynq = 双队列基础设施+双监控面，无场景支撑（与「微服务不拆」同源）。

**升级路径（现成、结构同构、业务代码零改）**：DomainEvent 与 phase3/10 §7 L1 事件设计同构——若「事件绝不丢」成为硬约束，升级 = `Dispatch` 改「同事务写 outbox + asynq/轮询投递」（dd §16 Outbox+Asynq 既定路线）。**触发信号**：①通知必达成合规硬要求；②高一致性跨域消费者增多且对账补偿不足；③多副本部署后钩子扇出成瓶颈。

**Kafka 评估（2026-10-16 所有者问询"需不需要引入 Kafka、变化大吗"——结论：不引入，维持分级方案）**：
- **量级错配**：Kafka 设计目标=每秒百万级流分发/跨系统日志流；本平台事件量=每天数千~数万条状态变更——四个数量级错配，用 Kafka 运通知=用货运列车送快递；
- **运维成本**：broker 集群（生产≥3 节点）/KRaft/分区与消费组管理/监控/升级——单人内网平台不可承受（与「微服务不拆·PG 单栈」纪律同源）；
- **业界关键事实（Confluent 官方课程/社区共识核验）**：**Kafka 本身不解决「消息不丢」**——双写问题（DB 事务成功+发 Kafka 失败=丢）依然存在，业界标准答案恰是 **transactional outbox**（业务数据与事件同事务落库+投递器轮询），而 **outbox 不需要 Kafka**（PG 内一张表+轮询即完整实现，Go 生态候选 river=PG job queue）；
- **变化量对比**：不动=0；→ outbox（「通知必达」出现时第一步）= 一张 domain_events 表 + Dispatch 改造为投递器轮询，**DomainHook 消费方零改，1–2 天**；→ Kafka = 新中间件集群 + producer/consumer group/schema/幂等消费/DLQ 自建 + 本地开发环境改造，**周级+长期运维**，且**仍需配套 outbox**（双写问题不因 Kafka 消失）；
- **Kafka 的真实门槛**（出现才立项评估）：跨系统流分发 / 多团队多服务解耦消费 / 高吞吐流（日志·埋点·事件溯源）/ 削峰填谷——本平台当前一条不占（业界参照：GitLab 业务事件走 Redis+Sidekiq 而非 Kafka）。

**业界对表结论（2026-10-16 核验——modular monolith 事件口径业界基准：进程内钩子=单体原子副作用首选 / outbox=投递需跨崩溃或跨进程边界时 / 通知类业界默认=at-least-once+消费方幂等[丢通知通常比重复通知代价高]）**：

- **符合项（5/8）**：①事务提交后派发（业界明确不建议 handler 进事务——handler 失败会污染业务状态，我们天然隔离）；②单体进程内事件（modular monolith 共识）；③DLQ+告警（message_log+死信链=小规模 DLQ 同构）；④扫描幂等+cron 可观测（job monitoring 标准）；⑤高一致性靠对账补偿（reconciliation 模式=支付/账务系统同款，回避分布式事务的标准做法）；任务队列 asynq=Go 生态事实标准。
- **有意偏差（1 项，已文档化+升级路径现成）**：业界对**通知类**的默认档=at-least-once+消费方幂等（丢通知代价>重复通知）；我们选 at-most-once（升级路径=outbox，1–2 天）。辩护=内网量小/丢失=用户困扰非数据损失/DevHook 结构同构；但须承认**这是低于业界默认档的一档**，非同等替代。
- **后置配套（2 项，升级时的已知成本，提前登记）**：①消费方幂等键——升级 at-least-once 的前置条件（outbox 重试必然产生重复投递）；②事件 Payload 版本化——多消费者演进后字段演进需版本纪律（现 Payload 透传单消费方阶段不急）。
- **零成本补强（本批采纳）**：通知丢失的**可审计性**——`ticket_events` 本身就是状态变更事实源，cron 对账「应有通知 vs message_log 实发」即可把 at-most-once 从「静默丢」变「可审计的丢」（发现缺失可人工补发；不做自动补发不加队列，量级≈半天，随 S10 cron 可观测面同批）。
