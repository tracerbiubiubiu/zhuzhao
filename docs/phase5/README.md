# phase5/ — Phase 5 规划：前端可视化配置与通用能力底座（规划草案）

> **定位校准（2026-10-08）**：本 phase 以"前端可视化配置线"立项，随 S5–S9 底座/能力段陆续归入，实际定位已扩展为**通用能力与产品化底座线**（所有者口径：**phase5 = 通用能力，phase6 = 真正的业务能力**）。
>
> **文档定位**：Phase 5 唯一规划文档（草案）。**状态 = 未排期、未启动**：批次划分/编号分配/量级细化待启动拍板（届时在本目录另立 02 号式实施计划）。本文件先落**目标形态、范围边界、前置触发**——与 `phase3/*` 同款纪律：设计就绪稿，非交付承诺。
>
> **立项由来**（2026-10-08 所有者指示，决策登记 = [design-decisions §27](../design/design-decisions.md)）：工单域配置面现状是"数据可配、界面兜底"——类型/字段/模板管理页已交付，但 states/transitions 走 JSON 源码模式、字段走表格全量替换（phase4/02 深水区降级决策的兜底形态）。所有者期望：**前端表单与运行流程都能在前端自定义配置**。同日追加指示：**taskrunner 任务面（cron/params/action 输入全手填）同步纳入本 phase 人性化演进（S4）**；**头像改图片上传（现 URL 手填）、工单字段支持富文本与图片/文档上传——MinIO 对象存储纳入本 phase 作公共底座（S5，IW2/10 号存储设计收编实施）**。P4 收口后触发项盘点（同日）：**通知渠道配置页（P4-2 本体已交付、页面"触发驱动后补"）收编进 S4**；字典/验证码/导出/PAT 经核实已随 P4 交付，不重复立项。同日第四轮：**消息通知模块立项（S6）**——对接企业统一消息平台（全渠道单接口）+ 消息模板（内容/人员参数化）+ 工单字段作参数渲染；**S4 的通知渠道配置页迁入 S6**（通知中心页面族归一段），S4 回归 taskrunner 任务面。同日第五轮：**AI 助手（S7，概要登记——形态未定，暂定参考 fastclaw 的平台内对话；长线 = AI 参与协助业务，示例场景 = 协助风险员工定性分析风险事件/关联资产/找责任人/自动下发工单）与数据大屏（S8，🚦 后置——当前数据量少，触发驱动）**。同日第六轮：**威胁情报缓存代理（S9，概要登记）**——对已有威胁情报 web 应用做能力补全（应用本体不动）：其每日/每小时查询配额受限，本段建缓存库（TTL 7/30 天双档），查询先缓存后回源；**定位 = 通用能力（外部限流 API 缓存代理，威胁情报是首个消费者），按"phase5=通用能力"口径归本 phase**；消费者 = phase6 风险模块 R1（情报源之一）。

## 0. 一句话

把工单域与任务域的"配置面"从手填/JSON 源码兜底升级为前端可视化，并补齐富媒体、消息通知、情报缓存与工单协作底座，十段递进：**表单可视化设计与字段自动化（S1）→ 流程状态图可视化设计（S2）→ 流程运行语义配置化（S3，🚦）→ 管理面配置人性化（S4：taskrunner 任务面）→ 对象存储底座与富媒体（S5，MinIO）→ 消息通知（S6：统一消息平台 + 模板 + 工单触发）→ AI 助手（S7，形态未定）→ 数据大屏（S8，🚦 后置）→ 威胁情报缓存代理（S9）→ 工单协作与提醒（S10：抄送/标签/角标/节点超时/导出）**。S2/S4 前端为主、存储契约零破坏；S1 前端为主 + 字段求值器小后端件；S5 为公共底座段（IW2 收编）；S6/S9/S10 后端为主（S6 = P4-2 通知通道的能力延伸；S9 = 外部限流 API 缓存代理通用件；S10 = 2026-10-09 场景差距分析产出）；S3 以工单自研翻案为硬前置；S8 触发驱动后置。

## 2. 范围：十段递进

### P5-S1 动态表单可视化设计器与字段自动化（前端为主 + 求值器后端件）

- **渲染器已在位，设计器选型有推荐项**：工单发起=自研七类型轻量渲染器（W4 交付；form-create 库引入决策顺延至设计器批，`views/ticket/create/index.vue` 头注释）——S1 启动首件 = 设计器选型拍板，**推荐自研设计器**（sortablejs 拖拽排序 + 属性面板，产物即 field schema 零映射；form-create designer 作半天 spike 对照——其 rules/options 组件树 JSON 与规范化 schema 不同构，引入需双向映射器+面板裁剪到七类型，高级布局能力用不上，模型税大于成熟度收益）。[12-frontend「阶段 2（远期可选）」](../phase3/12-frontend.md) 随本段转正。
- **后端存储不变**：产物仍是 `ticket_type_fields` 字段 schema；字段类型仍限七种（input/textarea/number/date/select/multi_select/tips）。
- **select/multi_select 选项引用 P4-3 字典**（已随 P4 交付，`/dicts` + `/dict-items` 各四端点已核）：设计器选项支持挂字典键而非死枚举，选项变更全系统生效。**人员/部门类字段自动补全（2026-10-09 场景补充）**：指派/抄送/参与人选人走既有用户搜索端点；M-HR 对接后（HRFetcher）组织人员数据入本地表，补全零额外对接——依赖 M-HR 触发，不阻塞本段。
- **字段自动计算/联动（2026-10-08 所有者场景补充）**：① **计算字段**——按已填字段公式自动算出派生字段，落点=字段 schema 扩展（field meta 增 formula）+ **服务端求值为 SSOT**（提交时后端算入 `custom_data`，前端仅预览展示——防篡改与现有哲学一致）；② **提交时条件取数回写**——按字段值判断后从数据源取数自动写入字段，落点=字段联动规则（数据层自动化，非流程层），取数走 `DataFetcher` 端口（按 source 类型注册 fetcher——见 §6 对接预留清单）。**求值器统一为白名单 Go 侧表达式求值器**（phase3/10 §4.2 既定路线；easy-workflow 表达式拼 SQL + 黑名单防注入为反面教材），字段公式（本段）与网关条件（S3）共用一件。**两个启动拍板点**：取数数据源白名单（内部资源/activelist/外部 HTTP——外部回到 §26.6 出站决策树）；取数身份（系统身份 vs 发起人代理——L2 可见性边界）。量级 +3–5 天（求值器为公共件）。
- 新字段类型 = 另立后端批：渲染器 + `validateFieldInputs`/G2 schema 校验同步扩，遵守"只增不改"兼容纪律，不混入 S1。
- 现 ticket/type 页表格模式保留为**专家模式/兜底**（phase4 深水区降级决策的形态直接复用）。

### P5-S2 流程状态图可视化设计器（纯前端为主）

- **采用现成拖拽画布组件，不自研画布**：候选 **LogicFlow / vue-flow**（均 MIT，推荐，启动批各 0.5 天同一 PoC spike——拖节点/连线/序列化回 transitions/回显——按映射成本+交互手感+包体拍板）；AntV X6 备选（能力过剩）；bpmn.js 排除（BPMN 2.0 标准模型与 transitions JSONB 不匹配且过重）。数据面：状态=节点、转换=边，与 `transitions` JSONB **天然同构**，映射器为浅层翻译。
- states/transitions 画布化：节点=状态、连线=合法转换，产物序列化回现有 transitions JSONB，**后端零改动**；中文化与交互打磨计入量级。
- **分层要求（2026-10-08 所有者问询后定）**：画布层（LogicFlow/vue-flow 封装+交互）与 schema 适配层（transitions 映射器）**分离**——任务域将来若立流程设计器可复用画布层、只换适配器；但**引擎与数据模型不合并**：工单流程=人触发的实体状态图，任务流程=完成事件驱动的执行编排，不同构——任务侧编排维持 16 号红线（不做通用流程引擎，轻编排走 zhuzhao 回调串联、重编排走外部 DAG [phase3/15](../phase3/15-script-platform-dagu-vs-inhouse.md) GPL 法务前置），不得为复用而把两者捏成一个"通用流程模块"。
- 可选校验增强批（纯增量、向后兼容）：`validateTypeGraph` 现只查端点在 states 内，可加 lint 级检查——终态可达性/孤立状态/无出边死锁告警（是否阻断保存待启动拍板）；**改图影响在途单告警（业界轻量实践，2026-10-08 对标 Jira 在途迁移后的取舍——迁移向导过重不取）**：保存图时扫描在途工单状态分布，存在将脱离新图的状态（改后 AssertTransition 恒拒=工单僵死）→ 告警确认，半天级。

### P5-S3 流程运行语义配置化（后端为主，🚦 双前置）

- 目标形态：转换级配置——**谁能触发哪个转换**（角色/属主/处理人）、转换前置条件、**自动分派规则**（[phase3/10](../phase3/10-ticket-business.md) `assignment_rules` 蓝本）、（远期）**审批节点**（phase3/10 BranchedStateEngine + `workflow_*` 蓝本）。**参考实现核验（2026-10-08）**：[easy-workflow](https://github.com/Bunny3th/easy-workflow)（MIT）——**phase3/10 §4.2 能力映射表的原始蓝本之一，本轮代码级核验为独立复核印证：§4.2 十二项借鉴点全部在参考实现中证实、四条避坑点（MySQL 绑定/表达式拼 SQL/反射事件/引擎内嵌身份）全部被其真实缺陷证实，无新增借鉴项**；不引库（零测试/无锁并发/改定义即在途漂移）。
- **流转时自动动作/自定义功能性节点（2026-10-08 所有者场景补充）**："按字段判断分支后取数回写工单"若发生在**流转时**（进入某状态触发），落点=S3 **转换后动作**（Post-function 形态）——实现形态=节点 meta + 显式 TicketHooks 钩子（phase3/10 §4.2 既定，编译期检查），**引擎不内置功能节点类型**（节点类型膨胀=easy-workflow 反面；功能外挂与 Jira post-functions 同构）；表达式求值与 S1 共用同一白名单求值器。提交时机的同款诉求归 S1 字段联动（见 S1 段），勿混入流程层。**动作库类型（2026-10-09 场景补充）**：取数回写 / 消息通知（S6）/ 抄送（S10）/ **提交任务**（工单到达某节点/审批通过后自动起 taskrunner 任务——走既有 Submit 通道，理想态登记）。🚦 前置不变。
- 硬前置：① [design-decisions §23](../design/design-decisions.md) 工单自研翻案条件成立（phase3/10 设计可整体复用为蓝本）；② S1/S2 收口。
- **架构约束**（不可绕）：
  - 权限判定必须落策略层——类型级策略数据 + fail-closed，经既有三层鉴权/Registry 形态接入；**禁止业务层手写绕过**（AGENTS 约定；§25 平台策略库"事实在 DB/语义在代码"的分界随翻案批重审）。
  - 迁移编号按启动时 11 号 §4 迁移地图对账占用（A2 规则：撞号让位重排）。

### P5-S4 管理面配置人性化（taskrunner 任务面）

- 现状痛点（task_center 四 Tab 已交付、输入全手填）与对策：
  - **cron 手填五段表达式 → cron 构造器**：预设模式（每天 HH:mm / 每周几 / 每 N 小时 / 每月几号 + 时间段选择）+ 自定义表达式专家模式；产物仍是 `cron_spec` 字符串——taskrunner 侧 robfig/cron 解析与分钟级 tick **零改动**；jobs 列表已回显 `next_run` 可作保存后预览。
  - **action_id 手填 → 动作下拉**：zhuzhao `jobs.Registry` 暴露**元数据读端点**（id/名称/描述/params schema），提交任务表单换搜索下拉；顺带**创建时 fail-fast 预校验**（现状未注册动作到回调时才 404，失败后置到执行期）。
  - **params 手填 JSON → 两步走**：近期保留 JSON 模式 + 动作说明旁挂（现"勿填口令/密钥/PII"提示与 64KB 预检维持）；远期动作注册时声明 params schema，前端按 schema 渲染动态表单——**与 S1 动态表单渲染器同构复用**（未声明 schema 的动作自动降级 JSON 模式）。
  - 可选后端随行（触发驱动，不预做）：[16 号](../phase3/16-external-integration.md) 后置项「一次性延迟任务 ProcessAt」若启用，提交表单增"指定时间执行一次"模式（与 cron 构造器同面板）。
- **协议衔接（勿另起炉灶）**：动作元数据面 = taskrunner `docs/taskrunner.md`「能力目录」两级路由方案（2026-09-15 定稿、实现后置）的**单服务前段**——目录解决"提交方不手填回调地址"，S4 解决"人不手填 action_id"，共用同一份动作注册元数据；跨服务目录（taskrunner 查目录、端点自注册、`owner_service` 多调用方）维持其既有触发（多服务接入时启用），S4 不依赖、不提前。
- **通知渠道配置页 → 迁至 S6**（2026-10-08 消息模块整段化）：渠道配置+消息模板+发送记录=通知中心一个页面族，归 S6 统一交付；本段回归 taskrunner 任务面。

### P5-S5 对象存储底座与富媒体（MinIO，后端底座 + 前端上传面）

- **底座（IW2 收编实施）**：[phase2/10-storage.md](../phase2/10-storage.md) 设计现成——S3 兼容客户端（开发 MinIO / 生产云 OSS 仅配置切换）、**预签名上传/下载**（前端直传，后端不扛文件流）、`file_objects` 元数据表、对象 key 规范 `{domain}/{yyyy}/{mm}/{uuid}.{ext}`、10MB 上限 + MIME 前缀白名单。本 phase 为其**实施载体**：compose 增 MinIO 服务（或 config 指向已有 S3）、storage 模块 + 预签名 client、迁移号启动时按 11 号 §4 对账占用（A2 规则，当前下一编号 000041）、**errcode 91000–91999 段规划随批落**（00 号既有登记）。
- **头像上传**（自服务面）：profile 头像由 URL 手填（`users.avatar` max=500 字符串）改预签名直传 + 回写对象引用；上传组件 + 即时预览。**下载形态启动批小拍板**：预签名 GET（有时效，img src 非稳定）/ 公共读桶 / 后端代理下载端点——头像对登录态可见且需稳定展示，三选一随批定。
- **工单附件（文档上传）**：10 号 `ticket_attachments` 蓝本实施——预签名上传 + 关联 API + 详情页展示/下载；权限码口径（复用 `ticket:update` vs 独立 `ticket:attach`）按 10 号 §1 既有拍板点随批定；删除语义按 10 号（删关联 + GC）。
- **富文本字段类型（richtext，第八种）**：字段类型枚举扩 `richtext`（`validateFieldInputs`/G2 schema 校验同步扩，守"只增不改"）；**正文 HTML 服务端消毒为 SSOT**（allowlist sanitizer——工单内容多人可见，防存储型 XSS；前端渲染不重复信任）；编辑器选型启动批拍（Tiptap / wangEditor 量级）；**编辑器内图片插入走同一预签名通道**（不引入 base64 内联，防库膨胀）；与 S1 设计器联动（富文本进可选字段类型调色板）。
- 顺序约束：附件/富文本均依赖底座先行，底座是本段第一个批次。

### P5-S6 消息通知（企业统一消息平台 + 消息模板 + 工单触发）

- **定位（P4-2 通知通道的能力延伸，非 §23 翻案）**：P4-2 已交付渠道配置化 webhook + 死信告警 + taskrunner 终败通知 hook；本段补齐**统一消息平台渠道 + 消息模板 + 工单事件触发**三件。§23 暂缓清单中"通知"一项随 P4-2 拍板事实上解封，本段延续同一口径；**SLA/审批/分派/报表维持暂缓不碰**。[phase3/10 §3 通知服务设计](../phase3/10-ticket-business.md)（邮件矩阵/事件订阅）作对接参考；**站内通知不取**（用户环境走统一消息平台）。
- **通道层（环境红利：全渠道单接口）**：企业统一消息平台 = 邮件/钉钉等所有渠道共用一个调用接口——通道抽象只需在既有 `notification_configs` 上**新增一种渠道类型**（type=uip：endpoint/凭据配置），**不做任何渠道 SDK 直连**；发送器抽象为 `ChannelSender` 端口（统一消息平台 = 首个 adapter；换平台/加渠道 = 新 adapter，业务代码禁止硬编码平台 HTTP 调用——见 §6 对接预留清单）。
- **模板层**：`message_templates` 表（code/名称/渠道/主题/正文/变量 schema）+ CRUD + 管理页；渲染 = **服务端占位符替换（字段值转义）**，不用完整模板引擎——防模板注入（用户可控的工单字段值不得被当模板语法执行）；模板声明自身接受的变量清单，调用方传参校验。**变量来源含时间类**（当前时间/相对时限，格式可配——2026-10-09 场景补充）。
- **收件人解析（人员参数化）**：模板收件人为变量——第一档 = 工单字段引用（assignee/creator）+ 固定人员；第二档（按需）= 角色+组织解析（工单组织的 admin/owner——L2/L3 域）。哲学与 assignee rule/事件解析角色同构：**解析归业务侧，消息平台只收最终收件人**。
- **触发层**：工单状态流转/待办 → 选模板 → 字段值填参 → 解析收件人 → 经统一消息平台发送。**启动拍板点：挂接机制**——a) 显式 emit（状态变更 service 层调用，C10 风格，推荐起步）；b) ticket_events 消费面（phase3/10 原设计——但事件表无 processed 列/无消费面，P4-2 交付时未含，选 b 需补迁移）。**触发面须域无关（2026-10-08 phase6 复核回写的要求）**：触发源与收件人声明不得焊死工单域——phase6 风险事件（新增/指派/超期/关闭，收件人 = risk owner 非工单字段）将复用同一模板/通道/触发面；若选 emit 须做成**可订阅内部钩子**（工单状态变更事件面 = S6 与 phase6 的共享基础设施，一次变更多订阅者，见 [phase6/README §3](../phase6/README.md)）。
- **发送记录**：`message_log` 表（模板/收件人/状态/错误/重试）+ 管理页；失败复用既有死信告警链。
- 迁移：`message_templates`/`message_log` 两表族，编号启动时按 11 号 §4 对账（下一编号 000041）。

### P5-S7 AI 助手（形态未定，概要登记——细节启动批定）

- **定位（概要）**：平台内嵌 AI 对话助手——用户在平台内与 AI 对话；长线设想 = **AI 参与并协助业务工作**，而非纯聊天窗。
- **演进路径（设想，未定）**：第一档 = 平台内对话（产品使用/数据问答）；第二档 = **AI 协助业务操作**——所有者示例场景：AI 协助风险员工对风险事件做**定性分析**，自动**关联资产系统**、找出**责任人**并**自动下发工单**（function-calling 代操作形态，场景载体 = [phase6 风险模块](../phase6/README.md)）。

### P5-S9 威胁情报缓存代理（概要登记——通用件，细节启动批定）

- **定位**：对**已有威胁情报 web 应用做能力补全**（应用本体不动）——解决其每日/每小时查询配额限制。技术形态 = **外部限流 API 的缓存代理**（通用件），威胁情报是首个消费者；**消费方 = phase6 风险模块 R1**（风险事件情报源之一）。
- **查询流程**：查询 → 先查本地缓存库（命中直接返回）→ 未命中调上游接口 → 结果入库带 TTL。
- **缓存设计要点**：缓存键 = 情报类型（IP/域名/hash 等）+ 查询值；**TTL 双档 7 天/30 天**（按指标衰减特性配置）；**配额耗尽降级策略**（返回过期缓存标记陈旧 vs 明确报错——启动拍板点）；可选第二档 = 高危指标后台批量刷新。
- **依赖**：上游应用 API 契约（查询接口/认证/限流数值）由企业方提供；调用凭据入配置管理。查询走 `ThreatIntelProvider` 端口（接口 + 通用 HTTP 实现 + config 挂点——§24 SSOProvider 同款预留模式：契约到位填配置即用）。
- 量级 ≈ 1 周（缓存表 + 查询代理 + TTL 管理）。

### P5-S10 工单协作与提醒能力（2026-10-09 真实场景差距分析产出）

- 量级：≈1.5–2 周（抄送 2–3 天 + 标签 2 天 + 角标 1–2 天 + 节点超时 3–4 天 + 导出含 BK-21 2–3 天）；迁移含 ticket_cc/tag 两表族（编号启动时对账）。

## 3. 明确不做（边界）

- **不做通用流程引擎/BPMN 全家桶**（Camunda/Activiti 级流程平台）——16 号 taskrunner 侧"不做通用流程引擎"红线同构适用工单侧；只做工单域状态图 + 语义配置。
- 不做跨系统编排（taskrunner 职责）；不做运行时热插拔自定义脚本动作（脚本注入面）。
- 任务面同构红线：**不做通用编排/DAG**（16 号"不做通用流程引擎"红线直接适用）；能力目录的跨服务自注册不随 S4 提前实施；params 脱敏维持后置（触发 = 日志出内网/接 ES，taskrunner.md §脱敏）。
- 富媒体边界：维持 10 号"不做"清单——病毒扫描/内容审核、>100MB 分片上传、CDN 独立域名均按需另立；云 OSS 生产替换 = 配置切换非代码分支。
- 消息域边界：**不做站内通知**（统一消息平台是唯一通道）；**不做渠道 SDK 直连**（邮件/钉钉均经统一消息平台，直连属环境变化再拍）；模板不做富排版引擎（纯文本/轻 HTML 占位符渲染）。
- 不动 §23 既有拍板：S1/S2 只换配置界面、引擎与存储零改动，**不构成自研推进**；S3 开工本身即翻案动作，未翻案前零投入。

**UAA「认证+鉴权全部移交」评估结论（2026-10-09 所有者问询后评估，重启 UAA 议题时的谈判交付物）**：分层定支持度——**认证**：✅ 完全支持（§24，L1/L2/L3 零改动）；**角色分配**（谁是什么角色）：✅ 支持（UAA 作 entitlement 目录，登录按 claims 映射本地角色）；**路由级（L1）**：⚠ 可谈——形式 a = 信任 token 权限 claims（需把 100+ 端点权限码词表搬 UAA 配置，维护成本高）；形式 b = UAA 管到角色、路径级留本地（**推荐**）；代码影响小（casbin 角色输入源可切，模型不动）；**资源级（L2）/状态机（L3）**：❌ **不可移交**——组织属主/委托/ticket_visibility 是平台私有数据语义，判定点必须在数据处（§25 定版；业界同理，Keycloak 类也只到角色映射）。**谈判口径 = IGA 形态：授权分配归 UAA、授权执行归平台**；UAA 若坚持 PDP API，L1 可接（每请求远程判定的延迟自担），L2 无解。账密登录保留（§24 双轨）已覆盖外部人员场景。

**「角色壳」落地方案（2026-10-09 所有者"套壳"问询后设计——形式 b 的具体实现，谈判首选）**：UAA 配 3–5 个**粗粒度应用角色**并在其界面做用户分配（满足其权限管理存在感，非糊弄——Keycloak role mapping/Okta app roles/Azure AD app roles 同款业界标准）；zhuzhao 登录 callback 按角色 claims **覆盖式同步**本地绑定（`uaa_roles → 本地角色` 映射表，单向收敛——本地特有细角色不反向暴露），之后 L1/L2/L3 照常。**四个实现拍板点**：①映射方向单向收敛；②fail 策略 = AT 有效期内不重查、仅登录/刷新时同步（天然降级，UAA 故障不断已有会话）；③审计 = 登录同步落角色变更记录 + 可选定时对账任务（防长期未登录用户角色漂移）；④壳厚度分级——**L0 壳**（UAA 只管应用准入/scope，角色平台自算）起谈，UAA 要存在感升 **L1 壳**（粗角色）。代码影响：`getRoles` 数据源接映射结果，Casbin/L2/L3/菜单渲染零改动（角色绑定进数据、判定在本地——接缝天然存在）。
