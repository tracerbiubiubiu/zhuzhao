# 文档维护约定

维护文档先问两件事：谁要用它解决什么问题，哪个文件已经负责这件事。五仓的实现与使用说明随各自代码维护，生态级规划和工程约定由主仓维护。查文档从[总入口](README.md)按任务进入，工程和测试规则见[工程公约](standards.md)。

## 1. 从哪里开始读

根 `README.md` 回答“为谁解决什么问题、当前能做什么、如何体验及参与”；先给价值和真实展示，再给可执行上手及文档入口，不把架构/安装命令当唯一首屏。五仓提供中文README与`README.en.md`语言切换，公开能力与成熟度保持一致；英文文档不表示UI或全部设计稿已国际化。`docs/README.md`回答具体任务应先读哪篇，避免让新人从审计流水推导现状。

每仓只建立有实际内容的分类：

- `guides/`：上手、开发、联调等可执行步骤。写明前置条件、命令所在工作目录、输入和预期结果。
- `design/`：当前架构、模块边界和关键流程，解释为什么这样组织。数据模型和 API 的准确字段链接到契约或源码。
- `api/`：供调用方查阅的协议、错误码和字段约定。生成文件注明生成入口，不手改生成物。
- `ops/`：部署、配置、备份恢复、发布和故障处理。区分开发、测试、生产及历史演练。
- `planning/`：主仓统一维护五仓当前范围、依赖、估算、决策及来源；兄弟仓只引用，不另建生态总账。
- `toolkit/`：可复用工作资料入口；`playbooks/`索引方法，`templates/`保存空白模板，`prompts/`保存开发/审计提示词原件。产品运行时提示词和业务模板仍随实际代码/配置维护。
- `review/`：当前控制台、审查方法和索引；`reports/` 保存需要长期追溯的正式时点报告，`archive/` 保存仍有决策或问题出处价值的历史材料。

主仓另有 `modules/`、`adr/`、`proposal/`、`phase1/` 至 `phase9/`，分别承载跨阶段模块说明、架构决策、提案和阶段设计。它们有不同职责，不因为统一结构就合成一篇大全，也不要求兄弟仓建立空目录或空阶段。

按读者需要安排入口。所有者先查已决定的事项、还有哪些问题要确认，以及评审时看什么。开发者从现有模块或本次设计进入，再沿链接查仍适用的规则正文和历史出处。若规则正文仍在阶段稿，当前入口直接链接相关小节。运维和审计需要命令、实际运行的版本及结果。把当前结论放前面，全量清单和历史报告放在后面。同一条规则在对应模块或共同设计中维护，阶段文档链接过去，并说明本批实现哪一段、何时做和怎样验收。

当前规划已统一迁入`planning/`，逐项去向见[迁移清单](document-migration.json)。脚本、测试与现行跨仓引用随目录同步迁移；冻结输入仍保留原字节和历史来源语义，不重排编号或改写历史证据。库、UI和Go服务按职责建目录，G06维护适用profile，不批量补空目录或同步所有部署布局。

这种分类借鉴 [Diátaxis](https://diataxis.fr/how-to-use-diataxis/) 按阅读需要区分操作、参考与解释的做法；具体目录服务本项目已有内容，不照搬空模板。

## 2. 什么应进入 Git

按以下顺序判断，处理现有文件时也用这一套。

1. **有人按版本使用它吗？** 当前指南、操作手册、合同、设计、架构决策、机器台账和空白模板随 Git 维护。生成工具的输入、消费者加载的生成物、合成测试向量和冻结证据按实际路径保留。例如 Swagger 有调用方，规划证据即使是旧 JSON 也可能仍被校验器读取。
2. **这里有没有唯一的长期结论？** 记录独有决策、未关闭问题、失败反例或复验边界的历史稿和正式报告继续保留。比如 [BK11 复盘](review/13-bk11-pool-deadlock-2026-10-26.md)给出池耗尽的失败证据、错判订正和未实施的试点裁决。查今日状态从控制台进入，历史原文按当时基线解释。新一轮复验只补新增证据和变化，已有结论用链接引用。
3. **主体内容已在别处维护，或只记录一次执行过程吗？** 索引和重复说明并入归属页，走读笔记、已填执行卡、全量日志、原始截图、调研副本、备份和纯操作收据归本地。比如空白验收卡留[模板库](toolkit/templates/README.md)，实际执行生成的日志随本地批次保存。正式结论只摘录可共享的发现、复验边界与材料 ID。

退出跟踪前，依[引用与迁移检查](#5-引用与迁移检查)查当前和历史链接、脚本/CI、消费者、固定版本与校验值。把仍有价值的结论和输入先交给归属页，保留原样可恢复副本及校验值，再移出当前维护集。文件名、扩展名、年龄和入链数量可用来筛选复查对象，保留决定要落到用途和内容。

本地档案按[材料目录](materials.md)归类。ignored `.codex/`可暂存执行中的材料，工作结束后把要保留的材料转入仓外档案，正式结论用稳定材料 ID。`doc/` 不另建长期知识库，旧 `deliverables/` 和 `outputs/` 不作为受控入口。仅限本机的受限资料单独存放，禁止通过 Git 或其他渠道上传，原名、真实路径和内容只留本地私有索引。 [受限资料边界](materials.md#仅限本机的受限资料)

仓内 Git、Docker、ZCode 忽略分别生效。仓外档案在其自身入口排除，仓内继续排除旧执行目录和误拷回的本地档案。ZCode 镜像段跟随 Git 规则，持久自定义段保留本地排除，本机配置继续留本机。以实际消费者核对构建裁剪，禁止通过忽略整个 `docs/`、`*.md` 或 `*.json` 隐藏应审输入。

根 `README.md`、`AGENTS.md`、法律文件及工具识别路径保留各自位置。源码与部署旁的长篇人工说明归 `docs/`。供首页展示而筛选的合成图片可放 `docs/assets/`，说明来源、现有或计划状态及隐私核验。展示材料禁止使用真实内部身份、地址或凭据。启动用时、性能和增长措辞按实测与可核证据书写。

## 3. 文件与目录命名

普通目录和文件用小写、连字符分词，例如 `deployment.md`、`frontend-ui.md`。目录入口固定为 `README.md`；根 `AGENTS.md`、`LICENSE` 等约定文件保留工具识别名称。ADR 在正文展示 `ADR-001`，文件名使用 `adr-001-主题.md`。

正式时点报告使用 `主题-YYYY-MM-DD.md`。已有报告的批号、发现编号、阶段编号不重排；历史缺号、续批或合并关系在索引解释，不能为凑齐编号制造空文件。

每个实际的文档目录都有 README，说明用途、当前状态、阅读顺序和文件入口。阶段 README 还应写明前置条件、交付边界和下一阶段条件。只有总纲的远期阶段应明确“研究/待立项”，不能用空设计稿制造已就绪的印象。

### 引用编号与命名空间

正文先写**事项名称（原编号）**。首次出现时按源台账的名称写，说明它属于工作包、发布验收点、所有者议程、业务决策、缺陷、估算行或测试场景，并链接来源。后文可用已清楚定义的短称。只交付包内一部分时，说明本批具体做什么。独立可读的表格用列名或表头说明来源，例如“工作包”“首版估算行”。

1. **编号随来源解释。** 同一个编号在两份台账里可以指不同事项。首次引用用“来源＋事项名称（原编号）”，例如“总账的业务意图持久交接（R01）”和“真实 UAA 接入条件的 R01”。常见混淆见[规划入口的编号索引](planning/README.md#常见编号怎么读)。
2. **阅读顺序用普通数字。** 文档里的办理步骤、验收卡内顺序和局部章节沿用各自的 1、2、3。样例主体用名称，跨文档引用测试时带上模块、场景名和原编号。需要跨文档追踪时先用原台账已有编号。首版必交项沿用目标 JSON 的引用位置和原文摘要。
3. **稳定编号保留原样。** 补零、连字符和前缀都是已有标识的一部分。历史证据、引用锚点和机器字段按原值追溯。若确需改机器编号，先列旧新映射、消费者和兼容方式，再按迁移验证。

### 仓库名称与改名边界

文档整理使用项目当前仓名和产品名。品牌和仓库改名由所有者决定，讨论与状态在[命名议程](planning/owner-decision-agenda.md#q13-新品牌与五仓名称)查阅。

仓库改名是独立维护批次。分别核对 GitHub 权限、仓库名、Go module/import、包和镜像、本地 worktree/remote、Action、依赖、链接和发布消费者，再做干净缓存及跨仓验证。数据库、API、二进制、卷名按各自消费者与迁移成本决定。GitHub 重定向只覆盖它支持的访问方式，Go 模块和 CI 要实测。

## 4. 内容怎样写清楚

### 页头和效力

新写或实质维护的现行文档使用简短固定页头，按适用性填写：用途/读者、适用范围、设计状态、实施/验证状态、权威来源及必要工作项/源码或契约基线。导航只指向状态权威，纯维护规则不伪造运行SHA；无需给全部旧报告批量增加frontmatter。

设计状态可为候选、方向已确认、准确合同已冻结、被替代；代码是否存在、哪组候选已验证、哪个环境已部署另行表述。不能用一个“完成/已批准”同时代表这几件事。API说明必须区分当前可用与目标接口；目标合同即使位于api目录，也须显式标注尚未实现。历史报告保持原日期/基线/失败和限制，用后继链接解释现状。

页头示例（只示范格式，不构成能力或验收事实）：

```markdown
> 用途：解释本模块目标合同；范围：当前获准工作包。
> 设计状态：候选，准确Schema待本批冻结；实施状态：未实现，未运行验证。
> 权威：对应共同合同/工作包；当前实现另见模块说明与准确源码。
```

### 载体与内容职责

| 载体/类型 | 维护什么 | 不承担什么 |
|---|---|---|
| Markdown指南/运维 | 前置、命令所在目录、步骤、预期结果与失败恢复 | 不复写接口全字段或把演练当生产承诺 |
| Markdown当前模块/目标设计 | 当前调用链/写主；或目标、非目标、数据/状态、授权/并发/恢复及验收，分别标注 | 不以Phase名或文件存在证明已实现 |
| OpenAPI/JSON Schema与接口说明 | 明确版本和当前/候选边界，机器可检验输入输出 | 不替代业务授权、事务和真实互操作验证 |
| JSON机器台账与Markdown投影 | 范围/依赖/价格/状态等事实由指定JSON维护，Markdown给人读结论 | 不让两份人工数字各自变更；冻结来源按固定commit验证 |
| ADR | 重要选择的背景、理由、后果、设计效力及实施状态、替代链 | 不为每项普通细节建立独立决策文件 |
| 固定时点报告/HTML原型 | 报告保存准确证据窗口；原型解释候选交互 | 报告不承担当下状态，原型不冒称Vue/真实链已交付 |

机器事实的Markdown摘要在同批从唯一来源生成或逐项核对，不重新报价或独立维护总数；G06自动化未实现前如实写人工/本轮静态核对，不能宣称已有通用生成器。遇到冻结估算/历史输入，以其登记commit和hash验证；当前说明变化不要求把历史hash改成当前文件hash。生成物注明实际工具/来源且不手改，现有Swagger/代码类型消费路径继续保留。

### 需求与补充的追踪

原始要求、后续纠正、例子与所有者确认分别记录来源；简短“可以”只绑定明确前文，不扩成全部未来实施批准。在[需求来源核对](planning/user-requirements-reconciliation.md)及配套 JSON 中记录每条要求归哪份设计、核到了什么程度、下一步要做什么。各模块继续维护自己的接口约定，估算、成熟度和决策各用已有台账。

每次新增场景或改变方向时增量对账，至少分清已检查、设计候选/骨架、已计价、已实现/已验证。仅文件存在、来源映射、窗口已排都不能证明内容已审透。历史覆盖声明保留其截止，新的结论必须说明新来源范围和未检查部分；原始会话和私有指南留本地，不进受控文档。

### 正文和说明

当前指南先讲读者要解决什么，再讲步骤或机制。关键术语第一次出现时用一句话解释；重要命令给前置条件和预期结果；接口示例使用真实字段名与序列化类型，示意代码明确标注不可直接运行的部分。

写业务场景时，在原段落说清谁做了什么、什么时候做、页面或记录如何变化。例如写“抄送人能查看并评论；要提交整改，系统会另查他的办理权限”。容易误读的词在首次出现处解释。例如“旧票”应写明是哪次规则功能上线之前已有的工单，或是已经按 A 版创建、后来遇到 B 版发布的工单。前者要查有没有可信的历史规则，后者继续按 A 版。若描述“恢复提醒”，写明业务已保存，服务重启后还能查到待发送记录。 [工单规则示例](phase6/ticket-module-detail.md#33-发布迁版与配置晋级) · [B2 验收卡](planning/phase6-b2-acceptance-cards.md)

写操作说明时，把可能混读的结果写完整。比如从主仓运行就绪探针，HTTP 成功说明核心服务通过自身就绪检查。UI、独立任务服务和清单服务是否已可用，分别核对[部署指南](ops/deployment.md)中的对应入口。若命令只适用于某次历史演练，保留演练时点与当时的环境说明。

区分“当前已实现”“已批准但未实施”“待拍板”“历史方案”。阶段名不是完成证据，注册项不是运行中的实例，测试通过也不是生产部署完成。需要判断现状时，先看实际代码、迁移与对应验收收据，再看有效决策和当前台账；历史报告只证明其注明的时点。

设计讨论保留旧决策和被取代关系。发现旧方案与现行实现冲突时，在冲突处说明适用范围并回链当前依据；不能一边保留“当前唯一”，一边追加相反结论让读者自行猜测。尚无有效裁定的约束集中记为待定项，文档整理不代替业务拍板。

图示用来解释仓库边界、调用链、状态或数据流，并配文字说明失败边界。优先在 Markdown 中维护 Mermaid 源码，随实现更新；GitHub 支持该格式，见 [图示语法说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)。无需为每篇文档添加装饰图。

## 5. 引用与迁移检查

同仓文档使用相对链接，目录链接优先落到 README。引用代码使用“仓库内路径 + 符号名”，行号只作辅助；不把个人工作站绝对路径写成他人无法打开的源码入口。

迁移时按原文件位置解析链接，再根据新位置重算相对路径，同时检查脚本、测试、CI、帮助文本和跨仓说明中的真实文件消费者。固定 commit 的历史链接保留历史含义，不把它们一律替换到当前分支。

迁移完成后核对旧文件的每项去向：保留、移动、合并或停止跟踪都要有依据。随后检查文件与章节链接、命名、目录 README、代码块、当前状态和跨仓契约；确认 Git/Docker 忽略规则与生成工具仍正确。

引用检查同时覆盖 Markdown 链接、行内代码形式的路径、跨仓 SSOT 指针，以及脚本/帮助文本的消费者；只检查可点击链接会漏掉旧路径。历史文件名和固定时点的命令保留原意，必要时在旁边补当前导航，不把历史章节号指向新短导览。门禁完成、提交、推送后要再核当前摘要，避免正文已收口而页头仍写“进行中”。

代码示例要么提供完整导入和可运行前置，要么明确它是接线片段，并解释变量来源；操作指南至少写清启动、健康检查与预期失败的排查入口。文档搬迁不应悄悄改变运行配置、依赖版本、权限或 API 行为。

## 6. 可复用工作资料与执行生命周期

[工作资料库](toolkit/README.md)统一索引方法、模板与提示词。方法说明工作步骤、检查维度和出口，空白模板定义填写结构，提示词帮助启动或接续工作；三者链接权威规则，不复制出第二套公约。已有[审计方法](review/audit-playbook.md)保留原路径，由playbooks索引；审计模板从方法正文提取，原章节保留跳转，不重复维护同一正文。

可复用原件默认随Git维护，并写清用途、读者、所需输入、输出、适用边界和权威来源。原件不含本轮真实基线、进度、账号、凭据、日志或“已验证”结论；占位符须替换后才能用于某次执行。提示词无权扩大当前会话授权，也不能覆盖AGENTS、工程规则或适用门禁。产品实际加载的系统提示词、消息模板、业务模板和测试夹具属于运行/测试消费者，保留现有代码或配置位置和门禁，不按名称移入toolkit。

GitHub会读取的PR/Issue模板保留`.github/`识别位置，工具要求固定位置的技能/配置/生成输入同理；toolkit只登记入口。第三方参考技能和提示词保持其示例/许可证/来源关系，不因出现“prompt/template/skill”就搬迁。现有分类有内容才建目录，兄弟仓复用主仓入口，不复制空框架。

每次新增或整理按以下顺序执行：

1. **创建前**：查现有入口与消费者，确定唯一属主、文档类型、原件或实例，以及Git或本地档案；能更新已有SSOT就不另建副本。
2. **写入时**：受控文档放归属仓docs并挂到相应README；模板原件只保留占位和说明。执行实例按批次在ignored `.codex/`或仓库外工作目录隔离，避免在src下另开长期资料目录。
3. **收尾时**：将独有发现、决策、必要输入和验证边界提炼为受控结论；需保留的原始材料原样归档，登记材料ID、来源基线及必要校验值，个人绝对路径只放本地索引。无保留价值且归属明确的临时产物核清引用后清理，不删除未知归属材料。
4. **交付前**：检查README入口、链接/锚点、脚本和跨仓消费者、Git/Docker忽略及Git状态；区分仍在执行、归档、停止跟踪与正式结论。记录未完成项，不把目录存在写成实现或门禁通过。

常见归属示例：空白审计报告在toolkit/templates；填写后的长期审计结论在review/reports；执行卡、全量终端日志和截图在本地批次；被校验器消费的冻结JSON仍按登记位置随Git保存。是否纳管由内容与消费者决定，不能以“模板”“历史”或扩展名一概处理。
