# 文档维护约定

> **用途**：五仓人工文档的分类、格式、效力和迁移规则。**范围**：按实际内容适用，保留各语言/仓库profile；不改变接口、运行或测试门禁。**权威**：本页管文档，[standards](standards.md)管工程与测试，模块事实仍归对应源码/合同/证据。

本约定适用于 zhuzhao、zhuzhao-ui、zhuzhao-utils、taskrunner 和 activelist。每个仓库维护自己的 `docs/`，主仓保存生态级公约和阶段规划；跨仓说明链接到归属仓的权威文件，不复制出另一份可独立漂移的契约。

## 1. 从哪里开始读

根 `README.md` 回答“为谁解决什么问题、当前能做什么、如何体验及参与”；先给价值和真实展示，再给可执行上手及文档入口，不把架构/安装命令当唯一首屏。五仓提供中文README与`README.en.md`语言切换，公开能力与成熟度保持一致；英文文档不表示UI或全部设计稿已国际化。`docs/README.md`回答具体任务应先读哪篇，避免让新人从审计流水推导现状。

每仓只建立有实际内容的分类：

- `guides/`：上手、开发、联调等可执行步骤。写明前置条件、命令所在工作目录、输入和预期结果。
- `design/`：当前架构、模块边界和关键流程，解释为什么这样组织。数据模型和 API 的准确字段链接到契约或源码。
- `api/`：供调用方查阅的协议、错误码和字段约定。生成文件注明生成入口，不手改生成物。
- `ops/`：部署、配置、备份恢复、发布和故障处理。区分开发、测试、生产及历史演练。
- `review/`：当前控制台、审查方法和索引；`reports/` 保存需要长期追溯的正式时点报告，`archive/` 保存仍有决策或问题出处价值的历史材料。

主仓另有 `modules/`、`adr/`、`proposal/`、`phase1/` 至 `phase9/`，分别承载跨阶段模块说明、架构决策、提案和阶段设计。它们有不同职责，不因为统一结构就合成一篇大全，也不要求兄弟仓建立空目录或空阶段。

入口先按读者任务分流：所有者看当前结论/设计深度/待决与短审阅卡，开发者进入当前模块/目标合同/原Phase来源，运维和审计进入步骤/准确组合与证据。当前结论在前，机器全量清单、日期流水和历史报告按需展开。同一机制的长期权威归领域/共同合同，Phase负责范围、先后和验收映射，避免每期重写同一份规则。

当前规划仍保留在review原路径，本轮先分清导航。若以后将现行计划迁入planning目录，按§5作一次完整消费者迁移；不能为目录整齐回写冻结输入、重排原编号或改变历史证据。库、UI和Go服务按职责建目录，G06维护适用profile，不批量补空目录或同步所有部署布局。

这种分类借鉴 [Diátaxis](https://diataxis.fr/how-to-use-diataxis/) 按阅读需要区分操作、参考与解释的做法；具体目录服务本项目已有内容，不照搬空模板。

## 2. 什么应进入 Git

当前维护的指南、契约、设计、已拍决策，以及仍需追溯的正式审计结论进入各仓 `docs/`。历史报告保留当时的基线、发现、原失败和验证范围；用状态说明及后续链接解释变化，不能把旧结论直接改成今天的结果。

根 `README.md`、`AGENTS.md` 和法律文件是入口、协作协议及法律用途的例外。GitHub 会读取 `docs/` 下的贡献指南，贡献说明也可统一放在这里，见 [GitHub 官方说明](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)。源码、部署目录旁的长篇人工说明迁入 `docs/`，避免第二套维护位置。

本地 `doc/` 保持为参考材料。执行卡、进度、阅读清单、原日志、截图、数据库备份和临时探针放在 `.codex/` 等本地目录，由 `.gitignore` 与 `.dockerignore` 同时排除。旧 `deliverables/`、`outputs/` 不再作为受控文档入口。

为README展示而明确筛选的合成产品图片可放`docs/assets/`，附来源/当前或规划状态/隐私核验说明；这是公开展示资产，不批量搬入原始审计截图。不得使用真实内部身份/地址/凭据，不把未来原型装成已交付产品；首次下载/构建未实测时不承诺“5秒启动”，竞品性能和增长百分比必须有可核依据。

判断是否停止跟踪时，先确认它没有独有决策、未闭环问题或必要证据。能合并的索引并入对应 README；过时操作样例先保留本机原样副本与校验值，再移出维护集。不能仅按文件年龄或目录名批量删除正式报告。

## 3. 文件与目录命名

普通目录和文件用小写、连字符分词，例如 `deployment.md`、`frontend-ui.md`。目录入口固定为 `README.md`；根 `AGENTS.md`、`LICENSE` 等约定文件保留工具识别名称。ADR 在正文展示 `ADR-001`，文件名使用 `adr-001-主题.md`。

正式时点报告使用 `主题-YYYY-MM-DD.md`。已有报告的批号、发现编号、阶段编号不重排；历史缺号、续批或合并关系在索引解释，不能为凑齐编号制造空文件。

每个实际的文档目录都有 README，说明用途、当前状态、阅读顺序和文件入口。阶段 README 还应写明前置条件、交付边界和下一阶段条件。只有总纲的远期阶段应明确“研究/待立项”，不能用空设计稿制造已就绪的印象。

### 仓库名称与改名边界

所有者已提出连`zhuzhao`平台名一并更换，名称尚未确定；此前保留该品牌的建议不再是现行选择。建议选定新品牌后采用“新品牌、新品牌-ui、新品牌-taskrunner、新品牌-activelist、新品牌-utils”的统一产品族；ui包含普通用户工作台，不必限定叫console，activelist用副标题说明动态清单职责。若某服务将独立维护为通用产品，再单独评估是否保留独立名字；不为统一改成空泛common。

当前先处理其他文档工作，不执行改名。GitHub改名可由维护者通过gh准备执行；本轮未重新核gh认证/管理权限，实际操作前核最新认证、仓库管理权限及消费者。未来作为独立维护批次，分别确定产品展示名、GitHub仓名、Go module/import、包/镜像与本地worktree/remote；清点Action/URL/依赖和发布消费者，再做干净缓存与跨仓验证。数据库、API、二进制和卷名按实际成本单独决定，不随仓名自动替换；Git重定向也不证明Go模块和Action消费者无需更新。新品牌和五仓映射由所有者选择，其余迁移清点由维护者准备。

## 4. 内容怎样写清楚

### 页头和效力

新写或实质维护的现行文档使用简短固定页头，按适用性填写：用途/读者、适用范围、设计状态、实施/验证状态、权威来源及必要工作项/源码或契约基线。导航只指向状态权威，纯维护规则不伪造运行SHA；无需给全部旧报告批量增加frontmatter。

设计状态可为候选、方向已确认、准确合同已冻结、被替代；代码是否存在、哪组候选已验证、哪个环境已部署另行表述。不能用一个“完成/已批准”同时代表这几件事。API说明必须区分当前可用与目标接口；目标合同即使位于api目录，也须显式标注尚未实现。历史报告保持原日期/基线/失败和限制，用后继链接解释现状。

页头示例（只示范格式，不构成能力或验收事实）：

```markdown
> 用途：解释本模块目标合同；范围：当前获准工作包。
> 设计状态：候选，准确Schema待本批冻结；实施状态：未实现，未运行验证。
> 权威：对应共同合同/工作包；当前实现另见模块说明与准确源码。
```

### 载体与内容职责

| 载体/类型 | 维护什么 | 不承担什么 |
|---|---|---|
| Markdown指南/运维 | 前置、命令所在目录、步骤、预期结果与失败恢复 | 不复写接口全字段或把演练当生产承诺 |
| Markdown当前模块/目标设计 | 当前调用链/写主；或目标、非目标、数据/状态、授权/并发/恢复及验收，分别标注 | 不以Phase名或文件存在证明已实现 |
| OpenAPI/JSON Schema与接口说明 | 明确版本和当前/候选边界，机器可检验输入输出 | 不替代业务授权、事务和真实互操作验证 |
| JSON机器台账与Markdown投影 | 范围/依赖/价格/状态等事实由指定JSON维护，Markdown给人读结论 | 不让两份人工数字各自变更；冻结来源按固定commit验证 |
| ADR | 重要选择的背景、理由、后果、设计效力及实施状态、替代链 | 不为每项普通细节建立独立决策文件 |
| 固定时点报告/HTML原型 | 报告保存准确证据窗口；原型解释候选交互 | 报告不承担当下状态，原型不冒称Vue/真实链已交付 |

机器事实的Markdown摘要在同批从唯一来源生成或逐项核对，不重新报价或独立维护总数；G06自动化未实现前如实写人工/本轮静态核对，不能宣称已有通用生成器。遇到冻结估算/历史输入，以其登记commit和hash验证；当前说明变化不要求把历史hash改成当前文件hash。生成物注明实际工具/来源且不手改，现有Swagger/代码类型消费路径继续保留。

### 需求与补充的追踪

原始要求、后续纠正、例子与所有者确认分别记录来源；简短“可以”只绑定明确前文，不扩成全部未来实施批准。当前[原话对账](review/user-requirements-reconciliation.md)及JSON给去向、证据深度和下一出口；模块合同、价格、成熟度和决策仍各归原权威，不在此重复维护。

每次新增场景或改变方向时增量对账，至少分清已检查、设计候选/骨架、已计价、已实现/已验证。仅文件存在、来源映射、窗口已排都不能证明内容已审透。历史覆盖声明保留其截止，新的结论必须说明新来源范围和未检查部分；原始会话和私有指南留本地，不进受控文档。

### 正文和说明

当前指南先讲读者要解决什么，再讲步骤或机制。关键术语第一次出现时用一句话解释；重要命令给前置条件和预期结果；接口示例使用真实字段名与序列化类型，示意代码明确标注不可直接运行的部分。

区分“当前已实现”“已批准但未实施”“待拍板”“历史方案”。阶段名不是完成证据，注册项不是运行中的实例，测试通过也不是生产部署完成。需要判断现状时，先看实际代码、迁移与对应验收收据，再看有效决策和当前台账；历史报告只证明其注明的时点。

设计讨论保留旧决策和被取代关系。发现旧方案与现行实现冲突时，在冲突处说明适用范围并回链当前依据；不能一边保留“当前唯一”，一边追加相反结论让读者自行猜测。尚无有效裁定的约束集中记为待定项，文档整理不代替业务拍板。

图示用来解释仓库边界、调用链、状态或数据流，并配文字说明失败边界。优先在 Markdown 中维护 Mermaid 源码，随实现更新；GitHub 支持该格式，见 [图示语法说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)。无需为每篇文档添加装饰图。

## 5. 引用与迁移检查

同仓文档使用相对链接，目录链接优先落到 README。引用代码使用“仓库内路径 + 符号名”，行号只作辅助；不把个人工作站绝对路径写成他人无法打开的源码入口。

迁移时按原文件位置解析链接，再根据新位置重算相对路径，同时检查脚本、测试、CI、帮助文本和跨仓说明中的真实文件消费者。固定 commit 的历史链接保留历史含义，不把它们一律替换到当前分支。

迁移完成后核对旧文件的每项去向：保留、移动、合并或停止跟踪都要有依据。随后检查文件与章节链接、命名、目录 README、代码块、当前状态和跨仓契约；确认 Git/Docker 忽略规则与生成工具仍正确。

引用检查同时覆盖 Markdown 链接、行内代码形式的路径、跨仓 SSOT 指针，以及脚本/帮助文本的消费者；只检查可点击链接会漏掉旧路径。历史文件名和固定时点的命令保留原意，必要时在旁边补当前导航，不把历史章节号指向新短导览。门禁完成、提交、推送后要再核当前摘要，避免正文已收口而页头仍写“进行中”。

代码示例要么提供完整导入和可运行前置，要么明确它是接线片段，并解释变量来源；操作指南至少写清启动、健康检查与预期失败的排查入口。文档搬迁不应悄悄改变运行配置、依赖版本、权限或 API 行为。
