# 文档维护约定

本约定适用于 zhuzhao、zhuzhao-ui、zhuzhao-utils、taskrunner 和 activelist。每个仓库维护自己的 `docs/`，主仓保存生态级公约和阶段规划；跨仓说明链接到归属仓的权威文件，不复制出另一份可独立漂移的契约。

## 1. 从哪里开始读

根 `README.md` 回答“这个仓库做什么、怎样进入文档”；`docs/README.md` 回答“我现在要做这件事，应先读哪篇”。入口应给阅读顺序和适用范围，避免让新人从历史审计流水中推导现状。

每仓只建立有实际内容的分类：

- `guides/`：上手、开发、联调等可执行步骤。写明前置条件、命令所在工作目录、输入和预期结果。
- `design/`：当前架构、模块边界和关键流程，解释为什么这样组织。数据模型和 API 的准确字段链接到契约或源码。
- `api/`：供调用方查阅的协议、错误码和字段约定。生成文件注明生成入口，不手改生成物。
- `ops/`：部署、配置、备份恢复、发布和故障处理。区分开发、测试、生产及历史演练。
- `review/`：当前控制台、审查方法和索引；`reports/` 保存需要长期追溯的正式时点报告，`archive/` 保存仍有决策或问题出处价值的历史材料。

主仓另有 `modules/`、`adr/`、`proposal/`、`phase1/` 至 `phase9/`，分别承载跨阶段模块说明、架构决策、提案和阶段设计。它们有不同职责，不因为统一结构就合成一篇大全，也不要求兄弟仓建立空目录或空阶段。

这种分类借鉴 [Diátaxis](https://diataxis.fr/how-to-use-diataxis/) 按阅读需要区分操作、参考与解释的做法；具体目录服务本项目已有内容，不照搬空模板。

## 2. 什么应进入 Git

当前维护的指南、契约、设计、已拍决策，以及仍需追溯的正式审计结论进入各仓 `docs/`。历史报告保留当时的基线、发现、原失败和验证范围；用状态说明及后续链接解释变化，不能把旧结论直接改成今天的结果。

根 `README.md`、`AGENTS.md` 和法律文件是入口、协作协议及法律用途的例外。GitHub 会读取 `docs/` 下的贡献指南，贡献说明也可统一放在这里，见 [GitHub 官方说明](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)。源码、部署目录旁的长篇人工说明迁入 `docs/`，避免第二套维护位置。

本地 `doc/` 保持为参考材料。执行卡、进度、阅读清单、原日志、截图、数据库备份和临时探针放在 `.codex/` 等本地目录，由 `.gitignore` 与 `.dockerignore` 同时排除。旧 `deliverables/`、`outputs/` 不再作为受控文档入口。

判断是否停止跟踪时，先确认它没有独有决策、未闭环问题或必要证据。能合并的索引并入对应 README；过时操作样例先保留本机原样副本与校验值，再移出维护集。不能仅按文件年龄或目录名批量删除正式报告。

## 3. 文件与目录命名

普通目录和文件用小写、连字符分词，例如 `deployment.md`、`frontend-ui.md`。目录入口固定为 `README.md`；根 `AGENTS.md`、`LICENSE` 等约定文件保留工具识别名称。ADR 在正文展示 `ADR-001`，文件名使用 `adr-001-主题.md`。

正式时点报告使用 `主题-YYYY-MM-DD.md`。已有报告的批号、发现编号、阶段编号不重排；历史缺号、续批或合并关系在索引解释，不能为凑齐编号制造空文件。

每个实际的文档目录都有 README，说明用途、当前状态、阅读顺序和文件入口。阶段 README 还应写明前置条件、交付边界和下一阶段条件。只有总纲的远期阶段应明确“研究/待立项”，不能用空设计稿制造已就绪的印象。

## 4. 内容怎样写清楚

当前指南先讲读者要解决什么，再讲步骤或机制。关键术语第一次出现时用一句话解释；重要命令给前置条件和预期结果；接口示例使用真实字段名与序列化类型，示意代码明确标注不可直接运行的部分。

区分“当前已实现”“已批准但未实施”“待拍板”“历史方案”。阶段名不是完成证据，注册项不是运行中的实例，测试通过也不是生产部署完成。需要判断现状时，先看实际代码、迁移与对应验收收据，再看有效决策和当前台账；历史报告只证明其注明的时点。

设计讨论保留旧决策和被取代关系。发现旧方案与现行实现冲突时，在冲突处说明适用范围并回链当前依据；不能一边保留“当前唯一”，一边追加相反结论让读者自行猜测。尚无有效裁定的约束集中记为待定项，文档整理不代替业务拍板。

图示用来解释仓库边界、调用链、状态或数据流，并配文字说明失败边界。优先在 Markdown 中维护 Mermaid 源码，随实现更新；GitHub 支持该格式，见 [图示语法说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)。无需为每篇文档添加装饰图。

## 5. 引用与迁移检查

同仓文档使用相对链接，目录链接优先落到 README。引用代码使用“仓库内路径 + 符号名”，行号只作辅助；不把个人工作站绝对路径写成他人无法打开的源码入口。

迁移时按原文件位置解析链接，再根据新位置重算相对路径，同时检查脚本、测试、CI、帮助文本和跨仓说明中的真实文件消费者。固定 commit 的历史链接保留历史含义，不把它们一律替换到当前分支。

迁移完成后核对旧文件的每项去向：保留、移动、合并或停止跟踪都要有依据。随后检查文件与章节链接、命名、目录 README、代码块、当前状态和跨仓契约；确认 Git/Docker 忽略规则与生成工具仍正确。文档搬迁不应悄悄改变运行配置、依赖版本、权限或 API 行为。
