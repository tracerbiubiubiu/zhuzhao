# 配置制品晋级方案（测试→生产）

> **当前安排（2026-11-11，所有者收尾口径）**。本篇保留为 Phase6 全项目重规划的配置晋级提案，尚未实施。原 B3 件 7 范围、CLI 入口、包形状与审批补偿方案作为设计输入，具体范围和排期待重规划。确认实施件 7 后，在实施前确定契约，首次生产配置晋级前完成验收。
>
> 本篇记录跨环境晋级的候选契约。原阶段排期见 [05 号 T1](../phase6/05-launch-batch.md#63-工单完善批06-号)，首版范围见 [06 号件 7](../phase6/06-ticket-completeness.md#37-件-7-类型定义包导入导出)，定义发布与在途版本语义见 [00 号 B0-3](../phase6/00-flow-engine-v2.md#flow-definition-snapshots)。

## 1. 目标与边界

在测试环境发布并验证工单类型后，导出指定配置，在目标环境查看实际变更、核准计划，再把同一批配置事务化落地。相同内容可以重复晋级。提交失败时自动回滚，提交成功后按已记录的变更做定向补偿。

| 数据 | 归属 |
|---|---|
| 工单类型、流程与字段、工单模板 | 首版配置包。类型的版本化定义取自已发布快照，模板是同包内独立的建单预填配置。 |
| 字典、用户、组织等引用 | 首版按稳定键解析并验证目标现状。字典只读，用户和组织继续由各环境维护。 |
| 系统保护种子、菜单、权限、角色及绑定 | 保留原迁移与授权通道。导入、导出均须拒绝受保护对象。 |
| 工单、评论、通知实例、任务实例、审计记录、附件对象 | 由运行环境持有。晋级不携带这类数据。 |
| 分派规则、字典写入、消息模板与规则、通知通道、系统参数、富媒体对象 | 按真实需求逐类扩展。每类单独核定引用、权限、密钥和补偿语义。 |

受保护种子按项目明确登记的对象判定。`is_system` 是部分表的保护信号，已有迁移还包含未带该标志的种子。首版开工时核对类型和模板种子，包括 `incident`、`request` 的边界，并明确哪些可编辑默认项允许按包维护。显式选择 code 也必须经过保护检查。

## 2. 首版包契约

### 2.1 形状与身份

包包含格式版本、导出程序版本、来源快照标识、实体清单、稳定引用和所需能力。导出使用一致的读快照，留下操作者、包摘要和实体键的操作记录。来源版本用于追溯，目标版本由目标端生成。类型主体与 B0-3 的已发布快照同形，包含 `states`、`transitions`、`transition_meta` 和完整字段 schema。类型元数据与模板按件 7 所需字段随包携带。部署所需的跨环境引用用具名结构表达。

类型按 `ticket_types.code`、字段按 `(type_code, field_key)`、模板按未软删行的 `ticket_templates.code` 定位。源端自增 ID、版本、审计操作者和生成字段属于来源信息或本地数据。导出端描述期望配置，目标端生成新增、发布、更新、无变化或阻塞操作。包中省略的实体不触发删除。

具体序列化格式、规范化规则、大小限制和版本兼容策略随 B3 开工冻结。规范化保留影响运行与展示的顺序，包括转换出边、字段和选项。包的格式版本和目标运行时能力分别校验。

### 2.2 引用与能力

- 用户用 `employee_no`，组织用 `code`，按目标环境校验存在性、有效性和适用范围。模板的 `org_path` 由目标组织派生。模板已有的类型和组织绑定变化应在计划中报冲突。目标写入归因于本次操作者，来源作者单列作溯源。
- 字段选项的 `dict:<code>`、表达式中的 `lookup_dict` 均是依赖。预检验证引用的字典、所需选项和启用状态。首版遇到无法静态解析的动态引用时拒绝。模板的 `default_fields` 按目标类型 schema 和建单实际消费形状验证，覆盖 `description` 与 `custom_data`。
- 用工单 `ActionRegistry` 核对转换动作，逐种校验参数。`notify`、`cc`、`reassign` 中的人员、消息模板等引用须识别并解析。`spawn_task` 还须核对目标 taskrunner 动作和所需回调能力。`jobs.Registry` 只用于核对相应回调。表达式须经过语法检查并核对目标实际装配的函数，包括 `lookup_dict`。
- 无法解析、无权限使用、目标不支持的引用和参数结构均阻塞计划。首版允许普通 Markdown，遇到项目附件引用须阻塞。富文本中的站内贴图用 `internal/service/ticket/richtext.go` 的 `ExtractFileRefs` 识别，模板 `custom_data` 中的文件引用按字段类型单独检查。资产搬运留待独立设计。

## 3. 计划与应用

### 3.1 Plan

目标端只读检查，在同一读快照内完成规范化对比、引用解析与部署预检。报告列明目标标识、包摘要、实体级动作、字段 diff、当前发布版本、相关版本的在途计数与阻塞项。引用解析失败、模板不可变绑定变化和保护种子都在计划中明确显示。目标存在会被晋级覆盖的未发布草稿时，先通过管理流程处置草稿，再重新计划。

将审批绑定到确定的计划标识。计划摘要至少覆盖包摘要、目标环境及数据库标识、规范化变更、实体基线（含不存在预期）、解析后的引用及其相关状态。审批走可信发布流程，执行时以该流程记录的审批标识及计划摘要为准。

### 3.2 Apply

1. 校验执行身份、审批记录、包与目标绑定。在同一写事务内重读并核对计划基线，使用与管理写入协调的锁或 CAS。预计新增的自然键用唯一约束兜底，发生并发冲突时按漂移处理。目标、草稿、当前发布版或关键依赖有漂移，整包拒绝，重新生成计划并审批。
2. 有变化的类型定义走 B0-3 的 deploy 路径生成新快照版本。已有工单继续使用各自固定的版本，新工单使用新发布版本。在途迁移仍走 B0-3 单独流程。内容等价时既不改定义，也不生成版本。仅模板变化时只更新模板。
3. 整包配置写入和成功审计同事务提交，任何实体、校验或成功审计失败均回滚。导入复用 authoring 和 deploy 的领域校验，需查库的校验及写入复用同一个事务句柄。`internal/repository/ticket_repo.go` 的 `ReplaceTypeFields` 当前自行开事务，实施时需提供可在外层事务执行的路径，并保留现有调用语义。
4. 生产执行使用可追溯的运维身份和必要的最小数据库权限。审计记录实际执行者、审批引用、目标、包和计划摘要、实体键及新旧版本，使用现有审计字段承载。失败通过独立的运维记录留痕。清单、计划、日志和审计不得包含密钥或完整 webhook URL。

相同内容在目标上重新 plan 后为无变化。旧的变更计划遇到已提交的版本也要按漂移处理。命令支持同一安全语义，避免用全局覆盖参数绕开审批、引用或版本检查。

## 4. 提交后补偿

在写入时保存受控的变更前值和新建实体清单，关联审批、计划与发布版本。首次上线前应能生成并核准定向补偿计划，并在当前目标状态上重新验证。

- 已发布类型可用前一份有效定义走 deploy 发布补偿版本。已经绑到新版本的工单继续使用其版本，确有迁移需要时走现有在途迁移流程。
- 模板按前值恢复，新增项在无冲突时停用或撤回。已有引用、并发修改或不可变绑定引起冲突时停止，交由审批流程处置。
- 备份与恢复按 [运维手册](../ops/runbook.md) 和 [备份手册](../ops/backup.md) 执行，适用于灾备。导入旧包只能恢复它表达的配置内容，不能撤销本次所有变更。上线前核对备份可用性。PITR 须以目标环境已验证的物理基备和 WAL 链为前提。

## 5. 首版交付与排期

| 时点 | 工作 |
|---|---|
| **Phase6 重规划 / 件 7 实施前** | 在全项目重规划中复核需要和范围，确认实施后确定引用、审批与补偿契约，并在 05 号、06 号件 7 和控制台登记。 |
| **确认实施后的交付批** | 原方案依赖 B0-3 快照、部署预检及发布语义，类型、字段、转换元数据、模板的导出、计划、应用与补偿范围在重规划时确认，开工前按完整验收范围复估。 |
| **首次生产配置晋级前** | 在隔离目标完成 §6 的往返、负例和补偿演练，运行四档验收并回填控制台。生产晋级以此为门槛，实际阶段与实施顺序以重规划为准。 |

原首版候选入口为独立的一次性 CLI 子命令，是否采用随重规划确认。可以参考 `cmd/server/main.go` 的子命令分发与 `cmd/server/reset_password.go` 的参数解析形态。生产权限和审计按 §3.2 单独设计。命令名、参数和审批载体在实施时冻结，未知子命令及参数错误应明确退出。界面和 HTTP 能力留在后续单独评审，届时按 `ticket:type:manage` 及目录授权规范接入。

扩展分派规则时，稳定标识和跨环境匹配顺序须一并设计。当前 `internal/repository/assignment_rule_repo.go` 的 `MatchOnCreate` 用 `priority,id` 排序，同优先级不能按源 ID 照搬。新增迁移届时按[项目控制台 §4 迁移地图](../review/11-project-control.md)取号。扩展通知通道时，生产凭证继续由目标环境管理，导出省略整段 webhook URL，更新保留目标绑定，启用前核验目标凭证与运行时通道能力。对象存储搬运需要单独定义失败和补偿边界。

## 6. 首次生产晋级验收

1. 在已迁移、与来源使用不同自增 ID 的隔离目标做导出 → plan → apply → 再导出，比较规范化配置和目标引用。先建在途单，再晋级有变化的定义，验证旧单仍按原流程及字段运行，新单用新快照。单独验证同包重放和仅模板更新。
2. 覆盖错目标、包或审批不匹配、并发管理修改、缺失或失效引用、目标能力缺失、受保护种子、附件引用和模板绑定冲突。对多实体包注入后段写入与审计失败，核验整包回滚。
3. 演练提交后的定向补偿，验证未覆盖随后产生的工单或无关配置。记录批准计划、变更审计、补偿结果与四档 `make acceptance` 结果。实施批将已验证的操作序写入运维手册，能力状态回填 [项目控制台](../review/11-project-control.md)。
