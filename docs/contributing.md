# 参与贡献

欢迎提交可复现的问题、实际使用场景、文档改进和范围明确的代码改动。当前能力与未来方向分别见[README](../README.md)、[路线](roadmap.md)和[控制台](review/11-project-control.md)。

## 先确认范围

小文案修正可直接提PR。提功能建议时，写清谁遇到了什么问题、会输入什么、预期看到什么结果，并举一个可以验收的例子。已有的安全检测、资产、自动处置或知识平台能办的事，优先通过接口接入。大型模块、协议或依赖先讨论范围。

公开问题使用合成数据，移除真实身份、公司标识、内部地址和秘密；附版本/提交、复现步骤、预期、实际结果及脱敏日志。不要通过公开issue传播漏洞细节或凭据；正式私密安全报告渠道尚待单独配置和公布。

## 本地开发与PR

1. 阅读[开发指南](guides/development.md)与对应模块，安装当前worktree的`make hooks`。
2. 每个写任务使用独立分支/worktree和运行资源；本项目测试数据可重建，仍须核清项目与在途任务归属。
3. 遵守[工程公约](standards.md)：先写可验证预期和失败测试，再做最小修改，不弱化已有回归断言。
4. 使用显式文件路径提交，核对提交文件，不带其他任务的修改。
5. 通过适用检查后提交小PR；政策允许单维护者在必需检查通过后合入。

本地检查分三档，按改动内容选对应检查。远端保护和其余组合 CI 以实际配置的启用情况为准。[开发指南 §4](guides/development.md#4-交付前验证)列出每档的检查步骤。

## 提交元数据与AI署名

本节是[工程公约§12-9](standards.md#12-工程与协作纪律)的元数据格式说明，不能新增、覆盖或豁免测试、授权、职责或准入要求。仅改本节工具名称、格式和示例且无运行消费者时，按文档档保留提交规范、文档链接和人工语义复核；同时改控制台仍跑规划针对检查。实质规则变化回到受保护权威文件同步，混合候选按最高档，不按“纯文档”标签免测。

- 对形成提交内容的实质AI辅助，在正文后的footer记录`AI-Assisted-By: <工具名>`；仅审阅用`AI-Reviewed-By: <工具名>`。
- 多工具按实际角色逐行列出，纯问答或未采用的输出不必列，不自动附上所有可用工具。这两种footer是项目自定义元数据，不作为GitHub共同作者展示。
- `Co-authored-by: NAME <EMAIL>`可选，用于实质参与产出且有可核实身份的共同作者；AI工具使用官方公布、可核实的身份邮箱，不编造`zcode@agent`等地址。需要关联GitHub账号时，邮箱须与对应账号绑定，见[GitHub多作者说明](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors)。

按实际参与填写，例如：

```text
AI-Assisted-By: <实际辅助工具>
AI-Reviewed-By: <实际审阅工具>
```

署名不替代实际贡献、本人理解和验证证据；本节不引入自动署名、CI或钩子检查，也不要求追改历史提交。

## 评审需要什么

PR包含改动摘要、影响面和验证证据；说明接口、迁移、权限、配置是否变化，实际执行结果及未覆盖路径。文档和截图区分当前产品、规划与合成示例，不把旧结果标成新候选执行。

公开能力描述同步中英README。详细文档以中文为主，不要求普通贡献翻译全部历史材料。兄弟仓按各自指南及同一生态公约执行。
