## 3. PostgreSQL 高可用

### 3.1 方案

- **云托管 Cluster（2 节点 + VIP）**（README §4 已决策）：主备自动切换，VIP 漂移，应用连接串不变。
- 自建 PG 备选：流复制 + Patroni + VIP —— ⚠️ 运维成本高，仅当无云托管条件时考虑。

### 3.2 应用侧要求

- 连接池（pgxpool）配置：`pool_max_conns` 按副本数分配，避免连接打爆。
- 只读副本（可选）：报表（7e）可走只读副本分流（⚠️ 延迟窗口，报表缓存已兜底）。

### 3.3 备份

- 定期备份（`pg_dump` 或 PITR）——Phase 3-min 也要求（README §3.1）。
- 恢复演练：每季度至少一次，验证可恢复。

## 4. Redis 高可用

### 4.1 方案

| 方案 | 说明 | 建议 |
|---|---|---|
| **Sentinel** | 一主两从 + Sentinel 监控，客户端 failover | ✅ **建议**（简单，Redis 在项目为辅助角色） |
| Cluster | 分片 + 自动故障转移 | ⚠️ 按需（数据量大/需分片时） |

### 4.2 影响面

- Redis 承载：会话/RT 轮换/Token 黑名单/登录限流（Lua）/Asynq 任务后端。
- **Asynq 依赖 Redis**：Redis 故障时任务执行暂停，但 **L1 事件事实在 PG，恢复后重放**（ADR-001/002 红线）——不丢事实。
- ⚠️ 鉴权链路（黑名单、`user:disabled`、登录限流）Redis 故障仍 **fail-close 503**（design-decisions §1.5）——HA 需覆盖。

## 5. Nginx 负载均衡

```nginx
upstream zhuzhao {
    server app1:8080;   # /health/ready 通过才在 upstream
    server app2:8080;
}
server {
    listen 443 ssl;
    # TLS 终止 + 反代
    location / {
        proxy_pass http://zhuzhao;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location /health/ {
        proxy_pass http://zhuzhao;   # 或直连各副本
    }
}
```

- 探针：`/health/live`（存活）+ `/health/ready`（就绪，含 PG/Redis 依赖检查）——LB 自动摘除不健康副本。
- 优雅关闭：Phase 1 信号处理 + 完成当前事务；advisory lock 随连接释放（W1）。

## 6. 故障演练场景

| 场景 | 预期 |
|---|---|
| App 副本崩溃 | LB 摘除；请求走存活副本；L1 事件由存活的单消费者续跑 |
| PG 主库故障 | 云托管 VIP 切换；连接短暂中断后恢复；事务重试 |
| Redis 故障 | 鉴权 fail-close 503（按设计）；恢复后 Asynq 任务重放 |
| 单副本滚动发布 | 先摘再发再挂，零中断（需 ≥2 副本） |

## 8. 验收用例

| # | 用例 | 通过标准 |
|---|---|---|
| HA1 | 多副本负载 | 请求分发到 ≥2 副本；单副本摘除后其余正常 |
| HA2 | 探针摘除 | ready 异常副本被 LB 摘除，不承接流量 |
| HA3 | PG 主备切换 | 主库故障 → VIP 漂移 → 应用自动恢复（连接池重连） |
| HA4 | Redis Sentinel | 主节点故障 → 从提升 → 功能恢复 |
| HA5 | 崩溃不丢回归 | ha 拓扑下 L1 事件仍不丢（复用 MI3） |
