# 17 - M-UAA：公司统一权限平台对接（岗位权限治理）

> **状态**：已立项（2026-10-09，所有者拍板；触发=公司《岗位权限治理指南》下发，对接形态明确）。**排期待定**（建议 phase5 后端批后或并行——MQ 基建独立于 phase5 各段）。
>
> **前置（内网后）**：公司平台产品/实例申请、MQ 资源申请（交换机×2+队列×3）、UAA 应用注册。
>
> **基线合规**：本文件以通用抽象表述对接对象（standards §1.1——公司平台名/联系人/内网 URL 不落本仓）；契约细节（报文字段/队列命名/VHOST）以公司指南原文为准，实现者内网可查。

## 0. 一句话

对接公司统一权限平台：认证走 OAuth2.0 授权码（§24 现成设计），权限数据面走 MQ（资源上报器+三消费者），三层鉴权判定**零改动**；量级 ≈ 2–4 周；**独立部署保证**（§5 三条设计要求——弃用 UAA 后系统功能零损失）。

## 1. 公司权限治理模式解读（IGA——业界标准形态）

| 层 | 公司 UAA 职责 | zhuzhao 职责 | 对应业界概念 |
|----|-------------|-------------|-------------|
| 认证 | 统一登录（OAuth2.0 Code 优先推荐/OIDC/SAML2.0） | SSOProvider 端口 → 换发本地 JWT | Federated Authentication |
| 权限目录 | 托管各系统上报的资源清单（菜单/功能/API） | **资源上报器**（词表变更 → MQ 推送） | Resource Registration |
| 分配治理 | BPM 权限申请审批 + 入转调离自动授权/回收 + 权限专员 | 消费分配结果，同步本地 | IGA：JML Automation + Access Request |
| 分发 | MQ 全量下发（账号/角色关系/资源关系） | 三消费者 → 本地同步 | Provisioning |
| 数据权限 | **六场景全部"业务系统自管"**（指南原文） | L2 三层判定照常 | Application-level Authorization |

> **指南背书的关键结论**：数据权限六场景（本位/汇报/组织/人员配置/角色配置/临时组织）**全部由业务系统自管**——公司规范正式确认"行级判定留本地"。zhuzhao L2（org ltree scope+委托轴+ticket_visibility）**覆盖甚至超出**公司六场景（委托链/可见性策略是公司模型没有的）。唯一新增义务：权限配置表定期回传（下发数据湖，治理/分析用）。

## 2. 对接件清单（六件）

| # | 对接件 | 内容 | 量级 | 性质 |
|---|--------|------|------|------|
| 1 | SSO 登录 | OAuth2.0 授权码 → 换发本地 JWT（§24 现成设计）；SLO 登出有标准形态（先清应用 token→调 UAA logout→跳 UAA 登录页） | 2–3 人日（原 M-SSO 工作量并入本里程碑；**mock IdP 可离线先行**，真实接入=换 config） | 加法 |
| 2 | MQ 数据面基建 | RabbitMQ client（**新依赖 amqp**——依赖决策：公司统一 MQ 集群，本仓只做 client）+ 消费框架（复用 cron advisory lock 经验） | 3–5 天 | 新基建 |
| 3 | **资源上报器** | menus/menu_apis 词表变更 → MQ 推送（映射：目录/菜单→type=1、按钮→type=2、menu_apis→type=3；code/parentCode 树形天然对齐）；触发=**定时全量对账**（W1 只读化后 menus 无业务写路径，写路径钩子不存在；对账周期随 M-UAA 启动拍板） | 3–5 天 | 新增 |
| 4 | 账号消费者 | PERNR → 本地 user 建/停（source=hr；JIT 对齐 §24）；离职自动停用（入转调离自动化落地面） | 2–3 天 | 新增 |
| 5 | 角色-资源关系消费者 | UAA 下发"用户×角色/菜单"关系 → 本地 Casbin 绑定**覆盖式同步**（AssignMenus 转应急通道）；**覆盖范围待拍板**：仅覆盖 source=uaa 绑定，superadmin+source=local+本地自建角色**豁免**（防 UAA 误下发冲掉 break-glass） | 3–5 天 | 新增 |
| 6 | 数据权限配置回传 | L2 权限配置表（用户-org-scope）定期导出推 UAA/数据湖（公司管控逻辑义务，轻量定期任务） | 2–3 天 | 新增 |

> **总账**：件 2–6 合计 ≈ **2–4 周**；原"2–3 人日"估算作废（仅覆盖认证版 SSO）。

## 3. 对 S3/phase5/phase6 的影响：零

- 三层鉴权判定引擎/词表/L2 语义/审计 **零改动**（公司指南自证 L2 自管）
- S3a/S3b 排位不变（S3a 排基线交付后；S3b 等场景——与 UAA 无关不混）
- phase5 十段/phase6 四段 **零改动**（M-UAA 是独立里程碑，正交于业务段）

## 4. 独立部署保证（三条设计要求——本节是本文件最重要的一节）

> **问题**：按公司方式实现后，如果后续不使用这套方案（换产品/弃用/回退独立部署），系统还能独立运行吗？
>
> **答案：能——且这是设计结构保证的，不是运气**。核心原理：**UAA 只在数据来源层（谁推送角色绑定），不在判定路径层（每次请求怎么判权限）**。

### 三条设计要求

| # | 设计要求 | 保证什么 | 违反后果 |
|---|---------|---------|---------|
| 1 | **本地事实源**：UAA 下发的角色绑定写**本地 Casbin 绑定表**（判定读本地），不做成"每请求远程查 UAA"的 PDP 模式 | 判定路径不经过 UAA——运行时零依赖 | 若做成 PDP → 运行时绑定 UAA，可用性/延迟/自主权全部被锁 |
| 2 | **同步可开关**：MQ 消费者带 config 开关；关停后系统运行在"最后同步状态"（角色绑定冻结） | UAA 故障/弃用不断已有会话与权限 | 若无开关 → UAA 故障影响本地判定 |
| 3 | **账密双轨保留**：本地账密+superadmin 永远可用（§24 break-glass） | UAA 停用时有备用登录通道 | 若只留 SSO → UAA 停=无法登录 |

### 对既有系统的改动面：零

> **判定路径零改动**（2026-10-09 确认）——三层鉴权引擎（L1 Casbin/L2 registry/L3 状态机）、账密登录、JWT/RT/黑名单/设备吊销、menu_apis 词表、PAT、审计+判定日志、组织树 ltree、2c 委托/ticket_visibility **全部保留**。M-UAA 是**纯加法**（新增 MQ 消费者/上报器/SSO 端口 = 新文件+config 挂点+Wire 注入），不改任何已有判定逻辑。

### 两个管理页的使用方式变化

| 页面 | 现状 | M-UAA 后 |
|------|------|---------|
| AssignMenus 角色分配页 | 管理员手配角色绑定 | **常态：只读展示**（UAA 下发同步的本地绑定，标注"由公司统一权限平台管理"）；**应急：UAA 不可用时重新启用手配** |
| 用户管理页"新增用户" | 管理员手建 | 常态下 MQ PERNR 自动建号，此入口降为应急（本地账号/superadmin） |

### 弃用 UAA 的最小操作步骤（演练清单）

| 步骤 | 操作 | 影响 |
|------|------|------|
| 1 | config 关闭 SSOProvider → 登录页恢复本地账密 | 已有账号照常登录 |
| 2 | 关闭 MQ 消费者（config 开关） | 角色绑定冻结在最后同步状态 |
| 3 | 重新启用 AssignMenus 应急通道 | 角色变更回归管理员手配 |
| 4 | （可选）清理 MQ 连接配置 | 部署简化 |

**全程零代码改动、零数据迁移、零功能损失**（损失=入转调离自动化退回手配——即回到 2026-08 之前的状态）。

### 禁止的反模式（与公司方案不触发，但要防将来引入）

| 反模式 | 为什么危险 |
|--------|-----------|
| 每请求远程查 UAA 权限（PDP 模式） | 运行时绑定 UAA；延迟/可用性/自主权全部被锁 |
| 权限数据只存 UAA 不落本地 | 数据主权丢失；UAA 停=系统瘫痪 |
| 会话 token 由 UAA 签发且本地不校验 | 认证被锁死；本地会话安全体系（RT 重用检测/设备吊销）失效 |
| 业务逻辑硬编码 UAA API 调用 | 代码耦合；换产品=大改 |

**公司 MQ 下发模式不触发以上任何一条**——资源上报是推数据出去、角色关系是写本地表、判定在本地。这是选择"照公司计划做"的架构安全前提。

## 5. 与 S3a 事件面的关系（正交，不混淆）

| | 事件面（进程内订阅钩子） | MQ 数据面（UAA 对接） |
|---|----------------------|---------------------|
| 范围 | zhuzhao 进程内（ticket 状态变更→通知/风险关单/timeout 基准） | 跨系统（zhuzhao ↔ UAA） |
| 协议 | 进程内接口（编译期检查） | MQ（RabbitMQ）+ HTTP（SSO） |
| 可替代性 | 不可替代（平台内部机制） | 可替换（UAA 停用→本地分配兜底） |
| 关系 | **正交**——事件面管进程内分发，MQ 数据面管跨系统身份与分配 | 互不依赖；资源上报器独立于事件面（W1 只读化后 menus 无写路径，仅**定时全量对账**） |

## 7. 量级与排期

- **M-UAA 合计 ≈ 2–4 周**（MQ 基建 3–5 天 + 资源上报器 3–5 天 + 账号消费者 2–3 天 + 角色关系消费者 3–5 天 + 数据权限回传 2–3 天 = 13–21 天；**另有 SSO 登录 2–3 人日**——原 M-SSO 工作量随件 1 并入，全含 15–24 天 ≈ 3–5 周）
- **验收分两档**：SSO 件 = mock IdP 走通完整回调链 → 自有 JWT 签发 → 三层鉴权行为不变（**不依赖内网，可先行开发验收**）；MQ 数据面 = 内网联调（三消费者走通 + 资源上报验证 + SLO 登出打通）——真实接入 = 换 config，不返工
- **排期**：phase5 后端批后或并行（MQ 基建独立于 phase5 各段，可穿插）；前置=内网（MQ 网络可达 + 公司平台产品/实例申请流程 + 契约细节）
