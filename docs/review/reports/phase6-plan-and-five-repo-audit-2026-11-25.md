## 1. 结论

- **审计者主观评分：62.5/100。** 只看代码与设计约 68 分，只看交付与可控性约 55 分，属于“底子好，但有几处系统性问题要先处理”。这是审计者的分档判断，不是项目评级或验收结论；这次是按风险挑重点的抽样审查，不是逐行审查。覆盖范围和评分依据见 §9。
- **方向成立。**
  - 定位是“专业工具负责发现和执行，本平台负责汇总结论、管流程、留证据”，适合单人维护。
  - “模块化单体 + 进程外扩展点”的架构适合当前阶段。
  - 工程底子扎实：Go 静态检查全部干净；前端开启严格类型检查，被跟踪代码 lint 零问题；认证主干和存储链路设计严谨。
- **已抽查的路径里未确认新增高危问题。** 这个结论不覆盖以下部分：新风险域代码、公式求值，以及所有动态验证（§9.1）。另有：
  - 一个授权缺陷已修复，但修复还没进 main（§2.1 第 1 条）；
  - 几项凭据和服务间认证的中等问题（§3.6）。
- 以下均为**审计建议，是否作为开工条件待所有者裁决**：
  - **开工第 10 项前**，建议先处理 §2.1 的 5 件事：
    - 合入 C05 修复；
    - 分别补证 PR 检查、合并提交和组合签收；
    - 确定本批的合入安排和签收责任；
    - 登记迁移缺号；
    - 整理环境台账。
  - **开工第 12 项（任务与清单联动）前**，建议补 §2.2 的 5 项。§1、§5 和控制台都引用这同一份清单：
    - 任务动作改为白名单；
    - 服务间身份按路由区分，签名升级到 v2；
    - 后台服务主体的授权模型；
    - 可靠投递底座：最小 R01，加统一回执与 outbox；
    - 堵住旧读入口的旁路，并给敏感写留下审计事实。
  - **申请入网前**（§2.3）：
    - 离线交付包和单例失格退出还不满足条件；
    - 回退已有手册步骤（runbook §6.5），缺的是带数据的回退演练。
- **最大的问题不在代码，而在两处**：
  - **投入比例。** 首版 97–151 个工程日中，“风险到整改”本身只占约 11%，其余多是平台化接缝；而这条主线至今没有真实用户用过。

- **主仓现在不建议拆仓，也不建议拆服务**（§3.7）。

### 2.1 建议开工第 10 项前处理的 5 件事（待所有者裁决）

**1. origin/main 带着一个未登记的 C05 缺陷（AUD-01）【已核：代码】**

- **origin/main 已有的检查：**
  - 入口认证 `internal/middleware/jwt.go` 的 `JWT` 先读数据库里的安全快照：账号已删除、已停用，或令牌代际对不上，都直接拒绝。数据库与 Redis 投影不一致时返回 503。

- **缺口：** 请求通过入口认证后，以下操作进入守卫事务时，不会再核验本次使用的凭据（Bearer 的令牌代际、PAT 的状态和有效期）：

  - 管理员重置；
  - 按原操作号查询。

  如果入口检查之后、事务提交之前凭据被撤销，这次操作仍可能写入（推断，未复现）。后续验证应针对这个并发窗口，不针对 Redis 投影滞后，因为入口已按数据库事实判断。

  - 合同层过度投入：CE01–05 估算 52–80 天，而对应代码层的 Hook、Sender、webhook 合计不到 500 行。
  - 可靠投递底座却欠着，收敛方式见 §2.2。
- **拆仓：现在不拆仓，也不拆服务（A2-06）。**
  - 工单命令在 IAM 守卫的同一事务里重读授权；组织移动在同一事务里改工单路径；17 个工单/风险文件直接查 IAM 表。现在拆，等于重做 C04/C05。
  - 通知不到 200 行，存储 852 行，拆出来没有收益。
  - utils 只有约 1.9K 行，已经出现三个版本漂移，可见多仓维护的成本。
- **“自由拼接能力”分三层实现：**
  - 进程内按配置启停模块；
  - 模块之间只走 Port 或 DomainEvent，并由守卫强制；
  - 外部能力走 X01/X02 连接器。
- **何时重新评估拆分（A2-07）。** 前提是：候选模块与其他领域的同事务调用为 0，且 repository 已按领域拆开。在此前提下，满足以下任一条件即可重新评估：
  - 每月被其他模块的门禁阻塞 3 次以上；
  - 资源占比超过 50%，且扩缩曲线与核心不同；
  - 每季度造成 SLO 违约 2 次以上；
  - 需要在独立网络区或凭证域运行。

  最可能先满足条件的是风险域，前提是先把风险代码移出 ticket 包。

### 3.8 前端设计

**发现（A6）**

- **同一状态的颜色有 4 套写法【已核】。**
  - 风险“已接受”用了绿色 success，会被读成“已解决”。
  - 工单优先级“低”也是绿色。
  - “待复测”在风险页是 warning，在工单页是 info。
  - 风险等级只显示纯文字，期限没有逾期标记。
- **风险页要手填数字 ID【已核：代码】。**
  - 派单工具栏要手填“目标组织 ID”和“整改类型代码”。
  - 登记对话框要手填“风险管理组织 ID”“受影响组织 ID”“责任人 ID”；指定责任人是另一个单独的操作。
  - 详情里的组织显示为数字。
  - 派单前，页面上看不到可辨认的姓名和组织名，派单人难以确认到底派给了谁。
- **工单详情页结构松散。**
  - 8 张卡片竖着堆叠，没有时间线。
  - SLA 只要工单没关就一直标红，与是否真的逾期无关【已核】。
  - 逐资产办理和复测藏在 860px 固定宽的弹窗里，弹窗内含 `custom_data_patch`、“通过（A）/打回（B）”这类实现术语。
- **导航不贴合角色。** 管理员的一级菜单有 9 项，“系统管理”排第 2；办理人的侧栏里没有“我的待办”和“待复测”；布局切换器常驻顶栏；页脚仍开着【已核】。
- **对比度不足。** 次级文字色 `#7a879c` 对白底只有 3.64:1【已核】，首页计数最低 2.19:1。
- **没有统一的样式变量。** 字号有 9 种，圆角 17 种，硬编码色值 47 处。
- **重设计方案的方向对，有三处排期问题和一处遗漏。** 方向：单侧栏加身份顶栏、页面合同、四态、逐页清单。
  - B2 风险页先于样式变量和页面模板上线，等于先造后拆。
  - U02 一个包里装得太多。
  - U06 一次改 27 页，是大爆炸式改造。
  - 原型里没有风险域、复测队列和接受审批。

**建议**

- **做薄的设计系统**：一套样式变量，8 个业务组件（状态标签、风险等级徽章、期限徽章、证据卡、时间线、人员/组织选择器、批量操作条、状态反馈区），3 个页面模板。放在 `src/components`，不换组件库。
- **关键语义色**（亮色主题；对比度按 WCAG 相对亮度公式计算）：

  | 语义 | 文字 / 底色 | 对比度 | 用途 |
  |---|---|---|---|
  | 次级文字 | `#667085` | 4.97:1 | 替换现在的 `#7a879c` |
  | 待复测 | `#0e6b80` / `#e6f5f8` | 5.47:1 | 新增复测色 |
  | 已接受 | `#344054` / `#eef0f4`，虚线边加盾牌图标 | 9.17:1 | 风险接受，临期转提醒色，过期转危险色 |
  | 成功 / 提醒 / 危险 | `#276b39`、`#8a4b08`、`#b42318` | 5.9 / 6.2 / 5.9 | 只用于关闭/通过、临期、逾期/打回 |

  完整色板（含暗色）、字号阶梯和各角色的目标菜单树见 A6 原文。
- **改造路线**：
  - S0 速赢；
  - S1 样式变量与语义词表；
  - S2 导航重组（需主仓迁移）；
  - S3 风险列表与办理页样板；
  - S4 工单详情；
  - S5 首页工作台；
  - S6 按页族拆成 4–5 小批推广。

  每一步都有可验收的出口。
- **代码层先打地基（A5）**：带类型的 http 封装、权限码常量表、统一的竞态守卫、用 features 层切断 risk 与 ticket 的互相引用、Element Plus 单独分包。然后用菜单的 component 字段指向 v2 页面，逐页替换。
- **速赢清单（1–3 天）**：
  1. 次级文字色改为 `#667085`。
  2. “已接受”和“低”改用中性色。
  3. SLA 分三档显示，优先级显示文字。
  4. 首页计数改用主文字色，emoji 换成线性图标。
  5. 筛选下拉加上维度标签。
  6. 关闭页脚，布局切换器移进头像菜单。
  7. 暗色主题补齐填充色变量。
  8. 风险等级改为徽章，责任列显示姓名。
  9. 对话框宽度改为 `min(原宽, 100vw - 32px)`。
  10. 弹窗去掉实现术语。

### 3.9 工程化、CI 与测试（A9）

- **做得好**：
  - `quality-gate` 汇总 job 适合作为唯一的必需检查。
  - action 按 SHA 钉版本，govulncheck 同时扫源码和实际 ELF。
  - 集成测试已进 CI，并带 `-race`。
- **直接 push 到 phase6 不触发 CI【已核：配置与运行记录】。**
  - Core 和 UI 的 push 触发列表里没有 phase6，所以已推送的合并提交本身没有运行记录，本地 17 个补修提交也没跑过 CI。
  - 进入 phase6 的 PR（Core #38、UI #17）跑过 PR 检查并全部通过，见 §2.1 第 2 条。
  - 建议把 push 触发统一成 `"**"`，并分别记录 PR 检查、合并提交检查和组合签收。
- **新分支首次推送会被历史合并提交卡住（有条件）【已核：实验】。**
  - 发生条件：push 事件创建了新分支（before 为全零），且分支历史含 main 上 GitHub 默认生成的合并提交 `d25367c8`。这时 commit-policy 的检查窗口只排除基线 `3ca64022` 的祖先，会把这个不合 Conventional 格式的合并提交算进去。
  - 主会话用本报告所在的文档分支模拟新分支首推，208 个提交中 1 个不合规，就是 `d25367c8`。
  - 同一分支的后续 push 和 PR 事件只检查新增提交，不受影响。
- **最关键的门禁没有机械约束。**
  - 四档 acceptance（254 项）、迁移往返、UI Playwright 都不在 CI 里。
  - 据助手的 gh 查询（主会话未复查），五仓 main 都没有分支保护，近期合入的 PR 没有评审记录。
- **重复与上手成本。**
  - 治理脚本在五个仓逐字节拷贝【已核 md5】。
  - 跨仓组合验证不可复现。
  - 新会话上手卡点多，例如 acceptance 默认指向共享 dev 栈，要手设 8 个环境变量。
- **蓝图：**

  | 分类 | 内容 |
  |---|---|
  | 必须做 | 分支保护，并把 quality-gate 设为必需检查；CI 触发统一为 `"**"`；修复首推误报，只允许 squash；utils 先打 tag 再钉版本；组合清单加组合冒烟 CI；Renovate；覆盖率合并单测与集成口径；staticcheck 最小规则集 |
  | 可简化 | 治理脚本收成单一来源，删除遗留的 `go-security.yml` |
  | 暂不需要 | monorepo、负载测试与混沌工程、OTel 全链路、多环境 CD |

- **版本策略**：多仓 + 组合清单。`go.work` 只在本地联调时使用，不提交。

### 9.2 结论有多可信

- **发现与复核数量。** 两轮共约 140 条发现，各切片之间有重叠。主会话亲自复核了约 45 条，就是正文里标【已核】的条目。
- **复核项怎么挑的。** 没有随机抽样，按两条标准挑：
  - 会影响开工、合入、入网判断，或严重度较高；
  - 能在代码、Git、配置或运行记录里直接核对。

  所以复核结果不能推及其余条目。未标【已核】的条目是分项助手的结论，未经主会话核实，使用前应自行核对。
- **复核本身也有漏。**
  - 主会话首轮复核时修正了 6 处，补充说明 1 处（§4.1）。
  - 随后的交叉复核又发现：有 3 条已标【已核】的结论只核了核心事实，周围的表述写过了头，其中一条（CI）是事实错误；主会话自己的一处“修正”也改错了，已撤回（§4.1、§4.2）。
  - 也就是说，【已核】只代表核心事实成立，不代表整段表述都对。
- **独立性有限。** 两轮都由 Claude 系列模型完成，盲区可能相近。所有者之前请其他模型做过的一轮，以及本次三位 Codex 助手的交叉复核，可以与本报告互相补充。
