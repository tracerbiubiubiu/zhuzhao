# 第 16 项首批模拟扫描与人工补核隔离验收

基线为 Core 远端主线 `6835f2738adbb303c61b721de927a3b1639a24d0`。本地候选固定到两份产品源码及一份集成用例的 SHA-256 清单。真实 HTTP 专项从同一份候选源码以 Go 1.27.4、`GOWORK=off` 构建并运行。标准四档另用独占 PostgreSQL、Redis 和 RustFS，源码摘要与 HTTP 专项一致。 [首批计划](../../planning/phase6-step16-scan-intake-plan.md)

## 基线实证与补修

- 复用受控来源的 AK/SK 上报、单事件去重、同序冲突隔离、数字旧序号拦截、人工评估及两类回执。基线真实进程验证 11 组场景，复现四种异常。无可比序号的等时及旧时观察可推进镜像，待核重投遗漏已存原因，无范围首写和已撤范围的原操作者重投均在未指派风险上返回 500。
- `internal/service/risk/report.go` 的 `applyObservation` 读取已锁镜像。两条观察无法按序号比较时，用本次收件的数据库观察时间判序。迟到记为 `stale_observed_at`，等时记为 `ambiguous_observed_at`，存量镜像缺观察时间记为 `missing_observed_at_baseline`。这些事件只落收件记录。正常推进和数字序规则继续复用。
- `replayOrQuarantineEvent` 在同源、同事件、同内容时返回原接入号、处理状态和已存原因。人工按原接入号核对原分类。授权谓词 `internal/repository/risk_item.go` 的 `riskVisiblePredicate` 将未指派视为责任人分支不匹配，L2 不可见时按原合同返回 404。

## 冻结候选的真实 HTTP 结果

独立助手在 PostgreSQL、Redis 与实际 Core 进程上复验 13 组场景，全部通过。验收使用虚构风险、资产、操作证据与专属账号。

- 缺少有序源必填序号只生成待核回执。无可比序号的合成来源追加两条等时及迟到观察后，仅新增两条收件行，风险、镜像、冲突、操作和历史的计数均保持原值。两条观察均无风险回链。复投和获权 GET 可读回各自原接入号及原因。
- 已有稳定来源条目和组织归属、缺少扫描结论的候选以 `new` 落账。获权人员在同一风险补写核实说明和本地级别，风险修订推进至 `2`，源观察保持原样。另一条缺资产身份的风险在核实并确认责任人后，生产派单依据查询仍为空。
- 对首次上报和人工评估，测试端先观察成功 HTTP 状态头，再丢弃响应正文并停止真实 Core 进程。数据库保留，启动同一制品后，来源以原事件及相同内容重签重投取回原 `ingest_id`，人工以原 `operation_id` 直接查询原修订。数据库核对没有重复评估、重复风险或重复镜像写入。
- 同组织只读人员评估返回 403，无对象范围的人员评估返回 404。真正移除原操作者的组织成员资格后，用原 JWT 读两类接入回执、读人工操作回执及同号重投均返回 404，原评估修订和业务计数保持原值。
