# UAA认证与权限治理接入合同

日期：2026-11-12。状态：**指南核对后的设计修订，尚未实现、未完成真实接入验收**。本页取代旧[17号](../phase3/17-uaa-integration.md)中“后续计划零影响”“全部数据权限本地自管”“只换配置”“冻结授权永久运行”的结论；历史估算保留追溯。

输入为所有者提供、仅本地阅读的岗位权限治理指南。本仓只维护必要的通用技术要求，不复制原文、截图、真实报文、人员、企业标识、平台地址、应用标识、队列名或凭据；具体企业契约及联调证据归私有集成仓。指南说明与本页建议分别标识，未确认的契约不编造。

## 1. 为什么菜单和角色也需要对接

统一认证回答“你是谁、是否通过公司登录”；权限治理回答“这个岗位应该获得哪些系统功能、谁批准、调岗和离职如何回收”。只有登录统一时，同一个员工仍可能在各业务系统保留旧岗位授权，无法集中审批、核查或回收。指南实际包含两者，不能按纯SSO接入估算。

菜单编码是跨系统识别资源的稳定键，资源还包括功能按钮、API及需要治理的数据属性。中央平台需要这些键，把岗位/业务角色对应到具体能力；不负责渲染本项目页面，也不代替本地后端的逐资源判定。页面隐藏不等于接口鉴权，稳定编码也不等于把数据库行ID或任意接口URL当权限。

例如：中央批准甲获得“风险管理”功能；本地接收授权后允许进入对应入口，但能否读取风险A、派发何种整改工单、能否修改已关闭工单，仍由本地当前范围、参与关系和业务状态决定。中央撤销后按完整有效来源重新计算：若另有当前有效、中央认可的独立授权链，可以保留该能力；不得由本地旧绑定或未经认可的组织/继承路径补回已经失效且无其他合法来源的能力。

## 2. 指南要求与本项目处置

| 指南位置/要求 | 本项目处置 | 尚不能据此断言 |
|---|---|---|
| 集成步骤：测试接入后，以单点、权限上报/下发、数据同步报告申请生产接入 | E01-UAA-R独立验收并作为企业模式首次正式激活门 | 本地mock或其他provider通过不等于企业验收通过 |
| SSO：提供授权码、OIDC及SAML路线，指南推荐授权码 | 延续授权码方向；实际协议、能力与安全校验先核验；不默认并做三套 | OAuth令牌不天然是身份证明；标准OIDC能力不等于该实例已开放 |
| 自研类：上报菜单/功能/API等资源，中央创建角色及资源关系 | 默认按自研类映射；核心维护资源语义，中央维护受管角色和分配结果 | 不擅自改成只上报少量“角色壳”以绕过资源治理 |
| 同步：账号、账号与角色关系、角色与资源关系分别下发 | 三条独立收件/幂等/领域提交/对账路径，不合并成一个不明范围的“权限同步” | 某账号的全量角色不等于整应用账号或授权的全量 |
| 账号角色结果带审批关联请求时需反馈处理状态 | 私有adapter将关联号映射为公开receipt引用；提交/安全生效后的结果可靠回传 | broker ACK或收到HTTP请求不等于授权已全部生效 |
| 数据权限：关系类和业务特有动态属性通常自管；稳定通用属性存在统一纳管条件 | 按§3逐属性裁定；本地仍执行行级过滤与动作检查 | “六种场景均本地自管”不能覆盖后续条件规则 |
| 本地管理的权限配置需按治理要求回传 | 只导出批准的最小配置字段、血缘、版本和时点；格式/频次/目的地待契约 | 不推送工单正文、附件或完整业务数据来代替权限配置 |
| 常态入转调离及权限开通/变更流程 | 消费批准结果，复用停用/会话吊销/交接能力，不自建另一套岗位审批产品 | HR同步、UAA建号和SSO JIT不能同时无归属地修改同一字段 |

指南对于账号同步全量/增量、可用字段等也要求双方确认；本页不会把缺少的版本、水位、删除语义当作现成外部能力。不同对象的动作枚举须分别映射，不能共用一个未经核验的整数枚举。

## 3. 权限和身份的管理权

**判定在本地，分配来源可以在中央。** 本地数据库中的受管授权是中央事实的执行投影，不是第二个可随意覆盖的分配源。

| 对象 | 默认管理权及本地责任 |
|---|---|
| 人员/组织事实 | 目录权威按字段登记；HR管组织/任职，UAA管应用账号及功能授权时，不让两个feed竞争写同一状态。先形成账户与人员/组织映射，不能因账号同号就自动合并 |
| 应用可登录性 | 中央停用必须限制访问；本地安全停用仍可进一步收紧。中央启用不得自动解除本地安全封禁。应用账号状态的业务含义单独映射，未知状态隔离 |
| 菜单、按钮、API目录 | 核心/扩展所有者定义语义、层级和有效路由，向中央登记；中央角色绑定不能创造新路由或任意执行地址 |
| 企业受管角色、用户角色和角色资源绑定 | 中央批准结果为写主，本地管理页只读呈现来源、同步时点和异常；不能普通本地分配后永久与中央结果取并集 |
| 组织角色及角色继承 | 也纳入有效授权来源分析；受管能力须有确定来源和优先级，不让组织/父角色成为撤权旁路 |
| 自身、汇报、组织关系及临时团队 | 按业务关系做本地行级判定；配置页面和必要治理回传另行验收 |
| 人员/角色配置中的通用数据属性 | 当符合指南纳管条件时，范围值由中央批准下发，本地映射和执行；组织属性若只是关系过滤，与作为角色配置范围值须分开判断 |
| 业务特有或频繁变化的属性、工单参与/抄送/状态 | 本地业务管理；不因中央功能授权就放开类型可见范围或处理权 |
| 虚拟风险组 | 延续已确认职责：授权管理成员可在风险职责范围管理和派整改单；组内owner/admin名称不等同系统admin，也不自动变成中央岗位角色 |
| 本地应急账号 | 独立、最小、受控的恢复通道；是否允许企业模式使用、触发和时限须与接入方确认；不默认给所有员工保留公司认证旁路 |

C冻结公共管理权规则和合成候选矩阵，不等待真实映射值或企业外部审批；真实值、提供方能力及批准记录在R激活前核验。E01-UAA-C交付一张逐能力/属性矩阵：资源键、业务含义、管理权、写入入口、直接/组织/继承来源、中央是否纳管、撤销方式、数据范围和值映射、应急例外。未裁定的通用属性标为**真实激活阻断**，不能先假定全本地或全中央。

## 4. 公共核心与私有adapter

沿用[扩展合同](extension-compatibility.md)与[迁移合同](intranet-adapter-migration.md)：公共核心拥有认证会话、资源目录和授权投影接收能力；公司协议、SDK、MQ拓扑、实际字段和凭据只在私有adapter。企业MQ不要求成为五仓通用运行依赖；mock部署不必启动企业连接。

公共边界分为认证身份交换、资源目录发布、账号变更、用户角色集合、角色资源集合、可选数据范围、治理回执/导出。不同边界有独立schema、来源、权限和完成语义。adapter以受信服务身份投递受限治理命令，不能通过通用CRUD任意改用户或伪造调用者；核心验证来源管辖后由本地领域服务提交。核心不能只接收“信任此adapter给出的全部Casbin规则”。

公共核心提供稳定端口和合成参考实现，私有adapter负责转换与可靠投递；这需要一次核心能力建设。公司协议变化可在相同公共合同下仅升级adapter，核心授权语义变化仍需合同版本和迁移，不能承诺永远无需修改。已有SSOProvider/MQ只是文档设计，当前没有可直接替换配置的完整实现。

### 4.1 资源编码与升级

核心采用应用命名空间内稳定的资源键、capability_id/contract_version及OpenAPI operationId映射，私有表转换为中央应用/资源键；动态operation_id仅为某次业务效果，不作角色/资源目录键。词义及旧别名见[共同合同](capability-invocation-contract.md)。目录、页面、按钮及API关系能导出/比对，别名不改权限语义、不按名称猜映射；外部角色/资源ID与本地数据库主键分离。

保留B案约束：页面只挂GET，写操作绑定按钮，既有登记例外照常受审。中央授予页面不自动附送写权限，私有扩展也不能复用核心资源键。普通角色拥有“风险管理”不意味着可以读取全部工单。

编码新增/变更/退役先输出差异：新能力默认不授予；改名若语义相同保留键；语义改变用新键或显式迁移；删除需解除映射并核对在途/旧客户端。角色绑定引用未知资源先隔离并告警，不以未知关系覆盖已知授权；独立、可验证的停用/撤销仍须按时生效，无法安全拆分的批次进入异常并按授权新鲜度政策处理。首次目录在中央确认可引用后才激活关系应用；目录同步失败不解释为空目录。

禁止把外部同名`admin`/`superadmin`直接映射内置管理员。这些本地角色存在特殊判定语义，只有单独批准的管理权映射能触及；私有模块的管理员也不继承主仓超管身份。

### 4.2 登录及身份绑定

认证adapter必须验证回调事务和当前提供方：一次性state、精确注册回调、短有效期与code重用拒绝；按实际协议实施PKCE，OIDC另外校验issuer/audience/签名/nonce/时效及身份关联。秘密在服务端，token和code不放普通日志。OAuth授权码加profile路线须核验可信身份获取与token绑定，不能把未验证JWT直接当用户。

SSO成功不等于本地已授权：校验账号已登记、双方状态可用及授权投影就绪后，签发本地JWT/RT；JIT默认关闭。若未来允许JIT，只建立受控身份，不隐式授予组织或管理员角色。来源主键与可变工号/邮箱/域账号别名分离；改号、回聘、兼岗及外部人员需受审映射，不能按邮箱自动并号。

本地登出必须吊销本地会话；中央登出、中央账号停用和本地会话/PAT/委托的联动分别验收。是否支持标准单点登出及注销事件以实测为准，不能把“跳转中央登录页”等同所有旧会话失效。协议选择延续授权码方向；如企业实际提供完整OIDC，应评估标准客户端收益后记录决定，不额外实现三套登录。

安全依据：[OAuth 2.0安全最佳实践](https://www.rfc-editor.org/rfc/rfc9700.html)与[OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html)。OAuth与OIDC的校验要求不同，具体启用能力必须在公司测试环境验证。

### 4.3 同步、撤权与生效回执

三类下发分别定义集合范围：某用户的全部角色、某角色的全部资源、账号自身的状态；应用/来源/主体/批次缺一不可。角色资源映射和用户角色关系不能混成一次全应用清表。全量空集合只有在范围和完整性已验证时才能按政策撤销该范围；分页不全、解析失败、未知枚举均不能生成缺失删除。

至少一次投递按收件identity、来源版本/快照及作用范围幂等，收件记录与本地领域变更同事务；投影必须包含直接角色、组织赋角和继承的来源链。保留历史source列延伸方向，但仅给三张表加source并不足以证明三源撤权闭合，具体表设计在E01-UAA-P冻结并按迁移地图申请编号。

无可信顺序/快照水位时，不以到达顺序推断新旧；查当前事实或隔离冲突。引用尚未到达时持久等待重放，不丢消息、不临时授予宽权限；停用等安全收紧路径须独立保证时效。完整目录、角色资源、用户绑定按依赖完成后才标记目标授权已生效。

复用停用与会话吊销领域入口，不能只更新`users.status`。授权策略提交后，还须让所有服务实例的Casbin及相关缓存按revision生效；失败持久重试并暴露待生效状态。broker ACK可在有可靠恢复记录后完成，审批业务回调的“生效成功”需达到约定的数据库/会话/实例收敛条件，两个ACK不能混同。

E01-UAA-C必须确定撤权时限、授权新鲜度阈值、断网行为及应急范围；数值待接入方确认，未配置/未验证不能激活企业模式。超过允许新鲜度后对受管能力拒绝访问或按已批准的有限策略降级，不能无限沿用最后一次授权。减少授予、账号停用、组织/继承撤回、活跃JWT/RT/PAT、设备会话及后续Agent grant均要有反例；未来grant不能复活已撤销的用户权力。

回传使用独立outbox和幂等键：领域提交后可靠重试，与应用处理状态/错误关联；不回传访问令牌或原始敏感报文。未成功时保留可对账回执，不能因回调服务短暂失败重复建号或重复赋权。

## 5. 模式、mock与切换

**两种模式都是正式支持的产品运行模式，独立模式不限于开发、mock或应急。**

- **独立模式**：不接UAA也能部署和长期运行，保留本地账号登录、账号管理、角色管理、用户/组织赋角、角色菜单分配、权限查询及三层鉴权。菜单目录仍按现有规则维护：运行期查看/分配，目录和API绑定经迁移管理；不能把“保留菜单管理”误报为已有生产菜单CRUD。后续声明式扩展目录按X01另行建设。缺少UAA地址、应用凭据、私有adapter或企业MQ时，独立模式仍须能构建、启动并使用这些原有能力；公共核心不内置公司SDK或公司特例。
- **企业模式**：迁到内网后，通过私有adapter对接公司UAA；同一公共核心按明确配置和来源管辖切换，不维护公司专用核心分叉。部署地点本身不决定模式；独立模式的产品能力不受UAA-R阻塞，公司要求纳管的实际使用场合仍须满足企业接入规定。中央管理纳管的账号/角色/授权结果，本地保存执行投影并执行三层判定；本地继续管理非受管业务规则。中央接管范围内的管理写入口调整为来源只读或受控操作，不删除独立模式的管理实现，也不在两个来源间无条件合并授权。

**应急是企业模式的受限恢复政策**，有批准、审计、有效期和事后核销，不等于切回独立模式。企业接口故障不得自动切回mock成功、本地自由授权或全员账密。首次接入及退出UAA都须显式执行接管计划，不能通过每请求开关或故障回退绕过中央治理。

mock永久保留，包含合成IdP、三类feed、数据范围与回执服务，跑同套公共合同正反例；其数据、issuer及信任域与企业环境隔离。现有开发账密和mock功能不因此被删除，企业模式的约束也不能只靠隐藏登录按钮实现。

真实切换采用：合同/来源矩阵→身份匹配预览→只读影子比较→目录注册确认→批准的角色/范围映射→小范围启用→撤权和故障演练→验收报告→生产申请。切换期每种事实只保留一个写主；关闭旧写入口有可核的配置与回执。

退回独立部署是受审的数据/凭据/授权迁移：清点中央投影、批准本地接管、建立有效本地凭据、验证权限与历史、再退出中央管理。关几个开关不能保证所有企业账号可登录，也不保证零迁移、零功能损失。

**双模式验收列入E01-UAA-P/R**：P必须在完全不提供UAA配置、禁用私有adapter且企业网络不可达时，验证独立模式启动、本地登录、账号/角色/菜单授权管理和正反向鉴权；同一核心候选再验证合成企业adapter及纳管来源写限制。R追加真实企业接入、已有本地身份/历史保留、批准接管和退出演练。只跑企业mock或仅验证应急超管可登录，均不能代替完整独立模式验收。

## 8. 本轮代码核查边界

`internal/repository/role_repo.go` 的 `GetEffectiveRoleCodes`合并直接、组织和继承三源；`AssignMenus`以及`internal/service/ticket/resource.go`的`Authorize`具有内置管理员特殊语义。`internal/service/rbac_service.go`的`reloadPolicy`与`internal/casbin/enforcer.go`的`New`尚不能证明跨实例撤权。`internal/service/user_service.go`的`UpdateStatus`及`internal/service/session_revoke.go`的`RevokeUserSessionsWithRetry`为停用可复用入口，不能由外部直写表绕过。

当前没有已实现的SSOProvider、企业MQ三消费者和上述完整投影协议；来源字段/唯一性也需按实际模型和迁移核对。本轮是设计和排期修订，没有新增业务API、权限码、数据库迁移或真实连接。文档静态通过不代表UAA接入验收通过。
