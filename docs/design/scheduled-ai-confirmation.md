# 自然语言计划与人工确认的联动场景

日期：2026-11-12。状态：A04/I02/I03详设补充候选，未实现。继承[AI调用合同](ai-invocation-contract.md)和[调度恢复合同](schedule-recovery-policy.md)，补足“人不在线、待确认跨时隙、计划变更、授权/确认到期”的组合语义。以下是技术推荐，持续自动写入的具体业务准入仍在A04启用前确认，不把创建周期任务等于永久批准副作用。

## 先分开三种授权

**批准保存一个计划**：批准版本化频率、时区、动作/模板、目标范围、预算与错失策略。允许调度器按计划创建发生次，不自动允许未来业务写入。

**逐次精确确认**：每次取得当期数据后生成具体命令，绑定发生次、操作者、目标、输入、定义版本和失效时间。批准只能执行这个命令；用户离线时持久等待，不占worker或模型连接。

**持续执行grant**：另行批准指定能力/目标/参数约束、数据区、次数/预算、有效期和撤销路径。仅对业务已经认可的有限自动场景开放；配置人、调度人、实际执行主体和批准人分别留痕。首发写操作仍逐次确认；有持续grant的只读计划可以在实时复验后运行。

计划描述可以是“每天9点查本组新增风险并生成整改建议”，但确认页必须显示它究竟只生成建议、每次待确认建单，还是获准在明确边界内自动建单。没有后一授权时不能推断为无人值守。

## 三个时间不能混用

- `scheduled_for`：原始时隙；决定发生次身份，不因人晚确认而改变。
- `confirmation_expires_at`：具体命令允许确认的截止；由数据时效、动作政策和计划上限取更严值。不是模型HTTP超时，也不是定时恢复窗口。
- `execution_start_not_after`：确认后允许开始的期限，取命令/源数据有效期、grant/计划截止及`confirmed_at + 允许排队TTL`的最早值；不能在确认后无限排队或延长原草案时效。开始时仍复验grant、实时权限、输入版本与幂等receipt；到期hold并重新预览，不沿旧批准继续。

确认截止必须明确展示。技术样例可用30分钟，但生产模板由场景政策确定，不设全平台统一SLA。结束/到期只关闭该命令的自动执行资格，保留发生次、草稿、原因和处理入口；没有执行不能显示任务业务成功。调度发生次的“已产草稿”与建单操作的“已完成”是两个可见事实。

## 场景一：用户离线，第二个时隙又到了

合成样例：Asia/Shanghai每天09:00查当前风险，甲需逐次确认建整改票。周一09:00生成草稿A，09:30到期；甲周二10:00才上线，周二草稿B也已生成。

当前状态型场景推荐每计划最多保留一个**可执行**的待确认草稿：A到期后保留历史与关联，B独立生成并重新查询；不能把A的批准挪给B，也不能把A/B风险取并集自动建单。若B也过期，甲看到“2次草稿已过期”，选择重新查询预览后产生新命令；原时隙记录不伪装成功。

这是待确认草稿的合并/到期政策，与调度器`coalesce_latest`不同：前者处理已经执行查询后的待批准输出，后者处理尚未执行的错失时隙。两层记录分别可查。过期草稿可以归档显示，不能删除审计或被后来一条“成功”覆盖。

## 场景二：历史任务必须逐日补齐

每天09:00生成前一日合规报告，计划选择`catch_up_bounded`，数据源支持历史区间。停机三天后，按原时区分别保留三个业务日期和发生次；每份报告的分发若需确认，则每日期一个待确认命令，不使用当前状态型的“只保留最新草稿”。

可以提供多选确认，但服务端逐份列目标、版本、期限和回执，只对本次明确选择的命令授权；某份数据/权限变化使该项失效，不能默改后继续分发。超出回补上限、无历史或确认积压超出容量，按已确认策略hold并保留准确余项。用户可以扩大获准预算或明确跳过，不能静默丢日期。

积压上限同时约束未确认数量与模型/取数预算。达到上限后停止新准入或hold余项，不继续每天调用模型制造无限待办。数量只在真实可计算时展示，未枚举范围给区间与unknown，不猜剩余条数。

## 场景三：确认后计划或权限变了

09:05甲预览对风险R1创建到组织A；09:06配置者把后续目标改成B；09:07甲点击旧确认。

旧草稿按冻结的计划/目标/定义保存，不能自动改为B。若本次计划修订声明撤销全部未执行旧命令，则旧确认返回失效；若只影响未来时隙，旧命令也必须复验A及旧定义仍允许执行。两种影响在修改计划的preview里明确展示，由有权配置者确认，不由后台猜测。

甲被撤权、所属组停用、风险负责人已变化、定义被停用或目标不再合法，都使旧命令不能执行；提示具体可披露原因和“重新预览”。恢复角色后不能重用已失效的批准。审批人与执行人分离的场景还要复验两者资格；邀请/CC不会附带处理权。

本地高风险写在C04守卫事务中与相关版本/撤权检查一起提交；跨服务不能声称原子锁住企业IAM，采用短期范围凭证、执行侧复验与审计，遇到不确定保守暂停。当前同步身份接缝不充当持续grant。

## 场景四：暂停、取消与外部效果未知

暂停计划默认停止新发生次准入，并按preview列出对可证明尚未开始命令的影响；不等于取消已running或外部已生效动作。删除计划不能删除历史运行或待对账效果。

用户撤销grant后未开始的命令hold；已经提交工单的receipt仍返回原工单，不能再退成“尚未执行”。外部超时可能已生效时进入`outcome_unknown`，暂停其后继并query/reconcile；恢复时查原operation ID，不能再问模型生成新命令执行一次。

“取消待确认草稿”只取消该草稿，还是同时暂停整个计划，必须是两个清晰操作。取消一个周一草稿不会悄悄取消周二计划；停整个计划要显示影响范围和已在途事实。

## 最小合同与界面

计划保存`confirmation_mode`、场景允许策略、待确认容量、时效政策与修订影响；发生次保存计划/参数快照和调度处理回执；草稿保存`occurrence_id + command_id + hash + versions + expires_at + status`；提交保存稳定操作receipt。字段为逻辑合同，准确DTO/表结构在I02/I03/A04同批冻结，不各建一套确认表或调度器。

等待确认采用持久状态和可恢复引用，不使用阻塞HTTP请求/驻留worker。通知只提示有待确认内容，不含可复用批准token；打开后按当前身份读取。查询失败显示“本次未取得数据”，不能产生零风险草稿。UI分别显示原定时间、取数时间、确认截止、当前可操作范围和最终结果。

默认只允许查看当前有权的草稿内容；失去源权限后审计保留必要元数据，不能为了展示历史泄露风险正文。模型不能把“已生成建议”总结为“已整改/已派单”。

## 最小验收与交付窗口

A04编码前与I02/I03一起冻结三种授权、草稿生命周期和修改影响；本补充不增加独立业务平台。工作计入原I02/I03/A04，若开工发现超出该包粗估，先具体化切片再复估。

必须覆盖上述四个组合场景，以及重复确认/确认与取消竞争、过期后点旧通知、跨时区日期、已建待确认与错失补发同时恢复、积压hold重启不重置额度、grant中途撤回、结果丢失查原receipt。mock控制模型/时钟/提供方；PG+Redis真实小栈证明持久状态和竞争；实际企业模型/授权接口分别待验。不以纯状态机单测证明跨仓正确性。

设计借鉴：[Temporal Schedule](https://docs.temporal.io/schedule)将调度、重叠和追赶政策分别管理；[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)展示持久等待人工输入及恢复。前者不替本平台批准业务写入，后者默认可无限等待也不代表业务确认应永不过期。这里采用的是本平台的时效/授权政策，不默认引入这两个运行时。
