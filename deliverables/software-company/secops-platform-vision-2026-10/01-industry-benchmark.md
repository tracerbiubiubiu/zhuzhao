# 01 · 业界实践对标

> 性质：发散研究稿（见目录 README）。本文回答"别人怎么干"，为差距分析（02）与架构提案（03）提供依据。所有对标基于公开产品的公开资料，引用为模式参考。

## 1. 安全部门平台的业界形态谱系

安全运营生态里的平台形态，大致分六类。判断"我们该建什么、买什么、接什么"，先看清谱系：

| 形态 | 代表 | 核心职能 | 与我们的关系 |
|---|---|---|---|
| SOC 工作台 / 案例管理 | TheHive、Microsoft Sentinel Incidents | 告警→案例→分诊→处置→复盘 | 我们的平台本质在这个象限（工单+流程），但缺事件接入 |
| SOAR（编排与响应） | Cortex XSOAR、Splunk SOAR、Shuffle | playbook 编排、连接器/action 库、自动化响应 | 我们规划的"自动化能力中心"在这个象限 |
| 分析自动化执行 | Cortex（TheHive 配套的分析器/响应器引擎） | 容器化跑分析/处置脚本，JSON 进出 | **脚本节点最直接的业界先例** |
| 漏洞/风险管理 | DefectDojo、Archer、ServiceNow IRM | 汇聚台账、分级、处置闭环、SLA | phase6 风险模块对标于此（立项时已对齐） |
| ITSM/CMDB | ServiceNow、Jira Service Mgmt | 资产台账、变更、工单 | 我们的工单+IAM 对标于此；资产面由外部资产平台承担（所有者 2026-10-20 补充），平台侧缺的是查询接入 |
| 通用任务自动化 | Rundeck、StackStorm、n8n、Ansible | 作业调度、脚本执行、跨系统动作 | taskrunner 对标于此（单步执行已闭环） |

**小团队安全部门的自建主流路线**（业界大量实例）：不做大而全 SOAR，而是"**工单/案例管理 + 轻编排 + 连接器 + 脚本执行 + 台账**"的组合工作台——典型如 TheHive（案例）+ Cortex（脚本执行）+ MISP（情报）三件套自托管。这与我们"IAM+工单+taskrunner+风险模块"的既有资产高度同构，说明方向不必推倒，缺的是四个面：**事件接入、资产查询接入、编排、脚本执行**（详见 02）。

## 2. 核心抽象对照表

业界安全运营平台收敛出的概念原语，逐个对照我们的现状：

| 业界原语 | 业界含义 | 我们现状 | 差距 |
|---|---|---|---|
| Incident / Case（案例） | 多条告警聚合成的处置单元，带状态机/负责人/时间线 | 工单（资源级）+ phase6 风险单（规划中） | 风险单≈案例，缺"告警→案例"的聚合层 |
| Playbook / Workflow | DAG 编排：条件/并行/审批/等待，节点=action | 无（16 号红线：不做通用流程引擎；最小替代 on_success 已设计未实现） | **空白**，phase7 核心 |
| Action / Integration | 对外能力的标准化封装：命名+输入 schema+输出 schema+鉴权 | taskrunner action_id（无类型的不透明串）+ capability_registry 方案（已定稿未实现） | 有雏形，缺"类型化 I/O"这一步 |
| Sensor / Trigger | 事件源接入（webhook/轮询/计划）触发 playbook | taskrunner cronloop（计划触发已有）；事件触发无 | 缺事件触发面 |
| Asset / Entity（资产） | 告警与动作的锚点：IP/主机/服务/责任人 | 由外部资产平台提供能力（所有者 2026-10-20 补充）；平台侧无查询接入，实体无资产引用字段 | 缺查询连接器 + 解析门面 + 实体挂接（不建台账） |
| Indicator / IOC | 情报指标，查询/富化/打分 | S9 情报缓存代理（已排期 W11-13，ThreatIntelProvider 端口已预留） | 已规划，可直接消费 |
| Artifact / Evidence（证据） | 处置过程产物（截图/报告/抓包），挂到案例 | S5 对象存储（进行中）；工单附件 | 底座将就绪，缺"运行工件→案例"的挂接约定 |
| Run / Job Execution | 一次执行：状态/重试/日志/时长/归因 | taskrunner job_runs + 幂等栅栏 + 审计（**业界少见的扎实**） | 已闭环，可作编排引擎的地基 |
| Credential Vault | 连接器凭据集中管理、注入、轮换 | config 化凭据 + env 注入（服务级） | 缺"每连接器凭据 + 脱敏 + 轮换"管理面 |
| Observability | 运行指标/队列水位/告警通知 | M4 未落地（asynqmon/指标/保留期清理均无） | 待补 |

对照结论：**我们的强项恰好是业界自建平台最容易做烂的部分**（鉴权/审计/幂等/状态机），弱项恰好是业界成熟的部分（编排/连接器/脚本/资产）——补弱项有成熟蓝本可抄，这是好消息。

## 3. 脚本契约专项：业界怎么定义"可上传执行的脚本"

这是所有者点名的问题（05 号文档给完整规范），此处先看业界共识。五个最有代表性的先例：

### 3.1 XSOAR automations / integrations（Python 为主）
- 脚本即 Python 文件，入口约定 `main()`；参数经 `demisto.args()` 取字典，结果经 `return_results()`/`CommandResults` 返回。
- **integrations 用一份 YAML 声明**：每个 command 的输入参数（名/类型/必填/默认值）与输出 context 路径；UI 据此自动生成参数表单。
- 每个 integration 打包为独立 Docker 镜像隔离执行；日志走 `demisto.debug()/results()`，与数据通道分离。
- 启示：**manifest 声明 → 表单自动生成 → 容器隔离**三件套是十年验证过的形态。

### 3.2 Cortex analyzers / responders（与我们的"脚本节点"最同构）
- 脚本分两类语义：**analyzer（富化：给观测值打分/打标）** 与 **responder（处置：对实体执行动作）**，各自容器化。
- 输入：JSON 文档（观察对象+配置）；输出：一份结构化 JSON 报告（taxonomies：级别/值/模块），由平台统一入库展示。
- 长短任务分档、每个 analyzer 有 job 规格（数据类型/温和程度标记）。
- 启示：**脚本按语义分 kind（富化/处置/作业）**，而不是一律叫"脚本"；输出报告结构化入库而非仅人类可读。

### 3.3 StackStorm actions（DevOps 界的 SOAR 前身）
- Python action 继承 `Action` 基类，实现 `run(**params)`，返回 dict；**参数 schema 声明在 pack 的 YAML 元数据里**（类型/必填/默认/enum），CLI 与 UI 都从元数据生成参数界面。
- sensor（事件源）→ rule（匹配）→ action（执行）→ workflow（串联），是"事件驱动自动化"的完整参考模型。
- 启示：**YAML 声明参数 schema + 基类只做薄封装**；不强制依赖 SDK（裸协议亦可）是低摩擦关键。

### 3.4 Rundeck（运维作业平台）
- job = 脚本/命令 + **options（具名参数，带类型与校验）** + 调度 + 通知；执行时参数经环境变量/文件注入。
- 每步执行日志按 job 落盘可查；成功/失败后动作（webhook/通知）可配。
- 启示：**参数经环境注入**（避免命令行注入）、**每运行一份完整日志**、**onsuccess/onfailure 钩子**（与 16 号"最小替代 on_success"设计互证）。

### 3.5 AWS Lambda / OpenAI function calling / MCP（协议化极简派）
- Lambda：event 进 JSON、出 JSON、日志到独立通道、env 注入配置与秘密、超时硬杀——**"数据通道/日志通道/配置通道三分离"的教科书**。
- function calling / MCP tools：工具= 名字 + **JSON Schema 输入** + 结果；模型侧与执行侧只认 schema。
- 启示：**JSON Schema 是脚本契约与 AI 工具契约的公共语言**——同一份 schema 既能生成前端表单，又能给 LLM 做工具调用（见 03-A1；AI 工具暴露形态见 D10——原"A10"系悬空引用，三审勘误 E-D8）。

### 3.6 共性蒸馏（八条，05 号文档据此展开）
1. 声明式 manifest（元数据与代码同包，平台据此校验/生成 UI/路由）；
2. 类型化输入输出 schema（JSON Schema）；
3. 数据与日志通道分离（stdout=数据，stderr=日志，或等价物）；
4. secret 经环境注入，绝不进参数与日志；
5. 工件（artifact）写约定目录，由平台收集入库；
6. 退出码语义化（成功/业务失败/临时失败/超时/取消 分开，重试策略据此定）;
7. 超时与取消是执行器职责（SIGTERM→宽限→SIGKILL）；
8. 一切通道有大小上限（日志行/总量/输出体积），超限截断并标记。

## 4. 编排引擎专项：自研 vs 引入

| 方案 | 优点 | 代价/风险 | 适配度 |
|---|---|---|---|
| 自研轻量 DAG（Go，复用 taskrunner 语义） | 零新依赖；幂等栅栏/重试/死信/审计直接复用；与 S2 画布 schema 适配层天然衔接；GPL 无虞 | 状态机/并发/可观测要自己写；长期演化成本 | **高**（单人+compose 现状） |
| Temporal（MIT） | 持久化执行/信号/定时器全都有，Go SDK 成熟 | 自托管重（独立 server 集群+DB）；学习曲线陡；与三层鉴权/审计体系要重新接线 | 中（若编排规模上量值得重估） |
| Dagu（GPL-3.0） | 单二进制、compose 友好、无状态文件存储 | GPL 仅限外部进程集成（法务未确认）；状态存本地文件（业务审计要自记）；无沙箱 | 中（15 号已留 PoC 折中档） |
| Airflow / Argo / Cadence | 生态大 | 分别偏数据批处理 / 需 k8s / 重 | 低 |

**业界观察**：XSOAR/Shuffle/Tines 的 playbook 引擎都是自研 DAG + action 抽象，没有一家拿通用工作流引擎当内核；通用引擎（Temporal/Airflow）胜在长任务与大规模，安全剧本的典型形态（几十步内、混合人工节点、强审计）恰恰是自研轻 DAG 的甜区。建议：**自研起步、接口留逃生门**（workflow 定义与执行记录抽象化，未来可换内核）。

## 5. 告警归一化与聚合专项

- **归一化 schema**：业界公共标准是 OCSF（开放网络安全遥测框架，Linux 基金会）——事件分类学+统一字段。全量采用过重，**借鉴其字段骨架自定轻量内 schema** 是小团队主流做法。
- **去重/聚合**：XSOAR 的 incident dedup key、TheHive 的 observable 聚合，本质与我们 phase6 R1 的"SHA-256(系统+类型+外部标识) 指纹去重、重报提计数"同构——**R1 设计已在业界主流航道上**，SOC 告警接入只是给它加一个源。
- **抑制**：维护窗口/静默规则（升级期间不建单）是标配，规则形态=匹配条件+时间窗+豁免人。
- **ATT&CK**：攻击战术/技术标签作为可选分类字段普遍存在，用于统计与检索，不建议第一档做映射自动化。

## 6. 身份与委托专项

- 平台侧：服务身份（非人主体）+ on-behalf-of 委托链是主流（"playbook 以张三身份执行、以连接器凭据出站、全程审计归因张三"）。
- 我们已有 X-Operator 明文断言 + HMAC 覆盖（16 号 B2 拍板），缺的是**非人主体类型**与**委托语义**（03-A6）。
- break-glass 与最小权限：自动化凭据按连接器粒度隔离、可独立吊销——我们 config 化凭据已有基础，缺管理面。

## 7. AI 专项

- 业界安全 Copilot 形态：自然语言查询（NL→结构化查询而非 text-to-SQL）、告警摘要/分诊建议、playbook 推荐生成。
- **工具调用面收敛于 JSON Schema**（function calling / MCP）——与 3.5 同语言。这决定了"Action 注册表"一旦带 schema，AI 接入是顺水推舟（03-A1、D10）。
- 两个安全要点业界反复踩坑：①用户可控文本（工单描述/告警 payload）进 prompt = 注入通道，需隔离与标注；②NL 查询必须走既有权限面（我们的 L2/GetFilter），AI 不得持有旁路。
- 新形态：**AI 智能体平台**（多智能体 / 长任务执行）正在成为安全运营栈的一员；对接是双向的——平台把智能体当能力来源（连接器 + Action），智能体产出回流为事件源，智能体调平台走 Action/MCP 暴露并带 on-behalf-of 归因。所有者已将其列为终态（D17），见 03-A1、04-§4.11。
