## 2. 四大结构性差距

### 2.1 G1 · 资产查询接入（Asset Access）—— 外部能力，缺的是接入

**所有者补充（2026-10-20）**：资产面由另一个平台提供能力，我们只需调其接口查询。因此 G1 不是"建资产面"而是"接入资产面"，体量显著缩小；但它仍是结构性的：场景 1/3/6/7/10/15 全部需要"实体 → 资产 → 责任人 → 组织"的解析链，没有接入就没有锚点——告警无法自动找到处置人、风险单无法按资产聚合、playbook 的"隔离主机"不知道主机属谁、审计追溯缺实体维度、L2 的 org 锚点（phase6 要求 risk_items 带 org_id）无从自动填充。

**业界做法**：外部真相源 + 本地"解析门面"（统一入口、字段归一、按需缓存），自有实体只存外部资产引用与解析时快照——责任人/部门在解析那一刻是谁，审计要稳定，与本项目审计快照列的既有模式同款。

**弥合路径（D4 已定：纯查询连接器，不自建台账、不做同步对账）**：
1. 资产平台连接器：声明式 HTTP 连接器（04-§4.9）即可，至少两个操作——按标识符解析（ip/hostname/fqdn/instance_id）、按条件列举（kind/部门，供巡检类 Job 取清单）。
2. 解析门面 `POST /internal/v1/assets/resolve`（04-§3.3）：平台内所有消费者（告警流水线、脚本 SDK、S1 字段联动、工单资产字段）只认门面，不直接耦合对方 API；门面负责字段归一与**键映射**（对方的责任人键 → 我们的 users，对方的部门码 → 我们的 org_id——L2 锚点自动填充的前提）。
3. 读穿缓存：可选，按对方配额/时延决定；形态复用 S9 缓存代理模式（TTL 分钟到小时级，资产变更频率低）。
4. 实体挂接：security_alerts / risk_items / 工单资产字段存 `asset_ref`（外部 ID）+ `asset_snapshot`（解析时的名称/责任人/部门/等级）；不建 assets 表。
5. 解析失败：实体 `asset_ref=null` 并打"未解析"标记进路由规则（可定期汇总回报资产平台方登记）；"未登记资产"的发现与治理是资产平台的职责，本平台不接管。
量级：连接器 + 门面 + 键映射 + 实体挂接 ≈ 1 周（原按台账口径的 2–3 周估算作废）；归属统一 = **phase7 前置批**（可与 phase6 收尾并行、契约就绪即做——2026-10-20 双审计统一 06/02/07 三处措辞）。**契约问**（须向资产平台方确认）：鉴权方式与配额、解析接口是否支持批量、责任人字段用什么键（工号？）、部门字段与我们 org 树的映射关系、重要性等级枚举、变更通知有无（决定缓存 TTL）。

### 2.2 G2 · 编排与连接器面（Orchestration & Connector Plane）

**现状**：taskrunner 是扎实的"单步可靠执行"；无 DAG、无类型化 action、无外部连接器（出站被 W0b 锁为单一回调目标）。

**弥合路径**：
1. 统一 Action 抽象（03-A1）——先于引擎，否则引擎没有可编排的节点类型。
2. 轻量 DAG 引擎（03-A5）——三表状态机，节点类型：action / script / approval（联动工单）/ wait（事件或定时）/ branch / parallel。
3. 连接器 SDK 与凭据管理（04-§2）——HTTP 连接器通用件 + 鉴权类型（AK/SK HMAC 内部、API Key/Bearer/OAuth 外部）+ 每连接器凭据隔离。
4. 画布复用 S2（schema 适配层分离是 S2 的既定设计，playbook 是另一份 schema 同一块画布）。
量级：A1 1–2 周 · A5 3–5 周 · 连接器 1–2 周 ≈ 5–9 周——2026-10-20 晚按 D1 分摊到 phase7（A1 + 连接器地基）、phase8（SOAR 能力迁移）、phase9（A5 引擎 MVP）、phase10（SOAR playbook 迁回）四段（07 号）。

### 2.3 G3 · 脚本执行面（Script Execution Plane）

**现状**：任务唯一形态=属主服务注册 handler，"加能力=发版"。安全部门的巡检/富化/处置逻辑变化快、数量多，发版节奏不匹配——这正是所有者"上传自定义脚本"诉求的根因。

**弥合路径**：05 号文档给出完整契约；执行面=独立 sandbox-runner（03-A2）；脚本包走 S5；注册为 Action 后对编排/工单/AI 同契约。量级：runner 2–3 周 + 契约/SDK/脚本库管理 1–2 周。

### 2.4 G4 · 非人身份与委托面（Machine Identity & Delegation）

**现状**：服务间 AK/SK HMAC + X-Operator 明文断言覆盖签名（扎实），但 IAM 里没有"非人主体"类型，也没有"以某人身份执行"的委托语义。playbook 自动跑、连接器出站、AI 代操作三件事都会撞上它。

**弥合路径**：03-A6——service account 类型（D9）+ on-behalf-of 链 + 审计标记；凭据按连接器粒度隔离可吊销。量级 1–2 周，建议随 phase7 首批。

## 4. 弥合原则（三条，用于后续所有取舍）

1. **连接器优先于重建**：资产、日志、情报、消息、身份——凡公司已有权威系统的，平台只做连接器 + 缓存 + 解析，不做第二真相源（资产面已由所有者明确：只查询、不建台账）；唯"无人管的"（跨系统处置记录、告警聚合台账）由平台兜底。
2. **人机界面分治**：工单 = 人的流程（状态图、审批、协作），playbook = 机器的流程（DAG、重试、幂等）；两者互操作（审批节点→工单、工单动作→playbook）但不合并引擎——这是 S2 分层决策的延伸而非翻案。
3. **台账唯一**：告警、风险、资产各有一张权威表，其它一切是视图/缓存/连接器；指纹去重与 source 列豁免是台账唯一性的两个技术保障。

## 5. 定位拍板：公司已有 SOC/SOAR 时怎么办（D3）

这是影响 phase7 体量的最大外部变量，必须在立项前摸清：

| 情形 | 平台定位 | phase7 形态 |
|---|---|---|
| **公司无统一 SOAR**（或 SOAR 只覆盖检测侧自动响应） | 平台 = 安全部门的工作台：案例/工单/风险 + 跨系统任务编排 + 脚本执行 + 台账 | 完整：Action + DAG + 脚本 + 连接器 |
| **公司有成熟 SOAR**（playbook 已在那里跑） | 平台 = 治理与人工协同层：案例/工单/风险/审批/报表（资产经查询接入）；自动响应动作**下发给 SOAR**（我们是它的调用方），SOAR 结果回流（我们是它的 webhook 消费者） | 收缩：Action + 轻编排（人工节点为主）+ 脚本执行（巡检/报表类，非实时响应）；连接器重点=SOAR 双向 |
| **灰色地带**（SOAR 有但安全部门自己用不顺/不开放） | 分域：实时响应归 SOAR，运营自动化（巡检/台账/报表/工单联动）归平台 | 中间态，按 Action 抽象双向可切 |

无论哪种情形，**Action 抽象 + 脚本契约 + 资产查询接入 + 事件接入面四件都是必要的**——它们不随 D3 变化；变化的只是 DAG 引擎的深度与连接器的重点。这也是为什么 03-A1 排在所有提案之首。

**2026-10-20 晚所有者确认：公司已有 SOAR，第一步先迁能力（任务中心预定义任务）、流程调度继续用 SOAR → 上表第二行"协同模式"生效（D3 已答）**：平台 = 治理 + 人工协同 + **能力提供方**（SOAR 调我们的 Action、我们触发 SOAR playbook、SOAR 能力逐个迁为 connector / script 型 Action）；**协同模式是过渡态**——所有者同晚明确编排最终全部迁回平台：phase9 自研引擎 MVP、phase10 playbook 迁回与 SOAR 退役（D1，07-§4.3–4.5）。
