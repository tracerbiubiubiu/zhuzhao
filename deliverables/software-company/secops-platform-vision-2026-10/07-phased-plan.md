# 07 · 分阶段计划：完整形态 + phase6 范围调整 + phase7–11

> 性质：发散研究稿（见目录 README），本文为**规划草案**——基于所有者 2026-10-20 三条口径输入整理。不改 `docs/` SSOT；采纳后按文档同步纪律落 `docs/phase6/README.md` 范围调整与新建 `docs/phase7+`。

## 0. 本轮口径输入（所有者 2026-10-20，本文据此成文）

1. **漏扫结果 + 整改跟踪 = phase6 的一部分**：整改跟踪通过工单；漏扫结果来自其他平台，我们提供**统一的获取接口**对接——正常是对方推过来，但曾出现过需要我们**主动去对方数据库拉**的情况，所以**推/拉接口都要提供**。
2. **不追求一步到位**：核心能力先搭起来（如对接日志、SOC 告警），后面的处置跟踪可以慢慢做，**但要先知道完整的形态是什么**。
3. 资产面由另一平台提供，只查询（已落 D4）。
4. **平台定位（所有者 2026-10-20 定调）**：主要使用方是安全部门，平台在**逐渐统合各个分散平台的能力**（安全运营、风险管理、渗透测试等），把分散的能力与数据打通、聚合到一起——本计划接入面与台账的设计皆服务于此。
5. **终态补充：对接 AI 智能体平台（双向）**（所有者 2026-10-20 补充）——平台可调用智能体能力作为输入 / 任务（智能体 = 一种能力来源），智能体亦可调用平台能力（Action 暴露）——两个接口面已被 A1 / A7 覆盖，登记为触发驱动段（D17，§4.8）。
6. **编排与 SOAR（所有者 2026-10-20 晚）**：**公司已有 SOAR**；第一步先把 SOAR 的能力迁过来（任务中心预定义任务 = Action），**流程调度先继续用 SOAR**，SOAR 的脚本 / playbook 调用本平台提供的能力（任务）；工作流须支持上传自定义 Python 脚本执行、脚本 / 任务定义输入输出。**二次强调（同晚）：SOAR 只是过渡，最终编排也要全部迁回本平台。** → D1 分阶段：Stage 1 = SOAR 编排（phase7–8）；Stage 2 = **既定排期段**（phase9 自研引擎 MVP → phase10 编排迁移与 SOAR 退役），不是触发驱动。D3 已答（协同模式为过渡态）。
7. **基础设施与 AI（同晚）**：asynq 是否够用 / 是否引入 Kafka → D21（建议不引）；AI 范围所有者不熟、后置讨论 → D8 / D10 / D17 与 phase11 智能面功能范围转"后置讨论"，仅保留零成本 AI-ready 设计位（Action schema、on-behalf-of 身份）。

## 1. 规划原则（四条）

1. **目标态先定、切片渐进**：§2 给完整形态；每阶段分"**核心切片**（必交付，以用户可感知的闭环为准）"与"**补全切片**（可滑入下阶段）"。
2. **接入先于处置**：告警/漏扫先进来、可见、去重、通知；处置自动化逐级加。手动处置（既有工单）从第一天就能用，所以"慢慢做"不会留下空窗。
3. **通用接入层从 phase6 第一天按通用形态建**：source adapter 模式，不为漏扫写死——phase7 的 SOC/日志告警直接复用同一层。这是"先知道完整形态"在工程上的落点。
4. **不变量先立**（§5）：九条第一天就要守的约束，防止渐进把自己画进死角。

## 4. 逐阶段详述

### 4.1 phase6（范围调整：+ 统一接入推/拉，首源漏扫结果平台；+ 人工复测关单联动）

既有 R1–R4 不变（见 `docs/phase6/README.md`），新增/升格三块：

**（a）统一接入层（通用件，首源=漏扫平台）**

- **推**（两入口，落同一原始表）：`POST /internal/v1/events`（AK/SK，能签名的系统）；`POST /webhooks/in/{token}`（只会发 webhook 的系统，每源验签 / 防重放 / 限流，03-A7）。
- **拉**（三型连接器，taskrunner cron job 驱动，04-§4.10）：
  - `http-pull`：周期调对方 API，水位 = 时间戳 / 游标 / 页码；
  - `db-pull`：周期对对方数据库执行**参数化只读 SQL 模板**（审批入库，禁自由 SQL），水位列必填，行数 / 时长上限，每次拉取审计——对应所有者提到的"曾需要我们主动去数据库拉"的特殊情况；
  - `file-pull`：SFTP / 共享目录的导出文件（扫描器常见导出形态），可选。
- **水位表** `ingest_sources(source, mode[push|http-pull|db-pull|file-pull], adapter, cursor/watermark, schedule, last_run_at, last_status, last_error, enabled)`。
- **流水线**：原始落盘 `raw_ingest_events` → 源适配器归一化为 `security_findings`（漏扫发现字段：scanner / external_id / 资产标识符 / vuln_id(CVE) / severity / title / port·service / first_seen·last_seen / scanner_status / evidence）→ 资产门面解析（asset_ref + snapshot）→ 指纹（R1 规则：系统+类型+外部标识；漏扫稳定键建议 `asset_ref + vuln_id + port`，兼容扫描器 external_id 在重扫间漂移的常见情况）→ 风险单聚合（存在则计数 + last_seen，否则建单）。
- **推拉并存 ≠ 双通道**（2026-10-20 晚修订，所有者口径）：推/拉是接入层都要具备的能力，但**每类数据只走一种模式**（按源配置），因此不存在推拉双通道对账；指纹去重仍保留——它防的是重投 / 重拉 / 重试造成的重复，不是推拉差异。

**（d）源数据与平台数据的一致性（D19）**

背景：平台拿到原始发现后起工单跟踪到闭环，但**暂不反向推送闭环状态到数据源**，再次拉取时源侧仍显示"开放"，两边必然不一致。处理原则不是"谁覆盖谁"，而是**两边记的是不同事实——分字段归属、按时间判优**：

| 字段组 | 归属 | 再拉取时 |
|---|---|---|
| 源观测字段：`source_status`、`source_severity`、title / evidence、`source_observed_at`、`last_seen` | **源为准** | 每次更新快照 |
| 平台处置字段：`status`、owner、due、处置结论、复测记录、平台 severity 覆盖值 | **平台为准** | 永不被源覆盖 |
| 衍生判断：是否重开 / 抑制 / 计数 | 规则引擎 | 按 D13 重报语义 + 下述时间判优 |

**时间判优**：源记录的观测时间 `source_observed_at` **≤** 平台关闭时间 → 陈旧数据，只更新源快照、不动平台状态；**>** 平台关闭时间 → 源在我们关闭之后又观测到它 = 真实再检出 → 按 D13 重报列处理（已修复 → 重开，或先标"疑似回归待确认"由人确认；已接受 → 计数；误报 → 抑制）。这样"以平台为准"成立的同时，不会把真回归当陈旧数据吞掉。源无观测时间戳时，用其扫描批次 / 报告 ID 的变化作为"新观测"判据；两者皆无则默认陈旧、只计数并标"无法判优"交人工。

**唯一键**：按源配置**稳定键优先级**——① 源 `external_id`（该源跨扫描稳定时）② 语义键 `asset_ref + vuln_id + port/location`（external_id 在重扫间漂移的源用它）；两者都存，匹配按配置顺序（04-§4.10 连接器样例的 `identity` 段）。

**差异可见**：提供"源侧仍开放 / 平台已闭环"差异视图供审计——这是预期状态不是错误。反向回传状态 = 触发驱动（源平台提供状态 API 时走连接器动作，04-§3.7 / §4.9），暂无计划。

**（b）整改跟踪（R3 具体化）**：风险单→整改工单（S1 schema 字段预填：资产 / 漏洞 / 修复建议）→ 工单终态经事件面联动风险单（既定要求：可订阅、禁硬编码）。

**（c）人工复测与关单联动（2026-10-20 晚修订：暂不对接扫描器做自动复测）**

复测由人工完成：整改工单内置结构化"复测结论"段（S1 schema：结论枚举 + 复测人 + 复测时间 + 证据附件），填写后存档关单；关单经事件面（可订阅、禁硬编码——phase6 既定）联动风险单，规则如下（D13）：

| 工单关闭结论 | 风险单联动 | 重报（同指纹再进来）语义 |
|---|---|---|
| 已修复（复测通过） | → 关闭（已修复），复测人/时间/证据**快照**进风险单关闭记录 | 视为回归 → **重开**风险单，可选自动再建整改单 |
| 不修复 · 接受风险 | → 进 R2 接受单流程（需审批 + 有效期 + 到期重审），**不是关闭** | 有效期内 → 计数 + last_seen，不重开；到期 → 重审 |
| 误报 | → 误报关闭 + 指纹进抑制名单（可配时长） | 抑制期内不建单只记录 |
| 重复 | → 解绑并并入主风险单 | 随主单 |
| 取消 / 作废 | → 风险单回"待处置"，**不关** | 正常建单 |

配套规则：① **M:N 关联**（一张工单可覆盖同资产多个发现、一个风险单可拆多团队多工单）——风险单在**全部关联工单终态**后才联动；② **复核门可选**（phase6 R3 "复核态可选开关"）：默认关；高危 / 严重可开，开则关单后风险单先到"待复核"，由安全侧确认再关；③ **反向不自动**：风险单被人工先关时只通知关联工单负责人并打标，不自动关工单；④ 终态对账扫描 cron 兜底（phase6 既定）。扫描器 `scanner_status=fixed` 的自动复测信号 = 触发驱动增强，**暂无计划对接扫描器**。

**核心切片**：接入层（推两入口 + http-pull + db-pull）、漏扫适配器、台账聚合、风险单→工单、整改工单"复测结论"段、关单按结论联动风险单（D13）、通知。**补全切片**：file-pull、复核门开关、重报重开自动再建单、R2 四策略与接受单到期重开、R4 报表、批量下发向导；扫描器自动复测信号 = 触发驱动（暂无计划）。

**量级**：原 MVP 4–6 周 + 接入层 1.5–2 周 = **6–8 周**。**对 `docs/phase6/README.md` 的变更点**（采纳后落档）：R1 数据源第一档改为"推 + 拉（含 DB 拉）"，扫描器连接器从二档升一档（对象=漏扫结果平台，非扫描器直连）；R3 新增"人工复测与关单联动"小节（关闭结论映射 / M:N / 复核门 / 重报语义，即 D13 表）；R1"已关闭单重报语义须拍"由 D13 重报列回答；"不做"边界维持（不做 SIEM 关联分析 / 实时自动响应 / 扫描器直连自动复测）。

**外部动作前置（2026-10-20 双审计补列）**：漏扫平台契约获取 = phase6 立项批第一外部动作（推 API 形态 / db-pull 只读账号与水位列 / 稳定键 external_id 跨扫描稳定性核对）——契约未定不阻接入层按归一 schema 桩先行（04 号蓝图支撑），但阻漏扫适配器收口与 DoD 验收，立项批即启动获取。

### 4.2 phase7（接入扩源 + 自动化地基）

- **扩源**：SOC 告警、日志平台告警各一个源适配器（webhook 推为主，http-pull 兜底）；归一 schema 由"发现"扩到"告警"（03-A8 `security_alerts`，与 findings 共用指纹与聚合语义）；路由规则（expr-lang 匹配 → 建风险单 / 挂到既有 / 通知 / 抑制）与维护窗口；告警聚合视图（按资产 / 类别 / 源）。
- **自动化地基**（都是 ≤2 周的小件，但决定后续形态）：Action 注册表（03-A1，存量 audit_archive 宽松迁入）；service account + 委托三元组（03-A6）；调度分工收敛（03-A4 / D18：维护型扫描留进程内 CronScheduler，业务 / 拉取 / 脚本走 taskrunner）+ cronloop 分布式锁 + 一次性延迟任务；资产查询门面 + 读穿缓存可选（02-G1）；运行可观测 M4（指标 / 队列水位 / 失败率告警走 S6）。**M4 约定（09 号补强）**：Prometheus 暴露格式 + OpenTelemetry 语义、`trace_id` 贯穿 taskrunner → sandbox-runner → 回调；并补"计划任务总览"只读视图（并列 CronScheduler 与 taskrunner jobs，防双轨割裂）。
- **核心切片**：两源进来可见 / 去重 / 通知 / 手动转工单；Action 表 + 身份 + 调度分工口径落地。**补全切片**：自动建单规则细化、日志深链构造器、回传 SOC 状态。
- **出口**：一条真实 SOC 告警从进入到人工建单全程可审计；自动化路径审计三元组齐全。量级 6–8 周。

### 4.3 phase8（自动化能力中心 = SOAR 能力迁移，编排留 SOAR）

所有者 2026-10-20 晚口径：**公司已有 SOAR，第一步把 SOAR 的能力迁过来（任务中心预定义任务），流程调度先继续用 SOAR**。因此 phase8 **不建编排引擎**，形态收缩为"能力提供方 + 人机界面"：

- 脚本契约（05 号）+ sandbox-runner（03-A2 第一档隔离）+ 脚本库管理面（上传 / 审批工单 / 版本 / 预构建 / 运行历史）——上传自定义 Python 脚本执行，输入 / 输出按 manifest 的 JSON Schema 定义，任务与脚本同一契约；
- **预定义任务目录**：SOAR 现有 apps / actions 按使用频率逐个迁为 `actions(kind=connector|script)`，每个带 JSON Schema I/O；迁移期两边都有的能力以我们为准还是以 SOAR 为准，按能力逐个定（04-§4.4 拍板点）；
- **SOAR 双向集成**：入 = SOAR 以 service account 调 `/v1/action-invocations`（04-§3.2）执行我们的 Action，结果经出站 webhook（04-§3.7）或轮询取回；出 = 我们触发 SOAR playbook（`soar.playbook.run` 连接器动作），审批凭证随请求下发；SOAR 产出经统一接入层回流为事件；
- 工单动作面板（F6）+ 自助任务门（F18）：处置人不离工单页跑富化 / 处置，表单由 schema 生成；
- 声明式 HTTP 连接器通用件（04-§4.9）+ 凭据管理面（F13）；
- 轻编排只保留 `on_success` 钩子 + `job_runs.result` 摘要列（16 号最小替代，回调串联够用）；**自研 DAG 引擎 = Stage 2，既定排期而非触发驱动**（所有者：SOAR 只是过渡，最终全部迁回）：引擎 MVP 在 phase9 启动（先跑平台自有链路），playbook 设计器与 SOAR playbook 迁移在 phase10（§4.5）；
- 脚本内调用其它 Action：默认不开（避免隐式编排），组合由编排层（Stage 1 = SOAR）负责；需要时 SDK `zh.actions.invoke()` 受 `platformAccess` 白名单约束。
- **核心切片**：脚本跑起来 + SOAR 能调我们的 Action 并取回结果 + 工单页能调。**补全切片**：更多 SOAR 能力迁移、我们触发 SOAR playbook、凭据轮换。量级 **6–9 周**（原 8–11 周去掉 DAG MVP 与设计器，加 SOAR 集成）。

### 4.4 phase9（处置闭环深化 + 自研编排引擎 MVP）

- 告警→风险→工单全自动路由（规则成熟后开自动建单）；值班表 + 升级链 + 通知聚合防轰炸（F9）；runbook 绑定告警 / 风险类型（F10）；证据中心（F11）；处置结论回传来源系统闭环（F21）。
- **自研轻 DAG 引擎 MVP（Stage 2 起点）**：03-A5 六节点（action / script / approval / wait / branch / parallel）+ WorkflowEngine Port；先承载**平台自有**的巡检 / 处置链（如 到期扫描 → 建单 → 通知 → 超时升级），**不碰 SOAR 现有 playbook**；工作流推进需要 at-least-once → outbox（03-A3）此时正式落地。
- 补全：定期报告（F7）、到期扫描作业族（F8）、批量操作泛化（F15）、ATT&CK 标签（F16）。
- **出口**：典型告警端到端无人工搬运；夜间可达值班人；一条平台自有链路在自研引擎上跑通并可审计。量级 8–11 周。

### 4.5 phase10（编排迁移与 SOAR 退役——所有者：最终全部迁回）

- playbook 设计器：S2 画布复用 + 新 schema 适配层（02 号 B2 壳层去耦即为此预留）；节点面板直接列 actions 注册表。
- **SOAR playbook 迁移**：按使用频率排序，逐个在平台重建；前置 = "SOAR 动作 → 平台 Action"映射表（phase8 能力迁移时同步维护）；人工节点改为审批节点接工单；每条 playbook 迁后进入**双跑期**（两边都跑、以平台结果为准、差异对账），稳定后在 SOAR 侧停用。
- SOAR 退役或降为外部能力（只保留平台不打算承接的长尾）；模板市场（F22）承接高频 playbook 的部门内共享。
- **检查点（phase10 立项前，09 号补强，D23）**：以 phase8 迁移期掌握的三指标——SOAR playbook 数量、复杂度分布（步数 / 长等待 / 人工节点占比）、SOAR 续费成本——对阈值决定"全迁"还是"长期双栈（高频迁回、长尾留 SOAR）"；阈值届时按数据定。
- **出口**：高频 playbook 全部在平台运行；SOAR 可下线或仅余长尾。量级 6–9 周（取决于 playbook 数量与复杂度——需所有者给出 SOAR 现有 playbook 清单后再精估）。

### 4.6 phase11（智能面，LLM 供给门控）

> **状态（2026-10-20 晚）**：所有者对 AI 不熟、功能范围**后置讨论**；本段为候选形态，D8 / D10 / D17 转"后置讨论"。现在只保留零成本 AI-ready 设计位：Action 带 JSON Schema（A1）、on-behalf-of 身份（A6）——两者本就是 SOAR 集成所需，不为 AI 额外做任何事。

- LLMProvider 适配（OpenAI-compatible 起步，内网模型 / 公司 AI 网关换 adapter）；MCP server 暴露 Action（D10）；NL 查询走结构化 API + L2（禁 text-to-SQL）；告警摘要 / 分诊辅助。
- 补全：NL 任务下发（Responder 默认人工确认，D8）；处置建议；playbook 草稿生成。
- 门控条件：LLM 供给落地。供给早到可与 phase9/10 并行做 Provider 与 MCP server（小件）。量级 5–8 周。

### 4.7 M-UAA 插入策略

- 件 1（SSO，mock IdP）2–3 人日，可塞 phase5/6 任一间隙；
- 件 2–6（MQ 面）需内网与 MQ 资源，就绪即插；最可能落在 phase6–7 之间或 phase7 内；整体时间线后移约一个月；
- source 列 a/b/c 拍板建议在 phase6 建表前完成（迁移合批）。

### 4.8 AI 智能体平台对接（终态登记，触发驱动，D17）

- **双向形态**：出 = 平台调用智能体能力作为输入 / 任务（智能体 = 一种能力来源：连接器 `kind=agent` → `actions`，长任务按 taskrunner 异步语义）；入 = 智能体产出（分析结论 / 事件 / 处置建议）经统一接入层成为事件源；反向 = 智能体调用平台能力走 Action 暴露（MCP，D10）+ `on_behalf_of` 归因（A6）。设计见 04-§4.11。
- **门控**：智能体平台的供给与形态未明，与 LLM 供给同门控；不进 7/8/9 基线。**登记理由**：A1（能力来源 / Action 暴露）与 A7（事件来源）两个接口面已天然容纳它，届时只加适配器、零架构改动——这正是"先知道完整形态"的收益之一。
- **量级**：适配器 1–2 周 / 源 + 归因审计接线（复用 A6）。可并入 phase11 智能面，也可作独立触发驱动段。

## 5. 跨阶段不变量（第一天就守住，避免渐进画进死角）

1. **接入层 source adapter 模式**：任何源 = 接入模式（推 / 拉）× 适配器（normalizer）；归一 schema 共享；**禁止为单一源写专用表或专用流程**。
2. **指纹与聚合语义统一在 R1**：发现 / 告警 / 手动三类进同一聚合实体（risk_items，D5）；指纹规则按源可配但语义一致。
3. **Action schema 即契约**（03-A1）：phase6/7 新增的任何"动作"（建单 / 通知 / 回传）按 Action 形态注册，哪怕第一档只是内建 kind。
4. **资产引用一律 `asset_ref + asset_snapshot`**（D4），不建资产表。
5. **事件可订阅、禁硬编码**（phase6 既定）；S6 事件结构体可序列化，为 outbox（03-A3）留门。
6. **审计三元组** actor / principal / on_behalf_of：phase7 起所有自动化路径必带。
7. **standards 公约不破**：GET/POST、POST URL 无业务信息（webhook token 豁免 D6）、AK/SK、errcode 族、OKPage。
8. **迁移前瞻**：phase6 建表预留 phase7/8 列（risk_items：source_kind / alert_count / first_seen·last_seen / attack_tactics / asset_ref / asset_snapshot），减少后续加列迁移。
9. **调度分工边界**（D18）：进程内 CronScheduler 只做平台维护型扫描；业务 / 拉取 / 脚本一律 taskrunner。
