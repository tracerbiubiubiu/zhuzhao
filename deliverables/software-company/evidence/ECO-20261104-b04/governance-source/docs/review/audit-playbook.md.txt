# 全面审计指南与执行模板

> 定位：可复用的方法与检查清单，适用于首次全面审计、阶段收口、跨仓契约审计及专项复审；不绑定某次审计、某个工具或某个实施阶段。
> 本文承接 [standards.md](../standards.md) §12-10 检查类型学，不改变工程公约、权限架构或产品范围。具体仓库、提交、环境、裁剪项和进度记录在每次独立执行卡中。
> 状态：执行方法已落档，不代表任何实现已经审计通过。创建日期：2026-11-04。

## 1. 目标与适用方式

全面审计回答四个问题：需求与设计是否合理完整；实现是否兑现有效设计；关键机制在真实操作、并发和故障下是否正确；现有测试与运维证据是否足以支持交付声称。符合文档不等于设计正确，测试全绿也不等于能力闭环。

- 首次全面审计：按当前快照覆盖全部约定模块，并追溯关键设计演进；不能以近期 diff 代替全量范围。
- 阶段/发布审计：检查变更窗口及其上下游、共享组件和历史回归面；明确复用哪些既有结论及其基线。
- 专项审计：可裁剪阶段，但须写明排除项、理由及失去的保证，不能把专项结论表述为全项目通过。
- 修复复审：对照原发现与修复提交验证根因、同类路径和回归守卫；原报告保留时点事实，复审另记。

正文保留通用方法，项目特有热点和当前拍板引用权威登记处，不在这里复制易过期的状态数字。

## 2. 启动：先建执行卡与覆盖清单

每次执行卡必须填写：

1. 审计目标、类型、当前交付范围、未来规划参照范围及明确排除项。
2. 每仓路径、分支、完整 commit hash、工作区状态；增量审计另列起止提交和逐笔 hash。区分本地 HEAD 与已确认远端状态，不把前者称为已推送版本。
3. 在途改动归属与处理方式：默认以已提交快照为基线；未提交内容单列，不混进结论。
4. 设计 SSOT、有效决策、已废止方案、历史报告、已知债务及后续规划索引。
5. 实际依赖版本与部署版本：发布 tag/锁文件/镜像标识、replace/workspace 覆盖、运行二进制或前端产物来源。公共库 HEAD 不能替代消费者实际 pin 版本的审查。
6. 环境归属、可用测试资源、允许的操作、禁止项、账号和证据存放位置。
7. 阶段顺序、每阶段范围与出口、发现编号前缀、报告路径和交接方式。

准备项必须逐项记录已确认/待确认、证据与下一步，不能只有“阶段 0 未完成”。至少包括远端差集、发布 tag 对应提交及实际依赖解析、运行产物来源、会话归属、隔离栈首拉、角色账号矩阵和证据目录。历史环境故障须区分原始证据、当前配置与待验证线索，不能把旧坑直接写成当前必现事实。网络访问方式按实际环境选择并记录，不擅自修改 remote。

执行卡同时写明报告、指南和原始证据的 Git 归属；落盘、纳入版本管理、commit/push 是不同动作，不从落盘授权推导提交授权。未跟踪文件不能据此视为无主或可清理。证据目录按轮次/批次隔离，报告使用相对链接；原始日志和截图先脱敏审查，再按约定选择归档。

覆盖清单至少逐项记录：能力/场景、设计锚点、实现入口、装配与配置、上下游、数据/权限边界、测试与动态证据、结果、剩余盲区。状态区分未审、进行中、已审、受限、范围外；受限项必须说明原因和影响。

设计阅读本身也记录全文精读、相关章节精读或索引浏览，不能把目录检索声称为全文阅读。

## 3. 文档裁定与演进边界

按主题权威归属、决策状态和变更时间判断有效要求；冲突时保留双方锚点及待裁定事项，不自行翻案。项目范围以 [VISION](../VISION.md) 为准，工程约束以 [standards](../standards.md) 为准，当前能力与健康状态查 [项目控制台](11-project-control.md)。兄弟服务契约回各自权威文档核对，主仓镜像不能替代原文。

逐项区分已交付承诺、已批准待实施、端口/桩就绪、触发驱动、明确不做、历史方案和已接受风险。未来规划用于检查前置、抽象边界、兼容性及不可逆决策；未来能力尚未实现本身不是当前缺陷。已接受取舍仍须核对适用假设是否失效、触发信号是否可观测、承接批次是否有效。

规划抛光轮执行 standards §12-10 截断规则；实现、安全、并发、契约与端到端核验不适用该截断。全面审计不能因为剩余发现全为 P2/P3 而提前停止覆盖。

## 4. 默认七阶段

阶段可以按执行卡拆批或裁剪。静态深读与动态验证随批相互印证；前端与跨仓消费点随相关模块提前检查，不全部后置。

### 阶段 0：基线与覆盖

完成 §2，识别在途会话、真实依赖和环境副作用。出口：范围可枚举、快照可定位、证据规则与验证限制明确；尚未验证的准备项不得标为完成。

静态准备与动态准备分别设出口：基线、范围和文档权威确认后可开始不依赖环境的设计阅读；动态验证须先满足对应批次的隔离、产物来源、账号和清理条件。环境未就绪不应阻断独立静态工作，也不能省略动态轨或把整阶段标为完成。

### 阶段 1：设计、边界与演进

检查需求闭环、概念模型、领域职责、信任边界、威胁模型、业务不变量、一致性承诺及演进前置。覆盖正常/拒绝/失败/重试/取消/恢复/删除/历史追溯。出口：设计裁定清单、不变量及实现核验项齐备；设计缺陷可独立成立，不以是否已实现决定严重度。

### 阶段 2：公共底座与身份权限

检查实际消费版本的公共包、认证会话、身份生命周期、角色组织、权限策略、网关与审计基础。验证提权、权限回收、跨组织/跨角色、签名规范化、重放边界、身份归因及依赖失败。出口：关键安全边界有正反证据，或明确验证限制。

### 阶段 3：业务模块与公共能力

按领域逐条审查用例、状态机、输入校验、字段与模板、存储、事件、通知、查询/导出等。追踪入口→服务→仓储→事务→副作用→展示与留痕；检查装配、配置与真实消费者。出口：各模块的设计、实现、测试与台账可逐项对账。

### 阶段 4：兄弟服务与跨仓闭环

兄弟仓既独立审查内部实现，也联合验证调用链。检查契约两端、错误与超时、版本兼容、重试/幂等/租约、部分失败、数据归属与故障恢复。出口：关键跨仓契约有生产方/消费方双侧证据，公共库发布与消费版本可追溯。

### 阶段 5：前端功能、交互与视觉体验

以真实角色、完整任务和浏览器证据检查功能、信息架构、操作效率、反馈防错、视觉一致性和基本可访问性，详见 §6。出口：关键旅程完成，状态与窗口场景覆盖清楚；审美建议与使用缺陷分开。

### 阶段 6：横切复核与总报告

跨模块复核 §5 各维度及未决疑点，对账已知债务、发现与整改承接。出口：所有范围项有结论或限制、发现已复核去重、证据可定位、未验证项和残余风险明确。审计阶段完成与产品通过交付门禁是两个结论。

## 5. 横切检查维度

以下维度分摊到各阶段检查，最终再复核组合路径：

- **设计与需求**：场景是否闭环、概念是否混淆、边界与抽象是否合适、默认值与隐含假设是否仍有效；端口有无实际可用契约。
- **权限不变量**：列表/详情/导出/附件同源可见性；可见不等于可写；账号/权限回收无其他凭证旁路；前端显隐不代替后端授权；普通主体不能通过系统动作放大授权。
- **威胁与输入**：匿名、普通用户、委托管理员、全局管理员、服务调用方各自可达面；认证绕过、对象枚举、越权、注入、SSRF、XSS、CSRF、路径穿越、文件/导入滥用、敏感泄漏及资源耗尽。内部回调、下载、探针、文档与管理工具也属于攻击面；内网不自动豁免。
- **事务与并发**：TOCTOU、锁顺序、CAS、嵌套取池、并发合并、重复副作用、连接/协程泄漏；查询和检查必须使用正确事务连接。按池容量验证，不能用机器核数替代容量边界。
- **一致性与恢复**：DB/Redis/队列/对象存储之间的部分成功；提交后崩溃、发送成功记账失败、超时但业务已完成、重复/乱序/迟到、租约接管、关闭排空；逐链声明丢失窗口、重复窗口、补偿与人工恢复办法。
- **数据生命周期**：唯一性、软删复用、关联完整性、孤儿、历史快照与归因、保留/归档/清理；迁移存量兼容、锁窗口、失败中断、往返及代码/DB 回滚耦合；DB、文件、配置、密钥和归档卷分别能恢复什么。
- **容量与性能**：N+1、无界查询、深分页、索引、连接池预算、大请求/响应、流式内存、缓存击穿、队列积压、扫描成本、超时及取消传递。实验声明量级、资源和指标；不在共享栈做无界压测。
- **观测与运维**：能否区分未启动/失败/慢/成功但结果丢失；注册不等于启动，健康不等于业务正确，无报错不等于成功。指标、日志、告警、巡检与 runbook 是否可用且可归因。
- **测试有效性**：断言是否测真实行为、mock 是否替代关键决策、负向是否因错误原因通过、并发是否假绿；CI 是否真跑声称门禁、架构守卫/迁移清单/codegen 是否覆盖实际面；检查端到端夹具隔离及清理。
- **构建与供应链**：依赖/tag/锁文件/镜像/生成物与产物能否追溯，依赖漏洞的实际可达面、许可证与密钥处理；网络漏洞扫描等有时效结果须注明日期与来源。
- **治理与台账**：提交声称与事实独立复验；已修未销/未修误销/半清/触发过点/重锚遗漏；同一根因跨仓合并登记，不重复计数。

## 6. 前端专项：功能、习惯与美观

源码检查与真实浏览器走查结合，不以截图代替操作、不以 E2E 绿代替体验判断。

1. **任务与导航**：用典型角色完成核心旅程；检查术语、菜单分组、入口、操作位置、返回路径、搜索/筛选/分页、表单顺序、合理默认值、跨页状态、重复输入与操作步数。用户不应理解内部实现才能使用。
2. **视觉与信息层级**：布局、留白、对齐、字体、色彩、图标、表格密度、主次操作、弹层与跨页一致性；长中文/工号/标题/错误/多图等真实内容下是否截断失义或溢出。结合受众与任务说明判断依据，不把个人偏好当缺陷。
3. **反馈与防错**：加载/处理中/成功/失败是否明确；错误能否指导下一步；重复提交、误删、未保存退出、并发冲突、过期会话、网络中断、危险默认值与恢复路径。
4. **基本可访问性**：对比度、键盘顺序与可达性、焦点、表单标签、点击区域、弹层焦点管理；不能只靠颜色、hover 或图标表达关键状态。
5. **场景组合**：正常、空、加载、失败、无权限、长内容；约定桌面窗口尺寸与缩放下的内部滚动、分页位置和操作可达性。未承诺移动端不等于可以忽略正常桌面窗口；具体视口记录在执行卡。
6. **工程消费面**：路由/按钮码、API 字段与序列化、类型生成接线、刷新单飞、缓存失效、错误展示、权限改变及退出清理；前后端对同一表达式/状态的理解是否一致。

体验发现区分阻碍任务、违反已定规范、视觉一致性、审美建议，并记录角色、页面、操作、截图/录屏、实际影响和建议。若只做专家走查，明确未进行真实用户研究；不虚报用户验证或标准认证。

## 7. 纯审计操作边界

- 默认不改受审实现、不 commit/push、不运行 `make acceptance`，也不直接调用四档脚本规避禁令。报告与执行卡落盘须有明确授权；这种文档授权不扩大为修代码或改环境授权。
- 隔离副本按固定提交构建，数据库、Redis、对象存储、端口及数据与共享栈隔离。先审查脚本副作用，再运行 lint/test/build/E2E；不得因命令名看似只读而直接执行自动修复、codegen、globalSetup、清库或服务重启。
- 测试证据记录实际运行源码/产物来源，不能用不明版本的常驻服务证明固定提交正确。环境受限不放宽结论；只做静态核验时如实标注。
- 项目账号与并发环境纪律遵 [runbook](../runbook.md) §4/§7；人工与 agent 多账号测试使用专属测试号，不改 E000001。既有测试若隐含改密/重置共享数据，先处理隔离与夹具前提，不能直接运行。
- 变异实验仅在临时副本进行；记录相对原快照的实验差异，恢复后复验。并发修复守卫按 standards §12-10 移除修复连跑至少 8 次并稳定变红；失败原因须与目标缺陷一致。假绿要披露，不能用扩大并发挤爆资源伪造失败。
- P0/P1 证实即报告并说明影响；不等待整批收尾，也不擅自修复。敏感证据脱敏，只保留必要复现信息，不落真实密钥与公司数据。

### 7.1 授权修复批与审计并行

通用处置规则以 [standards §12-10](../standards.md) 为准。首次进入修复批在执行卡登记授权范围、发现号、修复前基线、文件归属、验证环境和门禁计划；已有授权不反复询问。审计证据及原基线保持不变，修复在独立分支/工作树推进，其他模块静态审查可继续。

- P0 证实后立即报告、固定复现，再开修复批；P1 当前模块/批次收口时合并同根因与同类路径安排；P2/P3 记账并与后续阶段对齐。不能以紧急为由跳过设计裁定或编造验证结果。
- 修复范围由根因决定，不将无关重构和新能力混入；跨仓同时记录生产/消费方，公共库实际发布版本、消费者 pin 与工作区覆盖须可区分。
- 修复代码先让原复现失败、修复后通过，并补同类/边界测试；并发修复执行既有至少 8 轮变异要求。复验从提交后固定快照独立构建；若同一会话兼做实现与复验，也必须重新执行验证，不能以编写者判断代替证据。
- 正常修复批遵守开发门禁、三节说明、文档同步及显式路径提交；未满足门禁不得标产品交付完成。仅报告落档或测试环境授权不扩为实现授权，push 独立处理。
- 状态分别记录待修/待复验/复验关闭，以及未发布/已发布/已部署。原审计报告保持时点事实；复验报告登记完整修复提交清单、构建来源、结果与残余限制，再回链执行卡和相应台账。

## 8. 证据、分级与发现状态


### 8.1 证据要求

每条发现包括设计依据、实际行为、触发条件、影响与边界、可点击文件行号、文件路径及符号、所属完整提交、复现步骤与结果。跨仓分别标生产方和消费方版本。行号辅助定位，符号与 commit 保证代码移动后可追溯。

证据等级分别标注：动态复现（含环境/命令/退出码/关键输出）、静态确认（完整可达路径与约束）、待验证假设。历史测试/CI 报告只证明其当时基线，不写成本轮实跑。完整日志和截图以相对报告的证据路径引用；记录数据清理情况。

### 8.2 性质与严重度分列

- 性质：设计缺陷、实现缺陷、跨仓契约、文档/台账漂移、验证缺口、体验问题、已接受取舍或改进建议。
- P0：安全/数据损坏/门禁失效；P1：功能缺陷/台账失真；P2：设计缺口/口径漂移；P3：措辞/记账。按实际影响、可达性和暴露范围裁定，设计缺陷同样可能为 P0/P1，不能只按名称机械降级。
- 未验证假设不混入已确认缺陷统计；纯审美偏好不自动赋缺陷等级。已接受取舍列假设、残余风险、翻案触发与承接处。
- 编号在本轮内稳定（如 `<轮次>-B03-F01`），去重合并保留旧号指针。状态可为待复核、确认、误报、重复、已接受、待修、待复验、复验关闭；有修复提交不等于复验关闭。

## 9. 每批报告与交接模板

时点报告按 [standards](../standards.md) §12-3 归档；本项目默认 `deliverables/software-company/zhuzhao-<主题>-<YYYY-MM-DD>.md`。技术复盘进入 `docs/review/` 时再按目录编号规范办理，不把长期方法文档编号为某次复盘。

```markdown
# <主题>审计报告

## 范围与基线
目标、纳入/排除项、五仓或相关仓完整 hash、增量提交清单、在途改动处理。
设计 SSOT 与决策状态、实际依赖/运行产物、验证环境和允许操作。

## 覆盖与结论
逐能力列设计阅读、实现入口、测试/动态证据、结果和剩余盲区。
分别列已兑现、缺陷、文档漂移、已接受取舍、未来前置。

## 发现
编号、性质、P 级、证据等级、状态。
设计预期、实际行为、触发条件、影响/范围。
文件路径+符号+可点击行号+commit；跨仓两侧锚点。
复现步骤、命令、退出码、关键输出/截图证据。
修复建议、同类扫描范围、回归要求、建议挂点；不代所有者拍板。

## 验证证据与限制
本轮实跑、历史证据、静态确认、未运行与原因分列。
并发/变异/故障注入结果，环境清理与实验副本差异。

## 交接与下一批
覆盖游标、发现状态、未决设计问题、证据路径、下一批入口与依赖。
新增提交差集和是否纳入，建议所有者回填的台账位置。
```

接续会话先读执行卡、最新批报告、覆盖台账与在途记录；核对提交变化后从未覆盖项继续，不重做已完成部分、不凭聊天摘要推定已验证。报告落盘权限不足时在对话交付，说明未落档。

### 9.1 修复提交与复验记录

提交格式 SSOT = standards §12-9。新 fix 提交固定三节，以下为模板；占位内容必须替换为实际事实，不能把计划写成验证通过。

```text
fix(<模块>): <中文摘要，≤50 字，结尾无句号>

改动摘要：
① <根因与修复方式；单条不编，多条连续编号>
同类扫描：<实际扫描入口、结果及残留>

影响面：
<模块、路由、权限、依赖与存量兼容、配置或迁移影响>

验证证据：
<修复前基线与复现；修复后回归/同类/边界结果>
<并发变异及必要门禁的实际结果；未覆盖项与原因>

Refs: <审计发现编号；非审计修复不虚造编号>
```

修复前基线与报告路径可写入提交正文；提交完成后把其完整 hash 与跨仓实际消费版本写进复验报告，避免正文要求引用自己的 hash。复验另记目标发现、修复窗口、构建/环境、原复现与新增回归、变异结果、门禁、结论/限制和发布部署状态。提交标题声称修复不等于发现已关闭。

批号先在执行卡登记主题、负责人/会话与时间，再开始使用；并行会话先占先用，冲突时重新分配未使用编号，不改已发布发现号。取消批次保留占号记录，避免后续误复用。

## 10. 收口与维护

每批结束前确认：范围项均有结论或限制、发现已交叉复核与去重、关键证据可重放、未覆盖路径列明。最终汇总设计裁决、跨仓契约、覆盖与限制、残余风险、整改优先级及依赖、下一阶段硬前置。

总报告前重新核对所有受审仓的完整 HEAD、工作区及相对基线差集；逐项裁定新增提交纳入复核或排除，并写明结论截止版本。不得只在接续时检查版本，也不能把旧基线结论推广到未审的新提交。

未通过产品要求的门禁不能标记产品交付完成；纯审计禁跑验收时如实声明，本轮审计结论不替代 acceptance。控制台与债台账需回填时提示所有者；只有明确授权才直接改业务健康状态。

方法的改进回本文；某次基线、进度、计数和结论只回该次执行卡/报告。更新方法须核对 AGENTS、standards 与 runbook，不把实例中的约束误升格为所有审计通则。
